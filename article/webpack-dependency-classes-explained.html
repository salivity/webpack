Webpack Dependency Classes Explained

This article explores how Webpack models module connections under the hood using internal Dependency classes. It covers how Webpack's parser translates source code import statements into Dependency instances, how these objects build and navigate the ModuleGraph, and how specialized DependencyTemplate classes rewrite raw source code into final executable bundle code.

The Role of the Dependency Base Class

In Webpack, a module does not directly reference other modules. Instead, it holds a list of Dependency objects. When Webpack parses a file, it builds an Abstract Syntax Tree (AST) using Acorn. Whenever the parser encounters an import, export, or dynamic import statement, it instantiates a corresponding subclass of the base Dependency class.

The Dependency class encapsulates three critical pieces of information:

  1. The Request: The path or module specifier string (e.g., './math', 'lodash').
  2. Code Locations: The source ranges (character start and end offsets) where the import statement or identifier appears.
  3. Module Metadata: Information regarding used exports, side effects, and whether the reference is static or asynchronous.

Common Dependency Subclasses

Webpack uses specialized subclasses tailored to different module formats and ECMAScript features:

  • HarmonyImportSideEffectDependency: Represents an ES module import statement (e.g., import './styles.css') to ensure side-effect execution.
  • HarmonyImportSpecifierDependency: Represents a specific imported binding (e.g., import { add } from './math'). It tracks which export name is requested to enable tree-shaking and dead-code elimination.
  • CommonJsRequireDependency: Generated when Webpack detects a CommonJS require(...) call.
  • ImportDependency: Created for dynamic import() expressions, signaling to Webpack that a split point (new chunk) should be created.

Connecting Dependencies to the ModuleGraph

During the compilation phase, Webpack traverses the dependency tree using the Compilation and NormalModuleFactory objects. The Dependency object acts as an edge connecting two module nodes:

  1. When a module is parsed, its discovered Dependency instances are added to the module's dependencies array.
  2. Webpack passes each Dependency to the NormalModuleFactory, which resolves the request path and constructs the target NormalModule.
  3. The relationship is stored in Webpack's ModuleGraph data structure via methods such as moduleGraph.setResolvedModule(dependency, module).

By decoupling modules through Dependency objects, Webpack can inspect, modify, or prune connections (e.g., removing unused imports) without mutating the modules themselves.

Code Generation via Dependency Templates

Dependency classes not only define relationships in the graph, but they also dictate how source code is transformed. Most Dependency subclasses have an associated DependencyTemplate (such as HarmonyImportSpecifierDependency.Template).

During the code generation phase:

  1. Webpack iterates through all dependencies attached to a module.
  2. It invokes the static apply method on the matching DependencyTemplate.
  3. The template uses the source ranges stored inside the Dependency object to replace original syntax (like import { add } from './math') with runtime Webpack code (like /* harmony import */ var _math__WEBPACK_IMPORTED_MODULE_0__ = __webpack_require__(/*! ./math */ 1);).

Through this mechanism, Webpack avoids costly full-AST regenerations, relying instead on precise string replacements driven directly by its Dependency instances.
