Webpack Runtime Isolation for Embedded Widgets

Embedding web widgets on third-party websites requires strict isolation to prevent script collisions, styling overrides, and runtime conflicts with the host site. Webpack achieves runtime global isolation primarily by scoping its module loader, namespacing chunk-loading mechanisms, encapsulating the bundle execution context, and preventing global polyfill contamination. Configuring Webpack properly ensures that a widget can safely execute alongside host scripts—including other independent Webpack bundles—without interfering with the global window object.

Namespacing Chunk Loading with uniqueName

By default, Webpack 5 uses an array on the global window object to manage asynchronous chunk loading and code splitting. This property is typically named window.webpackChunk<name>. If both the host application and the embedded widget run Webpack without proper namespacing, one will overwrite the other's chunk registry, causing script failure.

Webpack isolates this runtime global via the output.uniqueName configuration setting. Specifying a unique identifier changes the internal array name to avoid collisions:

module.exports = {
  output: {
    uniqueName: 'myCustomWidget',
    // Generates: window.webpackChunkmyCustomWidget
  },
};

This ensures the widget's asynchronous chunks are pushed to and resolved from its own dedicated registry, completely separated from any Webpack instances running on the host page.

Encapsulating Code with IIFEs and Library Formats

To prevent module variables from leaking into the host's global execution context, Webpack wraps the generated bundle inside an Immediately Invoked Function Expression (IIFE).

You can control this encapsulation using the output.iife and output.library options:

module.exports = {
  output: {
    iife: true,
    library: {
      name: 'MyWidget',
      type: 'umd', // or 'window', 'var'
      export: 'default',
    },
  },
};
  • output.iife: true ensures that internal module variables, scoped runtime helpers, and closure-bound values do not bleed into the global window scope.
  • library.type allows you to selectively expose only the necessary public API (for example, mounting functions or event emitters) to a single namespace on the host window.

Managing Runtime Chunks

In multi-bundle setups, Webpack generates a runtime chunk responsible for linking modules and handling dependency resolution. If this runtime chunk is shared incorrectly across entries, widget logic can corrupt host execution.

For standalone widgets, it is standard practice to inline the runtime within the bundle entry point rather than creating a separate file, or to namespace the runtime execution context:

module.exports = {
  optimization: {
    runtimeChunk: false, // Inlines runtime into entry scripts
  },
};

Keeping the runtime inside the widget's primary bundle avoids loading extra network dependencies and ensures that all module lookup tables (__webpack_modules__ and __webpack_require__) exist purely within that script's closure.

Internal Module Scoping

At the module level, Webpack does not rely on global registers to map dependencies. Instead, it compiles each file into a function enclosure passed to an internal module map:

(function(module, __webpack_exports__, __webpack_require__) {
  // Module code executes within this local scope
});

Because Webpack transforms CommonJS and ES module imports into calls to its localized __webpack_require__ function, dependencies are registered and resolved internally. This completely prevents variable name collisions with host-level scripts that rely on identical global variable names.

Preventing Prototype and Polyfill Pollution

While Webpack isolates its own module and chunk execution, standard Babel or Core-JS polyfills included in a bundle can still mutate global prototypes (like Array.prototype.includes or window.Promise).

To achieve true runtime isolation when polyfills are necessary:

  • Use @babel/plugin-transform-runtime with Core-JS 3.
  • Set the option corejs: 3.

This instructs the compiler to rewrite references to native APIs into pure imports pointing to internal helper libraries, avoiding any direct modifications to global host prototypes.
