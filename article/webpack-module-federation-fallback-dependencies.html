Webpack Module Federation Fallback Dependencies

Webpack Module Federation handles remote micro-frontend failures by combining shared scope negotiation, semantic versioning constraints, and runtime fallbacks configured in the build settings. When a remote container fails to load, Webpack prevents fatal application crashes by falling back to locally bundled copies of dependencies and allowing dynamic error-handling strategies. This article explains the technical mechanisms Webpack uses to detect remote load failures, negotiate shared module scopes, and resolve fallback dependencies.

The Role of the Shared Scope

At the heart of Webpack Module Federation is the global shared scope object, represented internally as __webpack_share_scopes__. When a host or remote container initializes, it registers its available shared modules into this scope along with metadata such as version numbers, priority, and loading status.

Under normal circumstances, Webpack queries this shared pool to determine the highest compatible version of a library (e.g., React, Lodash) to avoid loading duplicate code. Each micro-frontend that lists a library under the shared configuration can act as either a provider, a consumer, or both.

How Fallback Dependencies Are Resolved on Remote Failure

When a remote micro-frontend fails to load—due to network drops, a missing remoteEntry.js, or a runtime script error—the fallback resolution proceeds through the following sequence:

  1. Failure to Populate the Shared Scope: If the remote container fails before executing its initialization function, it never registers its local versions of dependencies into __webpack_share_scopes__. The shared registry remains populated only by the host and any other remotes that initialized successfully.
  2. Version Negotiation with Remaining Providers: When the host or another container requests a shared module, the Webpack runtime searches the shared scope for an entry that satisfies the requested semantic versioning range (requiredVersion).
  3. Falling Back to the Local Build: If the failed remote was expected to provide a dependency, but no valid instance exists in the shared scope, Webpack checks whether the consuming application has a bundled fallback. By default, any package listed in shared includes a local fallback module unless explicitly disabled. Webpack executes this local factory function to instantiate the bundled dependency.
  4. Behavior with import: false: If a micro-frontend sets import: false for a dependency in its shared configuration, it designates that dependency as an external requirement that must be provided by another container. If the remote providing that package fails, Webpack cannot fall back to a local copy and will throw an unhandled runtime error (Shared module is not available for consumption).

Singleton and Strict Version Enforcement

Configuration options within the shared object significantly influence fallback behavior:

  • singleton: true: Webpack permits only one instance of the module in the shared scope. If a remote provides a newer version of a singleton library but fails to load, Webpack will use the host’s local version instead. A warning will only be emitted if version constraints are violated.
  • strictVersion: true: Webpack rejects fallbacks that fall outside the specified requiredVersion range. If the remote providing the valid version fails and the local fallback version does not satisfy the constraint, module execution halts.
  • requiredVersion: Dictates whether the local fallback or an alternative remote's shared dependency matches the semver criteria.

Runtime Catch Blocks and Dynamic Remotes

While Webpack natively resolves shared libraries back to local bundles, loading remote components directly (such as import('remoteApp/Widget')) requires deliberate runtime handling. If remoteEntry.js is unreachable, the import promise rejects.

To ensure component-level fallbacks, developers implement two primary patterns alongside Webpack's module resolution:

  • Promise-Based Dynamic Remotes: Remote entry URLs can be wrapped in promise-based scripts within webpack.config.js. If the primary remote URL fails to resolve, the promise catches the error and attempts to fetch an alternative URL or resolves to an empty module.
  • UI-Level Error Boundaries: Wrapping dynamic imports in standard JavaScript catch() handlers or React Error Boundaries allows applications to gracefully catch the failed module load and render a local fallback component instead of crashing the host tree.
