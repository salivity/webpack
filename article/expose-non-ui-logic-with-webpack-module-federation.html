Expose Non-UI Logic with Webpack Module Federation

Webpack Module Federation is commonly associated with sharing user interface components across micro-frontends, but it is equally suited for distributing headless, non-UI logic. This article explains how to expose and consume non-UI code—such as pure utility functions, API clients, and centralized state stores—across distributed applications, while ensuring state consistency and managing dependencies using the ModuleFederationPlugin.

Configuring the Remote Application to Expose Logic

Exposing non-UI modules uses the exact same exposes configuration as exposing UI components. In the remote application's webpack.config.js, map a public module key to the local file path containing your utilities or store definitions.

// remote/webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  // ... other webpack config
  plugins: [
    new ModuleFederationPlugin({
      name: 'utility_provider',
      filename: 'remoteEntry.js',
      exposes: {
        './formatters': './src/utils/formatters.js',
        './authStore': './src/store/authStore.js',
      },
      shared: {
        // Shared dependencies are declared here
      },
    }),
  ],
};

The underlying file is simply standard JavaScript or TypeScript:

// remote/src/utils/formatters.js
export function formatCurrency(amount, currency = 'USD') {
  return new Intl.NumberFormat('en-US', {
    style: 'currency',
    currency,
  }).format(amount);
}

export function slugify(text) {
  return text.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/(^-|-$)/g, '');
}

Consuming Utilities in the Host

The host application specifies the remote container in its configuration and imports the non-UI module directly.

// host/webpack.config.js
new ModuleFederationPlugin({
  name: 'host_app',
  remotes: {
    utility_provider: 'utility_provider@http://localhost:3001/remoteEntry.js',
  },
});

You can then consume the exposed logic in your code via static or dynamic imports:

// host/src/index.js
import { formatCurrency } from 'utility_provider/formatters';

console.log(formatCurrency(1250)); // "$1,250.00"

Exposing State Stores and Ensuring Singletons

Sharing state across micro-frontends introduces a critical requirement: store libraries and instances must remain singletons. If both the host and remote bundle their own copy of a state management library (such as Zustand, Redux, or Pinia), they will operate on separate instances, breaking state synchronization.

1. Configure the shared Option

To prevent duplicate library instances, declare the state management library inside the shared scope on both the host and the remote, marking it as a singleton.

// webpack.config.js (both host and remote)
shared: {
  zustand: {
    singleton: true,
    strictVersion: true,
    requiredVersion: '^4.5.0',
  },
}

2. Expose the Store Instance

Create and export the store instance or store hook from your remote application:

// remote/src/store/authStore.js
import { create } from 'zustand';

export const useAuthStore = create((set) => ({
  user: null,
  isAuthenticated: false,
  login: (userData) => set({ user: userData, isAuthenticated: true }),
  logout: () => set({ user: null, isAuthenticated: false }),
}));

3. Consume the Shared Store

Import the shared store into the host application. Because the underlying library is treated as a singleton, any updates dispatched from one micro-frontend update the state in all other micro-frontends consuming that store.

// host/src/App.js
import React from 'react';
import { useAuthStore } from 'utility_provider/authStore';

export function UserProfile() {
  const { user, logout } = useAuthStore();

  if (!user) return <p>Not logged in</p>;

  return (
    <div>
      <p>Welcome, {user.name}!</p>
      <button onClick={logout}>Sign Out</button>
    </div>
  );
}

Key Considerations for Non-UI Sharing

  • Initialization Order: Ensure the host application initializes its Module Federation container before executing shared logic. Dynamic imports (import()) in a bootstrap file allow Webpack to load asynchronous chunks and negotiate shared scopes.
  • TypeScript Types: Module Federation does not share type declarations at runtime. Use tools such as @module-federation/typescript or publish separate .d.ts packages to ensure type safety in TypeScript projects.
  • Network Latency: Non-UI functions fetched across remotes incur network latency on the initial load. Bundle essential initialization logic locally and reserve federated sharing for decoupled, domain-specific utilities or global state.
