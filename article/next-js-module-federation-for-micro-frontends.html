Next.js Module Federation for Micro-Frontends

This article explains how to build a scalable micro-frontend architecture by integrating Webpack Module Federation into Next.js applications. It covers using the dedicated Next.js Module Federation plugin, configuring both host and remote applications in next.config.js, managing shared dependencies, handling Server-Side Rendering (SSR), and dynamically consuming federated components.

Understanding the Integration Challenge

Webpack Module Federation allows multiple independent builds to share code and runtime dependencies dynamically. However, implementing it in Next.js presents unique challenges because Next.js features a specialized compilation pipeline for both Node.js (server-side) and browser (client-side) environments, alongside custom routing and asset optimization. To bridge this gap seamlessly, developers utilize @module-federation/nextjs-mf, a plugin specifically designed to handle Next.js chunking and SSR compatibility.

Step 1: Install the Required Plugin

In both your host (shell) and remote applications, install the Next.js Module Federation plugin:

npm install @module-federation/nextjs-mf

Step 2: Configure the Remote Application

The remote application exposes specific components or utilities to be consumed by other applications. Modify the remote's next.config.js:

const NextFederationPlugin = require('@module-federation/nextjs-mf');

module.exports = {
  webpack(config, options) {
    if (!options.isServer) {
      config.plugins.push(
        new NextFederationPlugin({
          name: 'remoteApp',
          filename: 'static/chunks/remoteEntry.js',
          exposes: {
            './Button': './components/Button.js',
          },
          shared: {
            react: { singleton: true, requiredVersion: false },
            'react-dom': { singleton: true, requiredVersion: false },
          },
        })
      );
    }
    return config;
  },
};

This configuration exposes ./components/Button.js under the module identifier './Button' and outputs a manifest file named remoteEntry.js.

Step 3: Configure the Host Application

The host application acts as the shell that consumes federated code from the remote. Update the host's next.config.js:

const NextFederationPlugin = require('@module-federation/nextjs-mf');

module.exports = {
  webpack(config, options) {
    config.plugins.push(
      new NextFederationPlugin({
        name: 'hostApp',
        filename: 'static/chunks/remoteEntry.js',
        remotes: {
          remoteApp: `remoteApp@http://localhost:3001/_next/static/${options.isServer ? 'ssr' : 'chunks'}/remoteEntry.js`,
        },
        shared: {
          react: { singleton: true, requiredVersion: false },
          'react-dom': { singleton: true, requiredVersion: false },
        },
      })
    );
    return config;
  },
};

The dynamic path ensures that Next.js loads the appropriate SSR or client-side entry file depending on the execution context.

Step 4: Loading Remote Components

In Next.js, federated components are best loaded dynamically to prevent hydration errors and handle network latency:

import dynamic from 'next/dynamic';

const RemoteButton = dynamic(() => import('remoteApp/Button'), {
  ssr: true,
  loading: () => <p>Loading remote button...</p>,
});

export default function HomePage() {
  return (
    <main>
      <h1>Host Application</h1>
      <RemoteButton />
    </main>
  );
}

Setting ssr: true allows the remote component to render on the server if the remote entry supports SSR, while ssr: false falls back to purely client-side rendering.

Handling Shared State and Best Practices

  1. Singleton Management: Always set core libraries like react and react-dom as singletons to prevent multiple instances from breaking React context or hook lifecycles.
  2. Error Boundaries: Wrap remote imports in React Error Boundaries to prevent a failed remote deployment from taking down the entire host application.
  3. Independent Deployments: Ensure remote entries are deployed with reliable caching headers, caching static chunks indefinitely while serving remoteEntry.js with short cache durations or no-cache to facilitate real-time updates.
