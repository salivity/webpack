Configure Webpack for Manifest V3 Service Workers

Migrating to or developing for Manifest V3 (MV3) requires replacing persistent background pages with background service workers. This guide outlines how to configure Webpack to compile scripts specifically for the Web Extension Manifest V3 service worker environment. It covers setting the proper execution target, preventing unsupported browser API polyfills, handling bundle chunking constraints, and managing the manifest.json file.

Key Technical Constraints in Manifest V3

Manifest V3 background service workers run in a specialized environment that differs from traditional web pages:

  1. No DOM or window object: Service workers execute in the WorkerGlobalScope (self). Any runtime reliance on window will trigger an execution error.
  2. Synchronous registration: Service worker event listeners (such as chrome.runtime.onInstalled) must be registered synchronously on the initial turn of the event loop.
  3. Chunk loading limitations: Dynamic chunk loading (code-splitting via import()) can fail if not properly declared as ES modules or if runtime chunk-loading mechanisms attempt to manipulate the DOM.

Core Webpack Configuration

To compile a Manifest V3 background service worker properly, Webpack needs specific output settings and the webworker target.

1. Install Dependencies

Install the core Webpack tools and plugins:

npm install --save-dev webpack webpack-cli copy-webpack-plugin

2. Configure webpack.config.js

Create or update your webpack.config.js with the following configuration:

const path = require('path');
const CopyPlugin = require('copy-webpack-plugin');

module.exports = {
  mode: 'production', // Use 'development' for unminified output during debugging
  target: 'webworker', // Configures the runtime to use 'self' instead of 'window'
  entry: {
    background: path.resolve(__dirname, 'src/background.js'),
  },
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].js',
    clean: true,
  },
  optimization: {
    // Disable code splitting for the service worker to generate a single standalone file
    splitChunks: false,
    runtimeChunk: false,
  },
  plugins: [
    new CopyPlugin({
      patterns: [
        { from: 'src/manifest.json', to: 'manifest.json' },
      ],
    }),
  ],
};

Why target: 'webworker' Matters

By default, Webpack assumes target: 'web'. In web mode, Webpack's internal runtime relies on window for global state and dynamic script injection. Specifying target: 'webworker' instructs Webpack to use self as the global object and removes DOM-reliant bootstrap code.

Managing Code Splitting

Background service workers can encounter issues with default code splitting. Service workers must establish their extension listeners immediately when executed. If code splitting creates asynchronous chunks that delay script execution, event listeners may miss initial browser events.

Setting optimization.splitChunks: false forces all background logic and dependencies into a single, synchronous background.js bundle.

If your extension requires dynamic imports or shared chunks across different entry points (like a popup or options page), you must declare the service worker as an ES module in your manifest.json:

{
  "manifest_version": 3,
  "name": "Extension Name",
  "version": "1.0.0",
  "background": {
    "service_worker": "background.js",
    "type": "module"
  }
}

When "type": "module" is configured, configure Webpack output to support ES modules:

output: {
  path: path.resolve(__dirname, 'dist'),
  filename: '[name].js',
  module: true,
  clean: true,
},
experiments: {
  outputModule: true,
}

TypeScript Integration (Optional)

If using TypeScript, ensure webworker DOM libraries are included in your tsconfig.json so that types like ServiceWorkerGlobalScope are resolved:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Node",
    "lib": ["ESNext", "WebWorker"],
    "strict": true
  }
}

Add ts-loader to your Webpack rules:

module: {
  rules: [
    {
      test: /\.tsx?$/,
      use: 'ts-loader',
      exclude: /node_modules/,
    },
  ],
},
resolve: {
  extensions: ['.ts', '.js'],
},

Verifying the Build

  1. Run the Webpack build command (npx webpack).
  2. Verify that dist/background.js contains no instances of window. in its Webpack boilerplate.
  3. Open chrome://extensions in Chromium-based browsers.
  4. Enable Developer mode and click Load unpacked.
  5. Select the dist directory and verify that the background service worker registers without errors.
