Webpack Default Export Interop: CommonJS and ESM

Webpack bridges the architectural gap between CommonJS (CJS) and ECMAScript Modules (ESM) using compile-time transformations and runtime compatibility helpers. When managing default exports across these module systems, Webpack inspects the module format and metadata flags—specifically __esModule—to determine whether an import targets a module's raw exports object or a designated default property. This mechanism ensures that code using modern import statements can interact reliably with legacy module.exports packages, and vice versa.

The Role of the __esModule Flag

Because CommonJS natively lacks the concept of a "default" export, tools like Babel and TypeScript introduced the __esModule boolean marker on the exports object to indicate that a CJS file was compiled from an original ES module source.

Object.defineProperty(exports, "__esModule", { value: true });
exports.default = function example() {};

Webpack evaluates this flag at runtime to dynamically route default import requests.

Importing CommonJS into ES Modules

When you use an ESM import to consume a CommonJS module:

import myLibrary from './legacy-module.cjs';

Webpack generates an internal helper (historically __webpack_require__.n) to resolve the import target. The helper executes the following logic:

  1. If __esModule is true: Webpack treats the module as transpiled ESM and assigns module.exports.default to myLibrary.
  2. If __esModule is false or absent: Webpack identifies the module as native CommonJS. It assigns the entire module.exports object directly to myLibrary.

This allows developers to import traditional CJS libraries—such as Lodash—using import _ from 'lodash' without needing to write import * as _ or accessing _.default.

Requiring ES Modules from CommonJS

When you use require() to pull in an ES module:

const myModule = require('./esm-module.js');

CommonJS has no standard mechanism to infer an unwrap operation for default exports. Consequently, Webpack returns the entire module namespace object. In this scenario:

  • myModule contains all named exports as keys.
  • The default export is accessible only through the .default property:
const value = myModule.default;

Webpack does not automatically unwrap the default export when using require(), maintaining consistency with Node.js module resolution semantics.

Webpack Runtime Helper Implementation

Under the hood, Webpack wraps imported dependencies inside a getter function to maintain live bindings and handle interop:

// Webpack's compatibility getter helper
__webpack_require__.n = function(module) {
  var getter = module && module.__esModule ?
    function() { return module['default']; } :
    function() { return module; };
  __webpack_require__.d(getter, { a: getter });
  return getter;
};

When an ESM file accesses the default import, Webpack executes this getter, returning module['default'] if the module was authored as ESM, or the root module object if it originated as CommonJS.

Webpack 5 Strict ESM Handling

In Webpack 5, interoperability rules depend on file extensions and the package.json "type" field:

  • Files ending in .mjs or within a package marked "type": "module" are treated as strict ECMAScript modules.
  • In strict mode, Webpack mirrors Node.js behavior: importing a CommonJS file via import defaultExport from './cjs' assigns the entire module.exports object to defaultExport, ignoring the __esModule flag unless configured otherwise via javascript/auto or specific module rules.
