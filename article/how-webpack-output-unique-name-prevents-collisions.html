How Webpack output.uniqueName Prevents Collisions

When running multiple Webpack bundles simultaneously on a single webpage—a common pattern in micro-frontend architectures and federated applications—different runtimes can clash over shared global variables. This article explains how Webpack's output.uniqueName option resolves this issue by isolating runtime instances, preventing chunk-loading conflicts, and ensuring that multiple independent bundles execute safely within the same global scope.

The Conflict: Shared Global Namespaces

By default, Webpack relies on global properties attached to the window object to manage asynchronous chunk loading, module caching, and runtime execution. In Webpack 5, the primary mechanism for chunk loading is an array attached to the global scope, typically named webpackChunk<name>.

If two or more separate Webpack builds are loaded onto the same window without distinct naming, they will both attempt to read and write to the same global property (such as window["webpackChunk"]). This collision creates severe runtime bugs:

  • Chunk Hijacking: One runtime might intercept and process a script chunk intended for another application, leading to missing dependencies or script evaluation errors.
  • Overwritten Globals: Global hooks, such as JSONP callbacks and module definition registries, can be overwritten by whichever runtime executes last.
  • Cache Poisoning: Identical module IDs or chunk IDs across different projects can accidentally resolve to the wrong build's internal modules.

How output.uniqueName Solves the Issue

The output.uniqueName configuration provides an isolated namespace for a specific Webpack compilation. Webpack uses this unique string to derive distinct names for all runtime-level global variables.

Instead of registering chunks to a generic global array, Webpack dynamically scopes the array name using the format:

window["webpackChunk_" + output.uniqueName]

When an asynchronous chunk is loaded via a <script> tag, the chunk pushes its modules and identifiers directly into this uniquely named array. Because the runtime only monitors its own namespaced array, each Webpack instance handles solely its own dependencies, completely eliminating cross-bundle interference.

Impact on Script Loading and Script Tags

In addition to namespacing the chunk array, Webpack uses output.uniqueName to identify and reuse its own script tags within the Document Object Model (DOM).

When loading chunks on demand, Webpack queries existing <script> elements in the DOM to avoid re-fetching scripts that have already been injected. It does this by checking a custom attribute: data-webpack. Webpack formats this attribute using the configured unique name:

<script src="bundle.chunk.js" data-webpack="my_unique_app:chunk-id"></script>

By querying for data-webpack^="my_unique_app:", the runtime ensures it never misidentifies a chunk injected by a different Webpack build, preventing false-positive loading states.

Role in Module Federation

In Webpack Module Federation, output.uniqueName is critical. Federated applications share dependencies and expose modules to one another dynamically at runtime. Webpack uses output.uniqueName to:

  • Create isolated containers on the global scope for exposed modules.
  • Ensure shared dependencies (such as React or Lodash) are tracked under the correct application scope before negotiation occurs.
  • Prevent remote entry scripts from overriding host or peer container entry points.

Configuring output.uniqueName

By default, Webpack 5 attempts to read the name field from the nearest package.json to populate output.uniqueName. However, relying on this fallback can lead to issues if multiple micro-frontends share identical package names or generic defaults.

The best practice is to explicitly define output.uniqueName in your webpack.config.js:

module.exports = {
  // ...
  output: {
    uniqueName: 'microAppBilling',
    // ...
  },
};

Explicitly setting this value guarantees a stable, conflict-free namespace across all deployment environments, allowing any number of Webpack runtimes to co-exist cleanly on the same window.
