Deterministic Module and Chunk IDs in Webpack

In Webpack, deterministic module and chunk IDs provide a reliable mechanism for long-term browser caching by generating predictable, short numeric identifiers based on module resource paths and chunk contents. This article explains how Webpack generates these deterministic IDs, the problems solved by shifting away from sequential integers, and how the underlying hashing algorithms balance collision avoidance with minimal bundle size overhead.

The Problem with Sequential IDs

By default in earlier versions of Webpack, modules and chunks were assigned incremental integer IDs (such as 0, 1, 2) based on the order of resolution. When a new module was introduced or an existing one removed, the entire resolution order shifted.

This behavior caused a cascading invalidation issue: even if a vendor chunk's code remained identical, its assigned chunk ID or the internal module IDs referenced inside it could change. Consequently, the output hash of the bundle changed, forcing clients to re-download unchanged assets and negating the benefits of long-term browser caching.

How Deterministic Module IDs Work

When optimization.moduleIds is set to 'deterministic' (the default setting in Webpack 5 for production mode), Webpack assigns short numeric IDs that remain constant across builds, provided the module itself has not changed.

  1. Path Normalization: Webpack takes the module's resolved file path and normalizes it relative to the project root (context). This ensures that builds generated across different machines or CI environments produce identical inputs for the hashing step.
  2. Hashing the Identifier: The relative path is passed through an internal hashing algorithm (typically based on a variant of MurmurHash3 or Xxhash).
  3. Truncation and Collision Handling: Webpack truncates the hash to a compact integer—usually 3 to 4 digits—to keep the generated runtime overhead minimal. If a collision occurs where two distinct modules generate the same shortened hash, Webpack increments the ID for one of the modules until a unique value is found.

Because the ID is derived from the module's stable path rather than compilation order, adding or removing other modules in the dependency graph does not alter the ID of untouched modules.

How Deterministic Chunk IDs Work

Similar to module IDs, chunk IDs can fluctuate if based on natural ordering. With optimization.chunkIds: 'deterministic' (also default in production), Webpack generates deterministic identifiers for chunks:

  1. Context Extraction: Webpack examines the chunk's constituent modules and its entry points or structural roles within the dependency graph.
  2. Hash Computation: A hash is derived using the identities of the modules contained in the chunk or the chunk's unique name/structure.
  3. Short Numerical ID Generation: The computed value is mapped to a small numeric ID. As with modules, this process includes collision-resolution logic to ensure that every emitted chunk retains a unique identifier without relying on arbitrary array indexes.

Configuration

In modern Webpack configurations, these settings are enabled out of the box when mode is set to 'production'. However, they can be explicitly defined in webpack.config.js:

module.exports = {
  mode: 'production',
  optimization: {
    moduleIds: 'deterministic',
    chunkIds: 'deterministic',
  },
};

Summary of Benefits

  • Cache Stability: Changes to one part of an application do not invalidate unrelated chunks, preserving vendor and split-chunk caching in client browsers.
  • Smaller Footprint than Named IDs: While named module and chunk IDs also provide determinism, they use full string paths that increase bundle size. Deterministic IDs yield tiny numbers (e.g., 314, 802), achieving optimal stability with negligible byte overhead.
  • Reproducible Builds: Builds executed on different environments or at different times produce identical asset outputs as long as the source files remain unchanged.
