Why Webpack ModuleConcatenationPlugin Fails

Webpack’s ModuleConcatenationPlugin—commonly referred to as scope hoisting—optimizes bundle size and execution time by flattening module scopes into single closures. However, this optimization can easily break, causing Webpack to bail out and revert to standard isolated module wrappers. This article breaks down the primary technical reasons Webpack fails to concatenate modules, covering module format mismatches, code-splitting boundaries, and configuration issues, along with instructions on how to identify specific bailout causes.

1. Pre-compilation to CommonJS by Babel

The most frequent cause of concatenation failure is transpiling ECMAScript Modules (ESM) to CommonJS before Webpack processes them. ModuleConcatenationPlugin strictly requires static ESM syntax (import and export) to analyze dependencies and flatten scopes.

If Babel (via @babel/preset-env) or TypeScript compiles your code into module.exports and require() calls, Webpack cannot statically determine the exports. To prevent this, ensure module transformation is disabled in your compiler configuration:

// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', { modules: false }]
  ]
};

2. Mixed CommonJS and ESM Dependencies

Scope hoisting can only concatenate modules if every participant in the scope is an ES module. If your module imports a dependency that exposes CommonJS (such as most Node.js packages distributed with require and module.exports), Webpack cannot inline the external module.

A module importing a CommonJS library can still be concatenated with other pure ESM modules that import it, but the CommonJS module itself will remain outside the hoisted scope, functioning as a boundary.

3. Modules Shared Across Split Chunks

When a module is imported across multiple asynchronous entry points or dynamically split chunks, Webpack must make a architectural choice. Inlining the shared module into every single chunk creates duplicate code and inflates bundle size.

Unless configured otherwise via SplitChunksPlugin, Webpack will bail out of concatenating that module into any single chunk so it can maintain it as an independent, shared dependency.

4. Asynchronous and Dynamic import() Calls

Static concatenation relies on knowing exactly when and where a module is executed. A dynamic import() statement defines an asynchronous chunk boundary. The module referenced by the dynamic import cannot be hoisted into the parent synchronous scope because it must be loaded on demand over the network.

5. Circular Dependencies

While ESM supports cyclic dependencies through live bindings, complex circular references can prevent Webpack from resolving a valid topological execution order. If the dependency graph forms a cycle where module declarations depend on each other prematurely, Webpack bails out of concatenation for the entire cycle to prevent runtime undefined variable reference errors.

6. Scope-Breaking Code Constructs

Certain JavaScript patterns prevent Webpack from safely flattening variables into a unified parent scope:

  • Use of eval(): eval creates a dynamic scope that Webpack cannot analyze statically. The presence of eval() automatically disables scope hoisting for that module.
  • Global Scope Leakage and Mutated Exports: Reassigning imported values or manipulating the module’s namespace object dynamically disrupts static analysis.

How to Diagnose Module Bailouts

To identify why a specific module failed to concatenate, enable optimization bailout reporting in your Webpack configuration:

// webpack.config.js
module.exports = {
  stats: {
    optimizationBailout: true
  }
};

When building, Webpack will print explicit explanations directly in the terminal for every module that failed to hoist, such as "Module is not an ECMAScript module" or "Cannot concat with [module]: Module is referenced from different chunks."
