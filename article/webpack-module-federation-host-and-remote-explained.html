Webpack Module Federation: Host and Remote Explained

Webpack Module Federation revolutionizes micro-frontend architectures by enabling multiple independent builds to share code dynamically at runtime. At the center of this mechanism are two primary roles: the host and the remote. This article explains the technical functions of host and remote containers, how they interact during execution, how they handle shared dependencies, and how an application can seamlessly operate as both.

The Remote Role: The Provider

A remote is an independent Webpack build that acts as a code provider. It exposes specific modules—such as UI components, utility functions, or entire sub-applications—so other builds can consume them over the network.

In the ModuleFederationPlugin configuration, a remote specifies:

  • name: A unique identifier used to create a global namespace at runtime.
  • filename: The entry manifest file (commonly remoteEntry.js) that defines the manifest of exposed modules and available shared dependencies.
  • exposes: An object mapping public paths to local files, declaring which modules are available for external use.

When a remote is built, it produces standard bundles alongside the remoteEntry.js file. The remote does not need to know which host will consume it; it simply serves its assets via a standard web server or CDN.

The Host Role: The Consumer

A host is an application build that acts as the entry point or shell for the user. Its primary responsibility is consuming modules provided by one or more remotes at runtime.

In the ModuleFederationPlugin configuration, a host specifies:

  • remotes: A key-value mapping that pairs an internal alias with the remote's identifier and entry URL (e.g., remoteApp: 'remoteApp@https://cdn.example.com/remoteEntry.js').

At runtime, the host dynamically loads the remote's remoteEntry.js manifest. Once fetched, the host can import remote components using standard dynamic import syntax (import('remoteApp/Button')) as if the code were located in its local node_modules.

The Runtime Interaction Lifecycle

The interaction between a host and a remote occurs in several distinct steps:

  1. Initialization: The host application starts and initiates the loading of the remote entry script defined in its configuration.
  2. Container Registration: The downloaded remoteEntry.js initializes a container interface on the global scope, making the remote's exposed module registry available.
  3. Scope Sharing: The host and remote negotiate dependencies through a global shared scope.
  4. Module Execution: When the host triggers a dynamic import for an exposed module, the remote container fetches the corresponding JavaScript chunk, executes it, and passes the resulting exports back to the host application.

Managing Shared Dependencies

Both hosts and remotes can define a shared configuration property. This allows them to avoid downloading duplicate libraries (such as React, Vue, or utility libraries) across micro-frontend boundaries.

During the runtime handshake, the host and remote compare the versions declared in their shared configurations:

  • If semantic versioning requirements match, only a single instance of the library is downloaded and shared across both containers.
  • Flags such as singleton: true ensure only one instance is ever loaded into memory, which is critical for libraries that rely on internal state or context providers.
  • The requiredVersion property prevents execution if a compatible version cannot be resolved.

Bidirectional Hosts: The Dual Role

The distinction between a host and a remote is not mutually exclusive. An application can simultaneously serve as both a host and a remote (known as a bidirectional host or omnidirectional host).

In this scenario, the build specifies both the remotes and exposes configurations within its ModuleFederationPlugin options. It can consume components from an upstream service while exposing its own components to downstream applications, enabling fully decentralized micro-frontend topologies.
