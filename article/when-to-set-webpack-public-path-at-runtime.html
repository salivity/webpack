When to Set webpack_public_path at Runtime

Webpack's __webpack_public_path__ is a free global variable that allows developers to dynamically configure the base path for loading dynamic assets and on-demand code chunks at runtime instead of compile time. While Webpack traditionally relies on the static output.publicPath setting in webpack.config.js, several modern architecture patterns and deployment pipelines require dynamic path resolution. This article outlines the primary scenarios where dynamically assigning __webpack_public_path__ is necessary and how it benefits application delivery.

Micro-Frontend Architectures

In a micro-frontend setup, multiple independently deployed applications share the browser window. A host application frequently loads remote child modules hosted on separate domains or paths.

If a micro-frontend utilizes code splitting, Webpack will attempt to fetch its dynamic chunks from the root domain of the host container by default. By dynamically assigning __webpack_public_path__ at the entry point of the remote module, the child application ensures that all its lazy-loaded chunks are fetched from its own origin rather than the host application's origin.

"Build Once, Deploy Anywhere" CI/CD Pipelines

Modern deployment workflows often use containerization (such as Docker) to promote an identical build artifact across multiple environments (development, staging, UAT, and production).

Setting output.publicPath at build time ties the bundle to a specific URL or CDN bucket, requiring a complete rebuild for every environment. By setting __webpack_public_path__ dynamically, the application can read the asset base path from a runtime environment variable, a global configuration object injected into window, or a server-rendered <meta> tag before loading any dynamic chunks.

Third-Party Widgets and Embedded Scripts

Applications distributed as embeddable third-party scripts (such as chat widgets, analytics trackers, or payment modals) are loaded directly into client websites over which the developer has no domain control.

When the embedded widget uses code splitting, it cannot rely on relative paths like /assets/, as the browser would resolve them against the host website's domain. Instead, the script can determine its own location at runtime—often via document.currentScript.src—and assign that base URL to __webpack_public_path__ so all supplementary chunks load from the provider's server.

Dynamic and Multi-Region CDNs

Global applications often direct users to regionally distributed Content Delivery Networks (CDNs) to reduce latency, or they implement automatic failover systems across multiple cloud storage providers.

In these architectures, the optimal CDN URL cannot be known during the build phase. At runtime, the server can supply the fastest, geographically closest CDN endpoint in the initial HTML payload, and the client script sets __webpack_public_path__ accordingly to route all subsequent chunk requests to that endpoint.

Multi-Tenant and White-Label Platforms

Enterprise SaaS platforms that serve multiple tenants from a single frontend codebase often serve distinct branding, localized assets, and static files from tenant-specific subdomains or dedicated asset buckets.

Setting __webpack_public_path__ at runtime allows the application to detect the current tenant—via subdomain or session data—and fetch dynamic assets from that tenant's designated storage bucket without requiring separate build artifacts for each customer.

Implementation Requirement

To ensure dynamic resolution works correctly, __webpack_public_path__ must be defined before any dynamic imports (import()) or split chunks are requested. It is typically set at the very top of the application's entry file or imported from a dedicated bootstrap file executed before the main bundle logic.
