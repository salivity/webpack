How Webpack Invalidates Persistent Cache Entries

Webpack 5 introduced persistent filesystem caching to dramatically improve build performance across independent compilation runs. To ensure that cached assets never lead to stale or corrupted output, Webpack utilizes a multi-layered cache invalidation strategy governed by a snapshot system. This strategy relies on filesystem timestamps, content hashes, dependency graph propagation, and specialized handling of external packages to accurately detect changes and invalidate cache entries.

The Snapshot System

At the core of Webpack's persistent cache invalidation is the snapshot mechanism. When Webpack builds an asset, it creates a snapshot recording the state of every dependency involved in the operation. These snapshots are categorized into different contexts:

  • Module Snapshots: Capture the state of source files and local project modules.
  • Resolve Snapshots: Capture the state of path resolutions, such as symlinks and module directories.
  • Build Dependency Snapshots: Capture dependencies critical to the build itself, such as configuration files and loaders.

Each snapshot records metadata—primarily modification timestamps (mtime) and cryptographic content hashes—for the referenced files and directories.

Timestamp and Hash Comparison

When a new compilation begins, Webpack queries the filesystem to compare the current state of files against their stored snapshots. To maintain high performance, Webpack first evaluates modification timestamps:

  1. Timestamp Check: If the file's mtime matches the snapshot, Webpack assumes the file has not changed and retains the cached module.
  2. Content Hash Check: If the timestamp has changed, Webpack reads the file and computes its content hash. If the hash matches the snapshot's recorded hash (for example, if a file was saved without changing its content), the cache remains valid, preventing unnecessary rebuilds. If the hash differs, the entry is invalidated.

Graph Propagation and Module Re-evaluation

Webpack's compilation model is built on an interconnected module graph. When a specific module's cache entry is invalidated due to a file change, Webpack does not discard the entire project cache. Instead, it invalidates only the changed module and traces its connections.

The compiler re-executes the loaders and parsers for the modified module, detects any changes to exported or imported identifiers, and determines whether dependent modules or chunk assets need to be updated. If the module's interface remains compatible, the cache invalidation remains localized; if imports or exports change, dependent chunks and modules are marked dirty and recompiled.

Managed Paths for External Dependencies

Hashing every file inside node_modules during each build would degrade performance. Webpack addresses this using managedPaths and immutablePaths.

By default, Webpack treats paths containing node_modules as managed by package managers (such as npm, Yarn, or pnpm). Instead of monitoring individual files within installed packages, Webpack tracks package metadata—primarily package.json versions and lockfiles. Webpack assumes that package contents remain static unless the package version changes or a package is added or removed. When a change in package.json or a lockfile is detected, the cache entries corresponding to the affected packages are invalidated.

Build Dependencies and Global Cache Invalidation

Dependency changes can occur outside the source code itself, such as updates to build tools, plugins, or configurations. Webpack handles this through cache.buildDependencies:

module.exports = {
  cache: {
    type: 'filesystem',
    buildDependencies: {
      config: [__filename],
    },
  },
};

When files listed in buildDependencies (such as webpack.config.js or custom build scripts) are modified, Webpack treats the entire cache configuration as altered and invalidates the entire cache store. Additionally, developers can supply a cache.version string, which acts as a manual invalidation trigger to purge all persistent cache entries across the project.
