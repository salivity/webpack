How Webpack Handles Shared Assets Across Entries

Webpack manages shared assets across multiple entry points through a multi-phase compilation process that moves from a detailed module dependency graph to an optimized chunk graph. When multiple entry points share assets or vendor libraries, Webpack maps individual module dependencies, isolates common nodes, and restructures the chunk hierarchy using internal optimization heuristics such as the SplitChunksPlugin. This process prevents code duplication, manages execution order, and ensures browser-efficient asset delivery.

1. Construction of the Module Graph

Before chunks exist, Webpack builds a ModuleGraph. Starting from the files defined in the entry configuration, the compiler traverses the source code and parses statements such as import, require(), and dynamic import() calls.

Each discovered file is transformed into a NormalModule instance. The connections between these modules are stored as dependency relationships in the ModuleGraph. At this phase, if two distinct entry points (such as app.js and admin.js) both require lodash, the module graph retains a single NormalModule instance representing lodash, connected to both entry trees.

2. Initial Chunk Graph Generation

Once the module graph is complete, Webpack creates the ChunkGraph.

  1. Entry Chunk Allocation: For every defined entry point, Webpack instantiates an Entrypoint object and creates an initial chunk.
  2. Module Assignment: Webpack recursively walks the module graph from each entry point and assigns every reachable module directly to that entry point's chunk.
  3. Dynamic Import Splitting: Whenever Webpack encounters an asynchronous boundary (import()), it creates an asynchronous child chunk rather than inlining the module into the entry chunk.

At this stage of compilation, shared static dependencies are actually duplicated across entry chunks. If both app.js and admin.js rely on lodash, lodash initially resides inside both entry chunks within the ChunkGraph.

3. Optimization and SplitChunksPlugin

To eliminate duplication and establish efficient relationships between shared assets, Webpack invokes optimization plugins, most notably the built-in SplitChunksPlugin.

The plugin inspects the ChunkGraph and identifies modules that appear in multiple chunks. It evaluates whether these modules should be extracted into a separate, shared chunk based on specific constraints:

  • Chunk Count (minChunks): The minimum number of chunks that must share a module before it is extracted (defaults to 1 for dynamic chunks, 2 for initial chunks in common configurations).
  • Size Thresholds (minSize, maxSize): Whether extracting the shared module produces a chunk large enough to justify an additional HTTP request.
  • Cache Groups: Rules that determine how modules are grouped together (e.g., grouping all node_modules into a shared vendors chunk).

4. Establishing Chunk Graph Relationships

When a module meets the extraction criteria, Webpack modifies the ChunkGraph:

  1. New Chunk Creation: A new common chunk is created (for example, vendors~app~admin.js).
  2. Module Reassignment: The shared module is disconnected from the original entry chunks and reassigned to the new chunk.
  3. Graph Edge Rewiring: Webpack updates the chunk relationships. The new common chunk is registered as a shared dependency of the entry chunks.
  4. Runtime Manifest Update: Webpack generates dependency metadata within its runtime. This metadata instructs the browser or the HTML generation plugin (like HtmlWebpackPlugin) to load the shared chunk before executing either of the entry chunks, ensuring all dependencies are in scope before execution begins.
