Webpack Loader Pitch Phase Explained

This article provides a concise overview of the pitch phase in Webpack loaders, explaining how its execution order differs from the standard loader phase, how its short-circuiting mechanism operates, and the primary scenarios where developers leverage it to optimize or alter asset transformation pipelines.

How the Pitch Phase Works

Webpack processes loader chains in two distinct phases: the pitch phase and the normal phase.

By default, Webpack executes loaders in reverse order (right-to-left or bottom-to-top) during the normal phase. However, before the normal execution begins, Webpack runs from left-to-right (top-to-bottom) during the pitch phase.

Each loader can optionally export a pitch method alongside its standard export:

module.exports = function (content) {
  // Normal phase
  return content;
};

module.exports.pitch = function (remainingRequest, precedingRequest, data) {
  // Pitch phase
};

The pitch function receives three parameters:

  • remainingRequest: The request string representing all loaders that will be executed after this one, including the resource file itself.
  • precedingRequest: The request string representing all loaders that have already executed their pitch method.
  • data: An empty object shared between the pitch method and the normal phase of the same loader, allowing metadata to be passed across phases.

The Short-Circuiting Mechanism

The most critical feature of the pitch phase is its ability to short-circuit the execution chain. If a loader's pitch method returns a defined value (anything other than undefined), Webpack immediately halts the pitch phase. It skips the remaining loaders in the chain, ignores the resource file itself, and turns around to execute the normal phase of the preceding loader.

For example, given a loader configuration of [loaderA, loaderB, loaderC]:

  1. loaderA.pitch executes.
  2. loaderB.pitch executes and returns a string of code.
  3. loaderC.pitch, the source file reading, and loaderB's normal phase are completely skipped.
  4. Execution jumps directly to loaderA's normal phase, receiving the output from loaderB.pitch.

When to Utilize the Pitch Phase

Developers and loader authors utilize the pitch phase in several specific scenarios:

1. Code Generation and Interception (e.g., style-loader)

The most common use case is when a loader needs to bypass the typical source transformation and instead generate JavaScript that imports other loaders dynamically. For instance, style-loader uses its pitch method to generate a runtime script that imports the CSS output from css-loader and injects it into the DOM via a <style> tag, rather than directly transforming raw CSS text.

2. Caching

Loaders that implement caching mechanisms, such as older implementations like cache-loader, utilize the pitch phase to check if a compiled result exists on disk or in memory. If a valid cache exists, the pitch method returns the cached module code immediately, preventing subsequent resource-intensive loaders (like Babel or TypeScript compilers) from executing.

3. Metadata Sharing

The data argument passed to the pitch method can be mutated to persist state into the normal phase. This is useful when expensive calculations or file inspections must be performed early, allowing the results to be consumed later without repeating work.

4. Bypassing Underlying Loaders Conditionally

The pitch phase allows you to inspect the incoming resource path (remainingRequest) and decide whether the file even requires processing. If a condition is met, returning the processed output immediately saves compilation time by preventing the rest of the loader stack from running.
