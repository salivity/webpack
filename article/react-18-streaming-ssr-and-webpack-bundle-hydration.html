React 18 Streaming SSR and Webpack Bundle Hydration

React 18 transforms server-side rendering (SSR) by replacing monolithic page rendering with streaming architecture powered by modern Suspense boundaries. Instead of waiting for the entire page's data and HTML to generate before sending it over the network—and subsequently blocking client interactivity until the entire JavaScript bundle downloads and parses—React 18 enables progressive HTML streaming and selective hydration. When paired with Webpack, this architecture coordinates chunk loading, asset emission, and runtime execution so that individual components become interactive as soon as their respective code chunks and HTML fragments arrive.

The Shift from Monolithic to Streaming SSR

In previous versions of React, SSR operated through renderToString. This approach suffered from four sequential bottlenecks:

  1. The server had to fetch all required data before rendering any HTML.
  2. The server had to render the entire component tree to an HTML string before sending it to the client.
  3. The client had to download JavaScript bundles for the entire application before initiating hydration.
  4. React had to hydrate the complete DOM tree in a single pass before any part of the UI became interactive.

React 18 resolves this with the renderToPipeableStream (for Node.js) and renderToReadableStream (for Web Streams) APIs. The server immediately sends an initial HTML "shell" containing fallbacks for components wrapped in <Suspense>. As asynchronous data resolves on the server, React renders the remaining components and streams them down the same HTTP connection alongside minimal inline <script> tags that replace the fallback markup with actual content directly in the DOM.

Webpack Code Splitting and Chunk Mapping

For streaming SSR to work with Webpack, the client-side build must be split into asynchronous chunks via dynamic imports (import()). Webpack creates isolated bundle files for these lazy-loaded modules and manages their retrieval using its internal runtime mechanics (such as __webpack_require__.e).

In a standard client-rendered application, Webpack requests chunks dynamically on demand. In streaming SSR, however, the server must determine which Webpack chunks correspond to the components being streamed. Tools and frameworks typically solve this using a Webpack compilation manifest:

  1. Manifest Generation: During the build step, a Webpack plugin (such as the manifest plugin or module federation hooks) records module IDs and maps them to their respective output chunks (chunk.js, vendor.js).
  2. Server-Side Module Tracking: While rendering the component tree on the server, the streaming renderer tracks which code-split components are encountered within each <Suspense> boundary.
  3. Asset Tag Injection: As each <Suspense> boundary finishes rendering on the server, the server injects <script> tags for that boundary’s corresponding Webpack chunk into the streaming response before emitting the component's HTML.

This prevents the "waterfall" effect: the client receives the markup and begins downloading the required Webpack chunk nearly simultaneously.

Selective Hydration

Once the HTML and corresponding Webpack bundles arrive in the browser, React 18 utilizes Selective Hydration via hydrateRoot. Hydration is no longer an all-or-nothing operation.

Because code is split using React.lazy, React waits to hydrate a given boundary until its associated Webpack bundle has been downloaded and executed. If Webpack is still downloading the chunk for Component B, React does not block Component A from hydrating. As soon as Component A's JavaScript is evaluated by Webpack's runtime, React hydrates Component A and attaches event listeners, making it fully interactive.

Interaction Prioritization

A critical touchpoint between React 18 and Webpack's runtime is interaction-driven hydration order. If multiple components are awaiting hydration while their Webpack chunks load in the background, React monitors user events (such as clicks, taps, or focus changes).

If a user clicks inside an unhydrated <Suspense> boundary:

  1. React intercepts and records the interaction event.
  2. React bumps the priority of that specific boundary above others.
  3. Webpack executes the corresponding module code as a priority.
  4. React synchronously hydrates that subtree and replays the user's recorded event against the newly interactive component.

Webpack Runtime Integration Requirements

To facilitate this architecture in custom SSR setups without an opinionated framework, the Webpack runtime must be present in the initial HTML shell. By ensuring the Webpack runtime and critical manifest data are loaded up front, any dynamically streamed <script> tag emitted later in the stream can immediately register its exported modules into window.webpackChunk without race conditions or undefined references. React can then successfully match the streamed DOM nodes to the client-side component definitions.
