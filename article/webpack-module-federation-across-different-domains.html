Webpack Module Federation Across Different Domains

Webpack Module Federation enables independently built and deployed JavaScript applications to dynamically share code and run as a single composite application. When micro-frontends reside on different domain hosts with isolated deployment cycles, Webpack bridges the gap using runtime manifest resolution, asynchronous chunk loading, cross-origin communication, and runtime dependency negotiation. This article examines the architectural mechanics that make cross-domain module federation work seamlessly without synchronized deployments.

Dynamic Remote Resolution via remoteEntry.js

At the center of cross-domain federation is the remoteEntry.js manifest file. Each federated application (the "remote") generates this manifest upon compilation. Rather than bundling remote code into the host application at build time, the host fetches the remote's remoteEntry.js file over HTTP at runtime.

When micro-frontends are hosted on distinct domains, hardcoding remote URLs at build time is often impractical. Webpack supports dynamic remotes, allowing the host application to determine the remote domain programmatically at runtime using utility functions or dynamic import() statements.

const loadComponent = (scope, module, url) => {
  return async () => {
    await __webpack_init_sharing__('default');
    await new Promise((resolve, reject) => {
      const script = document.createElement('script');
      script.src = url;
      script.onload = resolve;
      script.onerror = reject;
      document.head.appendChild(script);
    });
    const container = window[scope];
    await container.init(__webpack_share_scopes__.default);
    const factory = await container.get(module);
    return factory();
  };
};

This dynamic initialization ensures that the host container can resolve the remote entry points based on environment variables, API lookups, or user roles across multiple distinct domains.

Managing Distinct Deployment Cycles and Caching

Because each domain host operates on its own deployment schedule, the host and remotes must decouple their asset versioning strategies:

  1. Non-Cached Manifests: The entry point file (remoteEntry.js) should be served with Cache-Control: no-cache, no-store, must-revalidate. This ensures the host always receives the latest map of chunks immediately after a remote deploys.
  2. Immutable Chunks: The actual code chunks referenced by remoteEntry.js should feature unique content hashes in their filenames and be served with aggressive, long-term caching headers (Cache-Control: immutable, max-age=31536000).
  3. Public Path Configuration: The remote's output.publicPath must be set explicitly to its fully qualified domain name (or publicPath: 'auto') rather than a relative path. This ensures that when the host initiates requests for secondary chunks, the browser requests them from the remote's domain host instead of the host's domain.

Cross-Origin Resource Sharing (CORS)

Since assets are loaded across distinct domain boundaries (e.g., the host at app.example.com fetching chunks from cdn.microfrontends.com), the remote server or CDN must be configured with proper CORS headers.

The remote host must return:

Access-Control-Allow-Origin: https://app.example.com

Or a wildcard * for public assets. Without this header, browser security policies will block the execution of Webpack's dynamically injected scripts and JSONP chunk loading calls.

Runtime Dependency Negotiation

With independent deployment schedules, different remotes may declare different versions of shared libraries, such as React or Lodash. Webpack Module Federation resolves this using its shared configuration:

  • Semantic Versioning Negotiation: When a remote is loaded, Webpack compares the version requirements in the remote's manifest against the versions already initialized in the host's runtime sharing scope.
  • Singleton Enforcement: For libraries that require a single instance in memory (like React's context), the configuration sets singleton: true. If a remote requires a version that violates the host's version constraint, Webpack warns in the console and falls back to loading a separate instance unless strictVersion: true is enforced.

Resiliency and Failure Handling

Independent deployment cycles create the risk of a remote domain becoming unreachable due to network latency, server downtime, or deployment rollbacks.

To prevent a failed remote from breaking the entire host application, federated imports should be wrapped in boundary layers. This includes combining dynamic React.lazy() with native JavaScript try/catch handlers or React ErrorBoundary components. If a remote domain fails to respond, the host can catch the loading error gracefully and render a fallback user interface without interrupting the rest of the application.
