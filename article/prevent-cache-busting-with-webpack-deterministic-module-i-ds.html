Prevent Cache Busting with Webpack Deterministic Module IDs

Long-term asset caching relies on predictable file names, but Webpack's default module assignment can inadvertently change chunk hashes even when the underlying code has not changed. This article explains how Webpack assigns module identifiers, why natural or sequential numbering causes unnecessary cache invalidation across vendor chunks, and how configuring optimization.moduleIds = 'deterministic' solves this problem by generating consistent, short numeric hashes based on module file paths.

The Problem: Order-Dependent Module IDs

In Webpack, every file in your dependency graph is treated as a module and assigned an internal module identifier (moduleId). Historically, Webpack assigned these IDs using incremental counters (such as 0, 1, 2, and so on) based on the order in which modules were resolved.

When you add, delete, or rename an import anywhere in your source code, the resolution order of the entire dependency graph shifts. As a result:

  1. A newly inserted module takes an existing ID, shifting the numeric IDs of subsequent modules.
  2. Even if a vendor bundle (like a third-party library chunk) contains no actual source changes, the internal ID references compiled into that bundle change.
  3. Because the compiled output changes, Webpack generates a completely new [contenthash] for that chunk file.
  4. Clients are forced to re-download the entire vendor bundle, defeating browser-side long-term caching.

How optimization.moduleIds = 'deterministic' Works

Setting optimization.moduleIds = 'deterministic' tells Webpack to generate module IDs using a deterministic hashing algorithm rather than sequential numbering or build-order indexes.

Instead of assigning IDs based on when a file is discovered during the compilation pass, Webpack creates a short numeric hash derived from the module's resolved file path.

This approach ensures:

  • Isolated Changes: If you add a new module feature.js, only feature.js receives a new ID. Unchanged modules retain the exact same IDs they had in previous builds because their file paths did not change.
  • Stable Content Hashes: Because module IDs inside vendor chunks remain identical across builds, the compiled JavaScript output of those chunks does not change. Consequently, the [contenthash] remains identical, allowing browsers to safely serve the cached asset.
  • Minimal Bundle Size Overhead: While optimization.moduleIds = 'named' also avoids order-dependent shifts by using file path strings (e.g., ./node_modules/lodash/lodash.js), it significantly increases bundle sizes. The deterministic setting condenses these paths into short numeric values (typically 3 to 4 digits), offering cache stability without bloating the bundle.

Webpack Configuration

In Webpack 5, deterministic is the default behavior when mode is set to 'production'. However, if you are explicitly customizing optimization rules, you can define it directly in your webpack.config.js:

module.exports = {
  mode: 'production',
  optimization: {
    moduleIds: 'deterministic',
    chunkIds: 'deterministic',
  },
};

Pairing moduleIds: 'deterministic' with chunkIds: 'deterministic' guarantees that both internal modules and the resulting chunk bundles maintain persistent identifiers across independent production builds, preserving long-term browser cache validity.
