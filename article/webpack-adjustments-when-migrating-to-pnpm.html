Webpack Adjustments When Migrating to pnpm

Migrating a project from npm or Yarn to pnpm provides significant performance gains and disk space savings, but pnpm’s strict, symlinked dependency structure often causes build failures in existing Webpack setups. Unlike npm and Yarn v1, which hoist dependencies into a flat node_modules directory, pnpm relies on symbolic links and isolated virtual stores. This guide outlines the specific adjustments required in your Webpack configuration and environment to ensure seamless builds after migrating.

1. Configure Symlink Resolution (resolve.symlinks)

By default, Webpack resolves symlinks to their real disk location (resolve.symlinks: true). Because pnpm structures packages inside a hidden .pnpm virtual store and symlinks them to the project root, Webpack might resolve a package to its physical location rather than its symlink.

This can cause issues with singleton packages (such as React) or loader rules targeting node_modules.

Depending on your architecture, you may need to explicitly configure this setting:

// webpack.config.js
module.exports = {
  resolve: {
    // Keep true (default) if peer dependencies depend on the real location.
    // Set to false if you are working in a monorepo and packages must resolve
    // dependencies from the context of the importing package.
    symlinks: true,
  },
};

If you experience issues in monorepos where shared packages cannot find dependencies installed in an app's root, set symlinks: false.

2. Update Loader Resolution (resolveLoader)

In npm and Yarn, Webpack loaders (like babel-loader, ts-loader, or css-loader) installed by presets or third-party configurations are often accessible globally due to hoisting. Under pnpm, if a loader is not listed as a direct dependency in the root package.json, Webpack may fail to locate it.

To fix loader lookup failures, tell Webpack where to look for loaders:

// webpack.config.js
module.exports = {
  resolveLoader: {
    modules: ['node_modules'],
  },
};

Additionally, ensure all loaders used inside your module.rules are explicitly defined in your package.json under devDependencies.

3. Adjust Loader include and exclude Conditions

Many Webpack configurations exclude processing dependencies using regular expressions such as exclude: /node_modules/. Because pnpm resolves symlinks to their canonical paths inside .pnpm, paths might not match simple absolute string matches or custom regexes.

When transpiling specific packages (e.g., untranspiled ES modules in node_modules), avoid using strict directory structures:

// Before (Fragile with pnpm)
exclude: path.resolve(__dirname, 'node_modules')

// After (Robust with pnpm)
exclude: /node_modules\/(?!(@my-org\/my-package)\/)/

If you use resolve.symlinks: true, ensure that any custom include rules for local packages or monorepo workspaces match the real path of the source files, not the symlink path.

4. Prevent Singleton Conflicts Using Aliases

Because pnpm isolates dependencies, different packages might resolve separate instances of libraries that must operate as singletons (such as react, react-dom, or graphql). This commonly results in runtime errors like "Invalid Hook Call".

Use Webpack's resolve.alias to force all packages to resolve the exact same instance:

const path = require('path');

module.exports = {
  resolve: {
    alias: {
      react: path.resolve(__dirname, 'node_modules/react'),
      'react-dom': path.resolve(__dirname, 'node_modules/react-dom'),
    },
  },
};

5. Resolve Undeclared "Phantom" Dependencies

A common failure after switching to pnpm is Module not found errors for dependencies that were never explicitly declared in package.json. Flat package managers tolerate this because transitive dependencies are placed directly in the root node_modules.

To fix this properly:

  1. Identify the missing package from the Webpack error output.
  2. Add it directly to your package.json using pnpm add <package-name>.

If you have a massive legacy codebase where identifying every phantom dependency immediately is impractical, you can temporarily configure pnpm to mimic flat hoisting via an .npmrc file:

# .npmrc
node-linker=hoisted

Note: While node-linker=hoisted resolves errors without Webpack modifications, it eliminates pnpm's isolation benefits and should only be used as a transitional measure.
