Webpack splitChunks: chunks 'all' vs 'async'

In Webpack, the optimization.splitChunks.chunks configuration dictates which types of chunks are evaluated for code splitting and vendor deduplication. Choosing between the default value 'async' and the broader value 'all' fundamentally alters how Webpack handles shared modules across your application. This guide explains how both options function, examines how they treat synchronous versus dynamic imports, and outlines which setting to select based on your performance and architecture requirements.

Understanding the splitChunks.chunks Option

Webpack's SplitChunksPlugin extracts shared dependencies into separate files to avoid duplicate code across entry points and asynchronous bundles. The chunks property informs Webpack which bundles are eligible for this optimization. It primarily accepts three string values: 'async', 'initial', and 'all' (or a custom filter function).

The Default Behavior: chunks: 'async'

When chunks is set to 'async', Webpack only optimizes modules imported using dynamic import() statements.

  • How it works: If you load a module on-demand (e.g., import('lodash')), Webpack evaluates it for chunk splitting. If multiple asynchronous components import the same library, that library is separated into a shared chunk.
  • Limitations: Statically imported modules (e.g., import _ from 'lodash' at the top of an entry point file) are completely ignored. If multiple entry points or synchronous files import the same package, that package is duplicated in each resulting initial bundle.
  • Best used for: Applications where simplicity is preferred and minimizing the total number of initial HTTP script requests takes precedence over aggressive vendor deduplication.

The Comprehensive Approach: chunks: 'all'

Setting chunks to 'all' indicates that Webpack should evaluate every module for splitting, whether it is loaded synchronously or asynchronously.

  • How it works: Webpack checks for duplicate dependencies across both static entry points and dynamic imports. If a module like react or lodash is shared among different entry points, or shared between an entry point and a dynamic import, Webpack extracts it into a dedicated vendor chunk.
  • Benefits: This provides maximum deduplication and optimal long-term browser caching. When a common vendor library is extracted into its own bundle, users do not need to re-download it when application logic changes.
  • Best used for: Multi-page applications (MPAs), single-page applications with multiple entry points, or performance-critical apps where minimizing payload size and maximizing cache hits are critical.

Key Differences at a Glance

Feature chunks: 'async' (Default) chunks: 'all'
Eligibility Only dynamically imported (import()) modules Both static (import x from 'y') and dynamic imports
Initial Bundle Size Often larger due to duplicated static dependencies Smaller, as shared code is split out
HTTP Requests on Load Fewer initial script requests May increase initial script requests unless tuned
Caching Efficiency Lower for common static vendor packages Higher, vendor code can be cached independently

Practical Configuration and Recommendation

In most modern web applications, using 'all' is the recommended practice because it prevents shared libraries from bloating your main bundle. However, using 'all' may generate additional initial script tags. To manage this, combine 'all' with Webpack's constraint controls:

module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      minSize: 20000,
      maxInitialRequests: 30,
      automaticNameDelimiter: '~',
      cacheGroups: {
        defaultVendors: {
          test: /[\\/]node_modules[\\/]/,
          priority: -10,
          reuseExistingChunk: true,
        },
        default: {
          minChunks: 2,
          priority: -20,
          reuseExistingChunk: true,
        },
      },
    },
  },
};

Using chunks: 'all' with these parameters guarantees that code is only extracted if it meets minimum size thresholds, striking the right balance between avoiding duplicate code and preventing excessive network requests.
