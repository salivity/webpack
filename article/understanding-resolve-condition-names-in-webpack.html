Understanding resolve.conditionNames in Webpack

In Webpack 5, the resolve.conditionNames configuration option dictates how module resolution interacts with conditional exports defined in package dependencies. Modern npm packages use the exports field in their package.json to offer different versions of their code depending on the consuming environment, such as Node.js, browsers, or specific module formats. Configuring resolve.conditionNames allows developers to explicitly prioritize or add custom condition keys, ensuring that Webpack loads the exact module variant required by the application.

The Role of the exports Field

Historically, libraries relied on fields like main, module, and browser to specify entry points. Node.js introduced the exports field to standardize conditional imports. A package author can define multiple export paths based on conditions:

{
  "name": "example-library",
  "exports": {
    "import": "./dist/index.mjs",
    "require": "./dist/index.cjs",
    "browser": "./dist/index.browser.js",
    "development": "./dist/index.dev.js",
    "default": "./dist/index.js"
  }
}

When Webpack resolves import 'example-library', it checks these conditions from top to bottom against its internal condition list to select the first matching file.

How resolve.conditionNames Works

The resolve.conditionNames property defines the priority list of conditions Webpack uses when evaluating the exports field of imported packages.

By default, Webpack populates condition names based on the build target:

  • For target: 'web', Webpack defaults to conditions like ['browser', 'import', 'require', 'webpack', 'development'/'production'].
  • For target: 'node', it defaults to conditions like ['node', 'import', 'require', 'webpack', 'development'/'production'].

When you specify resolve.conditionNames in webpack.config.js, you override or augment the default resolution order.

// webpack.config.js
module.exports = {
  // ...
  resolve: {
    conditionNames: ['custom-env', 'import', 'require']
  }
};

In this configuration, Webpack first looks for a custom-env condition. If the target package provides that condition, Webpack uses its path; otherwise, it falls back to import, then require.

Common Use Cases

  1. Selecting Specific Code Variants: Libraries sometimes provide uncompiled or modern ESM variants under custom tags (like source or es2020). Adding these tags to conditionNames ensures Webpack bundles modern code instead of legacy, transpiled builds.
  2. Environment-Specific Builds: If you are building for edge runtimes, web workers, or micro-frontends, you can inject conditions such as worker or edge-light to match packages optimized for those environments.
  3. Overriding Defaults: If a dependency provides both browser and node targets, but a specific Webpack pipeline requires the Node implementation despite compiling for the browser, conditionNames can be configured to omit browser and prioritize node.

Ultimately, resolve.conditionNames provides granular control over package resolution, bridging the gap between modern package packaging standards and customized build requirements.
