Webpack Module Maps in React Server Components

React Server Components (RSC) introduce a dual-environment architecture where components render on either the server or the client, requiring a bridge to connect the two execution contexts. Webpack handles this boundary by generating and consuming a module map—a serialized manifest that maps abstract client references emitted by the server compiler to the actual compiled browser-side chunks. This article explains how Webpack identifies client boundaries, generates module maps during the build phase, and leverages them at runtime to resolve and hydrate client components.

Identifying the Component Boundaries

Webpack identifies client components through the "use client" directive placed at the top of a file. When compiling for the server, Webpack uses specialized plugins and loaders—primarily provided by react-server-dom-webpack—to intercept these directives.

Instead of bundling the client component's full implementation into the server bundle, Webpack treats the module as a proxy. The loader strips the component logic from the server runtime and replaces it with a lightweight "client reference" object. This reference contains metadata about the module, including a unique module identifier, the export name, and instructions on how to locate the real code on the client.

The Dual-Compilation Process

Webpack relies on two concurrent or sequential compilation passes to construct the RSC environment:

  1. The Client Build: Webpack compiles all browser-facing assets as it normally would. It traces the application's entry points along with all files marked with "use client", assigns chunk IDs, applies code-splitting rules, and outputs physical JavaScript bundles.
  2. The Server Build: Webpack compiles the server logic (the React Server Components). During this pass, client modules are not compiled into server code; instead, the compiler registers their export identities.

The react-server-dom-webpack/plugin hooks into Webpack’s compilation lifecycle (specifically the emit or processAssets tapable hooks). It extracts the output chunk data from the client compilation and aligns it with the module identifiers generated during the server compilation.

Structure of the Module Map

The module map is serialized as a JSON manifest (often referred to as the client manifest or SSR manifest). It acts as a dictionary linking server-side client references to browser-side bundles.

A typical entry in a Webpack RSC module map contains:

  • ID: The canonical identifier of the module (typically a file path or Webpack module ID).
  • Chunks: An array of chunk IDs or filenames that must be downloaded by the browser before this module can be executed.
  • Name: The specific export name (such as default or a named export like Counter).
  • Async/Sync Flags: Metadata indicating whether the chunk should be loaded asynchronously or synchronously.

Server-Side Serialization

When a server component renders a client component, React does not output HTML for that component. Instead, it emits a serialized payload using the RSC flight protocol.

React queries the Webpack runtime for the client reference associated with that module. React then serializes this boundary into the RSC stream as a special reference token containing the module ID and export name. Because the server knows the abstract reference, it can stream the UI tree without evaluating client-side dependencies (such as React hooks, DOM operations, or browser APIs).

Client-Side Resolution and Hydration

When the browser receives the RSC stream, it must convert the serialized reference tokens back into interactive components. This process unfolds in three steps:

  1. Decoding the Stream: The client-side flight response parser (react-server-dom-webpack/client) encounters the client reference marker in the stream.
  2. Consulting the Module Map: The parser checks the module map injected into the client environment (usually provided as an inline global script or fetched alongside the initial HTML). The module map informs the runtime which specific Webpack chunks contain the required component code.
  3. Chunk Loading and Execution: The runtime triggers Webpack's internal module loader—typically via __webpack_require__.e (chunk loading) followed by __webpack_require__ (module execution). Once the chunk is loaded and executed, the actual React component is passed into the React tree to complete hydration and render the interactive UI.
