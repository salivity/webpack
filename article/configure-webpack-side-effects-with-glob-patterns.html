Configure Webpack sideEffects with Glob Patterns

Configuring the sideEffects flag with an array of glob patterns allows developers to optimize bundle sizes via tree-shaking while protecting specific files from unintended removal. While setting sideEffects: false instructs Webpack that entire modules contain no runtime side effects, critical assets like stylesheets, global polyfills, and initialization scripts require explicit retention. This guide demonstrates how to define precise glob patterns in your configuration to safeguard essential files during the production build process.

Why Use Glob Patterns for sideEffects

Webpack uses the sideEffects property—typically defined in package.json—to prune unused exports. If a module is imported but none of its exports are used, Webpack skips evaluating it entirely if sideEffects is false.

However, certain imports modify global state or inject styles into the DOM without exporting values (e.g., import './styles.css' or import './polyfill'). Declaring an array of glob patterns creates an allowlist, signaling to Webpack which files must always execute when imported, regardless of whether direct exports are referenced.

Configuring package.json with Glob Patterns

The primary location for defining side effects is inside the project or library's package.json file. Webpack uses micromatch under the hood to evaluate these patterns.

Here is a standard implementation:

{
  "name": "my-app",
  "version": "1.0.0",
  "sideEffects": [
    "**/*.css",
    "**/*.scss",
    "./src/polyfills/**/*.js",
    "./src/initialize-analytics.js"
  ]
}

Pattern Matching Rules

When constructing patterns in package.json, keep the following conventions in mind:

  • File Extensions: Using "**/*.css" or "**/*.less" ensures that style sheets injected via css-loader or style-loader are never stripped out by tree-shaking.
  • Wildcards: The ** pattern matches directories recursively, whereas * matches files within a single directory level.
  • Relative Paths: Explicit paths to specific scripts should start with ./ relative to the directory containing package.json (e.g., "./src/registerServiceWorker.js").
  • Direct Subdirectories: A pattern like "./src/components/**/*.css" restricts side-effect evaluation to CSS files inside that specific folder tree.

Configuring sideEffects in webpack.config.js

You can also override or enforce side-effect behavior directly within the webpack.config.js file using module.rules. This is useful when consuming third-party packages that fail to specify sideEffects in their own package.json.

module.exports = {
  mode: 'production',
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader'],
        sideEffects: true
      },
      {
        test: /src\/polyfills\/.+\.js$/,
        sideEffects: true
      }
    ]
  }
};

Setting sideEffects: true on a specific rule tells Webpack to always retain modules matching that test condition.

Best Practices

  • Be Specific: Avoid overly broad patterns like "**/*" or "./src/**", as this defeats the purpose of tree-shaking and causes unused code to remain in the final bundle.
  • Isolate Side Effects: Keep code with side effects separated from pure utility modules. Rather than mixing global setups into an index.js file with exported helper functions, move initialization logic into dedicated files covered by the sideEffects array.
  • Test Production Builds: Tree-shaking optimizations only run in production mode (mode: 'production'). Always test production bundles to confirm that styles and polyfills are included properly.
