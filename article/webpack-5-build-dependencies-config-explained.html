Webpack 5 buildDependencies.config Explained

In Webpack 5, the buildDependencies.config option is a critical component of the filesystem cache mechanism that ensures build caches are invalidated when your build setup changes. This guide breaks down what buildDependencies.config does, why it is necessary for maintaining cache integrity, how to properly configure it to track your Webpack configurations, and how to avoid serving stale builds during development and production.

The Purpose of buildDependencies.config

Webpack 5 introduced persistent filesystem caching (cache.type = 'filesystem') to significantly reduce build times by storing compiled assets and module snapshots on disk. However, if you change your build configuration—such as adding a loader, updating a plugin, or altering an optimization setting—a previously saved cache might produce outdated or broken outputs.

The buildDependencies configuration object allows you to specify external files and dependencies that the build relies on. The config property within buildDependencies explicitly tells Webpack which configuration files must trigger a full cache invalidation whenever their contents change.

How to Configure buildDependencies.config

The standard implementation assigns an array containing __filename to buildDependencies.config. This ensures that the primary Webpack configuration file itself is tracked as a cache dependency.

// webpack.config.js
const path = require('path');

module.exports = {
  cache: {
    type: 'filesystem',
    buildDependencies: {
      // Invalidates the cache when webpack.config.js changes
      config: [__filename],
    },
  },
};

Tracking Additional Configuration Files

In modern development workflows, Webpack configurations often depend on external configuration files, helper modules, or environment definitions. If changes in these supplementary files affect the final bundle, they should also be added to the config array.

Common examples include:

  • TypeScript configurations (tsconfig.json)
  • Babel configurations (babel.config.js or .babelrc)
  • Tailwind or PostCSS configurations (postcss.config.js, tailwind.config.js)
  • Split Webpack configuration modules (such as separate base, development, and production files)
// webpack.prod.js
const path = require('path');

module.exports = {
  cache: {
    type: 'filesystem',
    buildDependencies: {
      config: [
        __filename,
        path.resolve(__dirname, 'webpack.common.js'),
        path.resolve(__dirname, 'tsconfig.json'),
        path.resolve(__dirname, 'postcss.config.js'),
      ],
    },
  },
};

Why It Matters

Without properly defining buildDependencies.config, Webpack may reuse the cache from a previous run even after you modify your build settings. This leads to subtle, hard-to-debug compilation issues where new configuration rules appear to have no effect until the cache directory is manually deleted. Defining this property guarantees that any configuration change safely resets the cache state, balancing rapid build performance with build consistency.
