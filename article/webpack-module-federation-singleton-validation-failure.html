Webpack Module Federation Singleton Validation Failure

In Webpack Module Federation, configuring a shared dependency as a singleton ensures that only a single instance of that library is loaded across the host and all remote containers. When a shared singleton module fails version validation—meaning an application requests a version outside the acceptable semver range defined by requiredVersion—Webpack executes a specific resolution sequence governed by your configuration. This article examines the exact runtime behaviors, console outputs, and failure modes that occur when a singleton requirement cannot be satisfied.

Default Behavior: Runtime Console Warnings

By default, Webpack prioritizes maintaining a single instance over strictly enforcing version requirements. When a version mismatch occurs:

  1. A Console Warning Is Emitted: Webpack prints a runtime warning in the browser console. The message typically states:
    Unsatisfied version X.X.X from <remote-name> of shared singleton module <module-name> (required Y.Y.Y).
  2. Execution Continues: The runtime does not halt. Webpack provides the already loaded instance or selects the highest compatible loaded version among all federated containers.
  3. Singleton Guarantee Maintained: Only one instance of the module exists in memory, protecting against issues that arise from duplicate library states, such as multiple instances of React or state-management stores.

Strict Version Enforcement: Runtime Errors

If the shared module configuration includes strictVersion: true, Webpack changes its fallback behavior from passive warning to active enforcement.

  • Execution Halts: Instead of a warning, Webpack throws a fatal runtime exception.
  • Uncaught Error: The application or remote container attempting to consume the mismatched dependency will fail to load, throwing an error indicating that no acceptable version could be resolved.
  • Use Case: This setting is recommended for mission-critical libraries where breaking API changes between versions would lead to silent data corruption, broken rendering, or hard-to-debug runtime exceptions.

Fallback to Secondary Versions

When singleton: false, Webpack can instantiate multiple versions of a dependency simultaneously to satisfy differing version requirements. However, once singleton: true is configured:

  • Fallback copies are disallowed.
  • If a host application loads version 17.0.0 of a library and a federated remote requires ^18.0.0, the remote is forced to use the host's version 17.0.0 (unless strictVersion: true halts execution).
  • If the remote tries to access APIs introduced in version 18.0.0, it will result in TypeError: ... is not a function or undefined runtime errors.

Mitigation Strategies

To resolve singleton requirement failures in production:

  • Align Dependency Ranges: Use flexible semver ranges (e.g., ^ or ~) in the requiredVersion field rather than pinned versions to give Webpack more latitude during resolution.
  • Enforce Root Monorepo Constraints: If using a monorepo, standardize shared package versions across all packages using tools like npm workspaces, Yarn workspaces, or pnpm.
  • Configure Load-Order Priority: Ensure that the shell or host container loads the highest version of the shared dependency first, as Webpack's singleton negotiation will default to the earliest initialized instance unless asynchronous chunk loading allows higher versions to pre-empt it.
