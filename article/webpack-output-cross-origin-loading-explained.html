Webpack output.crossOriginLoading Explained

The output.crossOriginLoading setting in Webpack dictates how dynamically loaded code chunks, such as those split via asynchronous import(), request external resources across different origins. By configuring this property, Webpack appends the standard HTML crossorigin attribute to dynamically generated <script> and <link> elements. This article explains what output.crossOriginLoading does, the values it accepts, and the HTTP security headers required on the hosting server to ensure assets load properly and securely.

What is output.crossOriginLoading?

When Webpack splits code into multiple bundles, it injects <script> tags into the DOM at runtime to load chunks on demand. If these assets are hosted on an external domain—such as a Content Delivery Network (CDN)—browsers treat them as cross-origin requests.

By default, cross-origin scripts are executed with restricted error reporting, often masking errors as a generic "Script error." Configuring output.crossOriginLoading forces Webpack to add the crossorigin attribute to these dynamically injected tags, enabling full error tracing in window.onerror and allowing Subresource Integrity (SRI) checks.

Supported Values

The output.crossOriginLoading option accepts three values in your webpack.config.js:

module.exports = {
  // ...
  output: {
    crossOriginLoading: 'anonymous', // Options: false, 'anonymous', 'use-credentials'
  },
};
  • false (Default): Disables cross-origin loading behavior. Dynamic <script> tags will not include a crossorigin attribute.
  • "anonymous": Injects crossorigin="anonymous" into dynamic tags. The browser sends a cross-origin request without user credentials (such as cookies, HTTP Basic authentication, or client-side SSL certificates).
  • "use-credentials": Injects crossorigin="use-credentials" into dynamic tags. The browser sends the request with credentials included, which is necessary if your asset server or CDN requires authenticated access.

Supported Security and CORS Headers

Setting output.crossOriginLoading on the client side requires specific Cross-Origin Resource Sharing (CORS) HTTP headers on the server hosting the static chunks. If the server does not return the correct headers, the browser will block the script from executing.

  1. Access-Control-Allow-Origin
    • Required for: Both "anonymous" and "use-credentials".
    • Behavior: When using 'anonymous', the server can return either a wildcard (Access-Control-Allow-Origin: *) or a specific origin (e.g., Access-Control-Allow-Origin: https://example.com). When using 'use-credentials', the wildcard * is not permitted by browsers; the header must explicitly reflect the requesting origin.
  2. Access-Control-Allow-Credentials
    • Required for: "use-credentials".
    • Behavior: The asset server must set this header to true (Access-Control-Allow-Credentials: true). If set to false or omitted when using 'use-credentials', the browser rejects the response.
  3. Cross-Origin-Resource-Policy (CORP)
    • Header: Cross-Origin-Resource-Policy: cross-origin
    • Behavior: While not strictly part of CORS negotiation, modern browsers check this header to defend against speculative side-channel attacks (like Spectre). If a server protects assets with Cross-Origin-Resource-Policy: same-origin, the browser blocks the assets regardless of the crossorigin attribute.
  4. Integration with Subresource Integrity (SRI)
    • While not an HTTP header itself, enabling output.crossOriginLoading is a mandatory prerequisite for using SRI headers and plugins (like webpack-subresource-integrity). SRI requires explicit CORS authorization to validate script hashes against loaded content to prevent tampering.
