Webpack maxInitialRequests and Page Load Guide

The maxInitialRequests setting in Webpack controls the maximum number of parallel HTTP requests allowed for an entry point when a user first loads a webpage. By setting a ceiling on how many separate JavaScript and CSS files the browser can fetch at startup, this configuration balances browser caching efficiency against network overhead, directly influencing core performance metrics like First Contentful Paint (FCP) and Largest Contentful Paint (LCP).

What Is maxInitialRequests?

In Webpack, optimization.splitChunks.maxInitialRequests is a configuration property that dictates chunk splitting for entry points. An "initial request" refers to any script or stylesheet required to render the initial view—specifically, files referenced directly by HTML <script> and <link> tags, rather than those loaded dynamically via import().

When Webpack analyzes code to separate vendor libraries or shared modules into distinct chunks, it checks maxInitialRequests. If creating another chunk causes the total count of initial files to exceed this threshold, Webpack suppresses further splitting and merges the remaining modules into existing chunks, even if those modules satisfy other rules like minSize. In Webpack 5, the default value is 30, whereas in Webpack 4, the default was 3.

Impact on Page Load Performance

The value assigned to maxInitialRequests directly impacts the critical rendering path in several ways:

1. Network Protocol Efficiency (HTTP/1.1 vs. HTTP/2 and HTTP/3)

Under the legacy HTTP/1.1 protocol, browsers are limited to roughly six concurrent TCP connections per origin. If maxInitialRequests is set too high, requests are queued, causing network contention and delayed execution.

With HTTP/2 and HTTP/3, multiplexing enables browsers to download dozens of small files concurrently over a single connection. Consequently, higher values are generally safe under modern protocols, allowing developers to split application bundles into more granular chunks without significant request-queuing penalties.

2. Long-Term Caching vs. Request Overhead

Higher limits allow granular code splitting. For instance, separating large third-party dependencies (such as React, Lodash, or analytical tools) into separate chunks means a code change in the application logic invalidates only the app chunk, leaving vendor chunks cached in the user's browser.

However, setting the limit excessively high can degrade performance even on HTTP/2. Dozens of micro-requests introduce decompression overhead, redundant HTTP header size, and increased JavaScript parsing and compilation overhead on low-powered mobile devices.

3. Initial Rendering Metrics

If maxInitialRequests is set too low (e.g., 1 to 3), Webpack bundles code into a small number of large files. While this minimizes the number of round trips, it forces users to download non-essential code upfront, delaying FCP and Time to Interactive (TTI). Conversely, a balanced value allows the critical entry point to stay lean while secondary initial assets load in parallel.

Recommended Configuration Strategy

To optimize maxInitialRequests:

  • Audit the Hosting Infrastructure: Use higher values (e.g., 20–30) if your application is served via HTTP/2 or HTTP/3 with a Content Delivery Network (CDN). If supporting HTTP/1.1 environments, keep the limit lower (around 5–8) to avoid connection blocking.
  • Coordinate with minSize and maxAsyncRequests: Ensure that minSize prevents the creation of micro-chunks (under 20 KB) that waste HTTP overhead, and align maxInitialRequests with your application's actual dependency footprint.
  • Measure Real-World Impact: Validate adjustments using tools like Google Lighthouse and WebPageTest, monitoring FCP, LCP, and Total Blocking Time (TBT) across both mobile and desktop profiles.
