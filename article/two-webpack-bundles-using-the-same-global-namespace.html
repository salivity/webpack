Two Webpack Bundles Using the Same Global Namespace

When two independent Webpack bundles execute on the same web page using an identical global namespace, they inevitably collide at runtime. This conflict leads to chunk loading failures, module ID collisions, broken asynchronous imports, and corrupted application state. Because Webpack relies on global variables to coordinate dynamic loading and expose exports, sharing a namespace causes one bundle to unintentionally hijack or overwrite the execution context of the other.

The Mechanism of the Collision

By default, Webpack uses a global array to manage asynchronous chunk loading and module resolution. In Webpack 5, this is governed by output.chunkLoadingGlobal (which defaults to webpackChunk combined with the project name), whereas Webpack 4 used output.jsonpFunction (defaulting to webpackJsonp). Additionally, bundles configured to export APIs globally share properties assigned through output.library.name.

When a bundle initializes, it checks the global scope (usually window) for its designated namespace. If the namespace does not exist, Webpack initializes it as an array and overrides its .push() method with its own runtime resolver. If two separate bundles target the same variable—such as window.webpackChunk or a shared window.MyApp—the following issues occur:

1. Chunk ID Collisions and Deserialization Failures

Webpack identifies code-split chunks using numeric or deterministic string IDs (like 0.js, 1.js, or generated hashes). When Bundle A requests chunk 1, it pushes [ [1], { ...modules } ] into the global array.

If Bundle B also has a chunk labeled 1, both runtimes listen to pushes on the exact same array. Bundle A's runtime may intercept and execute Bundle B's chunk, or mark chunk 1 as resolved before Bundle A's actual code arrives. This leads to immediate runtime errors such as TypeError: Cannot read properties of undefined or Loading chunk failed.

2. Runtime Interceptor Hijacking

The first bundle to load sets up an internal monkey-patched .push() implementation on the global chunk array. When the second bundle loads, it either wraps or overwrites this .push() handler with its own runtime logic.

Because the second bundle's runtime does not contain the internal module registry of the first bundle, any subsequent asynchronous chunks loaded by Bundle A will be processed by Bundle B's resolver. This causes missed module registrations, unhandled promises, and silent execution failures.

3. Global Library Overwrites

If the bundles are exposed as libraries using identical output.library configurations, execution order determines survival:

// Bundle A execution
window.MyLibrary = { featureA: function() { ... } };

// Bundle B execution
window.MyLibrary = { featureB: function() { ... } };

The second bundle entirely replaces the object reference of the first. Any host code or scripts relying on MyLibrary.featureA will fail immediately upon attempting to invoke the overwritten methods.

How to Prevent Global Namespace Collisions

To safely run multiple independent Webpack applications on a single page, each bundle must have isolated runtime identifiers:

  • Configure output.uniqueName: In Webpack 5, set a distinct output.uniqueName in webpack.config.js for each project. Webpack uses this string to derive unique values for chunk loading registries automatically.
  • Isolate Chunk Loading Arrays: Explicitly define unique values for output.chunkLoadingGlobal (Webpack 5) or output.jsonpFunction (Webpack 4) to ensure dynamic import queues do not overlap.
  • Namespace Library Exports: Ensure output.library.name is unique, or compile bundles as native ES modules (output.library.type: 'module') to bypass the global window object entirely.
