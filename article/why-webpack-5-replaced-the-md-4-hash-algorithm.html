Why Webpack 5 Replaced the MD4 Hash Algorithm

Webpack 5 transitioned its default hashing algorithm away from legacy MD4 to modernize build performance, resolve critical compatibility failures with modern Node.js runtimes, and support hardened operating environments. While MD4 was originally adopted strictly as a fast way to generate cache-busting file hashes, changes in underlying cryptographic libraries—specifically OpenSSL 3.0—rendered MD4 a major liability for developers. This shift allowed Webpack to adopt faster, non-cryptographic hashing algorithms like xxhash64 while eliminating breaking build errors across the JavaScript ecosystem.

The Role of MD4 in Early Webpack Versions

In Webpack 4 and earlier versions, the bundler used MD4 to generate asset hashes for file naming (such as [contenthash] and [chunkhash]). Webpack did not use MD4 for data security or cryptographic protection; it used the algorithm purely to generate unique, deterministic strings for browser cache invalidation. At the time, MD4 was chosen primarily because it was computationally faster than standard alternatives like MD5 or SHA-256 within Node's built-in crypto module.

Breaking Changes in Node.js and OpenSSL 3.0

The primary catalyst for dropping MD4 was the release of Node.js 17, which upgraded the internal cryptography engine from OpenSSL 1.1.1 to OpenSSL 3.0. OpenSSL 3.0 introduced strict security policies that actively disabled legacy and cryptographically broken algorithms by default.

Because MD4 had been proven insecure since the 1990s, OpenSSL 3.0 categorized it as unsupported legacy cryptography. When older Webpack builds ran on Node.js 17 or higher, calls to Node's crypto.createHash("md4") failed abruptly, throwing the widespread error:

Error: error:0308010C:digital envelope routines::unsupported

While developers temporarily bypassed this issue using the --openssl-legacy-provider flag, Webpack required a permanent, native resolution that did not rely on deprecated system libraries.

Enterprise Security and FIPS Compliance

Beyond basic compatibility, MD4 presented severe issues in enterprise environments configured for FIPS (Federal Information Processing Standards) compliance. Hardened operating systems and enterprise containers completely restrict non-FIPS-approved algorithms. Even though Webpack used MD4 strictly for compilation integrity rather than data encryption, security scanners and FIPS-enabled operating systems routinely blocked the process, preventing enterprise development pipelines from succeeding.

The Move to xxhash64

To resolve both security and compatibility hurdles, Webpack 5 made xxhash64 the default hash function. Unlike MD4, XXH64 is explicitly designed as an extremely fast, non-cryptographic hash algorithm.

Switching to xxhash64 provided several direct benefits:

  • Superior Execution Speed: XXH64 processes data near RAM speed limits, generating hashes faster than MD4.
  • OpenSSL Independence: Because it is non-cryptographic, it does not rely on OpenSSL's legacy modules, avoiding ERR_OSSL_EVP_UNSUPPORTED runtime crashes.
  • Low Collision Rates: Despite being non-cryptographic, it provides excellent distribution and collision resistance suitable for enterprise-scale asset tracking.

By abandoning MD4, Webpack 5 removed an obsolete dependency on broken cryptographic APIs, ensuring long-term runtime stability across newer Node.js versions and delivering faster asset compilation.
