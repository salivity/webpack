Fix Version Mismatches in Webpack Module Federation

Managing shared dependencies across micro-frontends can lead to runtime crashes or redundant code downloads when hosts and remotes rely on conflicting package versions. This article explains how Webpack Module Federation negotiates library versions, how to configure the shared option to enforce compatibility, and how to prevent multiple instances of stateful packages like React.

How Module Federation Resolves Versions

Webpack Module Federation uses a shared scope mechanism to register and negotiate dependencies at runtime. When a host or remote initializes, it registers its own shared dependencies and their respective versions into this shared scope.

By default, Webpack determines whether to reuse an existing library or fetch a new one based on Semantic Versioning (SemVer):

  • If the requested version satisfies the SemVer range required by the consuming container, Webpack reuses the already loaded version.
  • If the versions are incompatible (for example, a major version difference such as v17.x vs. v18.x), Webpack will download and load the second version separately to avoid breaking the application.

Enforcing Single Instances with singleton

Certain libraries rely on global state, contexts, or DOM access and cannot have more than one instance running in the application (e.g., react, react-dom, vue, or state management libraries). Loading two copies of React, for example, typically causes the "Invalid Hook Call" error.

To ensure only one instance is ever loaded, use the singleton flag:

// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      shared: {
        react: {
          singleton: true,
        },
        'react-dom': {
          singleton: true,
        },
      },
    }),
  ],
};

When singleton: true is set, Webpack will always choose the highest available version in the shared scope and provide that single instance to all containers.

Controlling Compatibility with requiredVersion and strictVersion

While singleton: true guarantees a single copy, it does not guarantee that the highest available version is backward-compatible with older containers. If an older micro-frontend requires React 17 and a newer one introduces React 18, forcing React 18 on the older container could introduce bugs.

To control this behavior, combine requiredVersion with strictVersion:

  • requiredVersion: Explicitly defines the SemVer range accepted by the container. You can set this manually or read it dynamically from your package.json.
  • strictVersion: Dictates the behavior when a version check fails. If set to true, Webpack throws a runtime error instead of logging a console warning and proceeding with an incompatible version.
const deps = require('./package.json').dependencies;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'remote_app',
      shared: {
        react: {
          singleton: true,
          requiredVersion: deps.react,
          strictVersion: true, // Throws an error if versions do not match the range
        },
        'react-dom': {
          singleton: true,
          requiredVersion: deps['react-dom'],
          strictVersion: true,
        },
      },
    }),
  ],
};

Deciding Between Shared Instances and Isolated Duplicates

For stateless, utility-driven libraries (such as lodash or date-fns), having multiple versions loaded simultaneously is often acceptable and safer than forcing an incompatible update.

  • For stateful libraries: Always configure singleton: true, specify requiredVersion, and evaluate whether strictVersion: true is necessary to prevent silent regressions.
  • For stateless utility libraries: Omit singleton. Allow Webpack to resolve the highest compatible version, or fall back to loading duplicate copies if the versions diverge across major releases.

Proactive Governance and Tooling

Relying entirely on runtime negotiation adds operational risk. To minimize version mismatches before reaching production:

  1. Monorepo Architecture: Use tools like Nx, Turborepo, or pnpm workspaces to enforce a single source of truth for core dependencies across all micro-frontends.
  2. Automated CI Checks: Implement pull request checks that parse each micro-frontend's package.json to flag mismatched major or minor dependencies prior to merging.
  3. Coordinated Upgrades: Establish an upgrade cadence across teams for critical foundation packages so that remotes and hosts stay within compatible version ranges.
