Webpack optimization.sideEffects and package.json

This article explains how Webpack's optimization.sideEffects configuration setting directly interacts with the sideEffects property declared in a project's or dependency's package.json. You will learn how these two mechanisms collaborate to enable efficient tree shaking, what happens when either is toggled, and how to avoid common bundling pitfalls like accidental deletion of styles or polyfills.

The Role of package.json sideEffects

In modern JavaScript development, a side effect occurs when a module modifies global state, executes code upon import (such as polyfills), or imports global CSS.

By default, Webpack cannot safely assume that an imported module without consumed exports can be omitted, because running that module might trigger necessary side effects. The package.json sideEffects field allows package authors to inform Webpack about the nature of their code:

  • "sideEffects": false: Informs Webpack that none of the files in the package produce side effects upon import, allowing unused re-exports or unused modules to be completely skipped.
  • "sideEffects": ["./src/polyfills.js", "**/*.css"]: Specifies a whitelist of files that contain side effects, leaving the rest marked as side-effect-free.

The Role of optimization.sideEffects

The optimization.sideEffects configuration in webpack.config.js is the engine-level switch that controls how Webpack handles side-effect declarations during the build process.

  • true (Default in production mode): Webpack respects and acts on the sideEffects declarations found in package.json files and performs module pruning.
  • false: Webpack completely ignores package.json sideEffects declarations. Modules will be included in the bundle even if they are re-exported and unused.
  • "flag": Webpack analyzes modules for side effects by checking source code statements (like AST evaluations), but it does not skip module evaluation based on package.json metadata.

How They Correlate

The relationship between the two settings is hierarchical: optimization.sideEffects acts as the master consumer, while package.json sideEffects acts as the data provider.

  1. Both Enabled (optimization.sideEffects: true and "sideEffects": false): Webpack skips importing unused modules entirely. For example, if you do import { button } from 'library' where library/index.js re-exports hundreds of components, Webpack reads the sideEffects: false from the library's package.json and skips compiling the unused components completely.

  2. Master Switch Disabled (optimization.sideEffects: false): Regardless of whether a library or your local package.json specifies "sideEffects": false, Webpack will ignore that declaration. All re-exported modules will be retained in the compilation pipeline, significantly increasing bundle size and compilation time.

  3. Missing package.json Declaration: If optimization.sideEffects: true is enabled, but a package does not declare "sideEffects": false (or its globs), Webpack assumes all files within that package have side effects. Tree-shaking of unused re-exports is bypassed for that package to prevent breaking functionality.

Key Considerations

  • CSS and Global Scripts: If you set sideEffects: false in your local project while optimization.sideEffects: true is active, importing CSS files directly (e.g., import './style.css') might be omitted from production builds because Webpack sees no consumed export. You must whitelist these files using the array format in package.json.
  • Build Performance: Enabling optimization.sideEffects speeds up production builds because the bundler skips parsing, processing, and traversing entire dependency subtrees that are marked without side effects.
