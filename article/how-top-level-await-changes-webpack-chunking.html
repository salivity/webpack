How Top-Level Await Changes Webpack Chunking

Using top-level await fundamentally transforms how Webpack bundles and executes JavaScript modules by converting standard synchronous modules into asynchronous boundaries. When a module utilizes top-level await, Webpack alters its chunk evaluation order, modifies runtime orchestration to rely on native promises, and automatically propagates asynchronous execution status up the dependency graph. This article details the specific mechanics, chunk-splitting behaviors, and runtime changes that occur when top-level await is introduced into a Webpack project.

Transformation into Asynchronous Modules

Under standard conditions, Webpack treats EcmaScript modules as synchronous units executed sequentially during runtime initialization. When a module contains a top-level await expression, Webpack marks the module as an async module. Instead of evaluating immediately upon execution of the enclosing chunk, the module evaluates asynchronously, returning a promise to the Webpack runtime. Webpack injects specialized runtime helpers (such as __webpack_require__.a) to intercept module exports and coordinate the resolution of these module-level promises.

The Propagation Effect Across the Dependency Graph

Async modules are contagious. If Module A utilizes top-level await, any Module B that imports Module A via a static import declaration also becomes an async module by extension, even if Module B contains no await keywords itself.

This propagation continues upward until it reaches either:

  1. An entry point configured to support asynchronous execution.
  2. A dynamic import() boundary, which naturally handles asynchronous resolution via promises.

Because the async property cascades upward, an entire branch of your dependency tree can be converted into asynchronous evaluation targets, directly impacting how Webpack clusters those modules into chunks.

Impact on Chunk Splitting and Execution Flow

Top-level await shifts the execution lifecycle of Webpack chunks from a deterministic, depth-first synchronous traversal to a promise-driven asynchronous resolution.

  • Non-Blocking Sibling Evaluation: In standard Webpack output, a chunk block waits synchronously for each module in its dependency list to finish evaluating before moving to the next. With top-level await, child modules within the chunk initiate their asynchronous operations simultaneously. Siblings that do not depend on the awaiting module can continue executing without waiting for the promise to resolve.
  • Delayed Dependent Execution: Any module or chunk downstream of the top-level await module is paused until the promise fulfills. Webpack defers the execution of the dependent module's factory function, preventing execution of consumer code until all imported promises settle.
  • Dynamic Import Alignment: Because static imports of top-level await modules behave asynchronously, they functionally mimic the behavior of dynamic import() expressions within the runtime graph. While Webpack might not automatically force the async module into a separate .js file purely because of the keyword, it treats the module boundary as an asynchronous barrier identical to a dynamic boundary.

Entry Chunk Constraints and Configuration Requirements

Entry chunks face distinct challenges when dealing with top-level await. Traditional HTML <script> tags without type="module" cannot synchronously wait for an entry bundle that returns a promise.

When top-level await affects an entry chunk:

  • If building for web targets without ES module outputs (output.module: false), the entry chunk cannot synchronously execute top-level awaits without top-level runtime orchestration. Webpack wraps the entry execution in an internal promise handler, meaning code outside the bundle relying on global variables set by that entry point may execute before the entry finishes loading.
  • When targeting modern environments with experiments.outputModule: true, Webpack outputs the entry as an ES module, allowing the browser runtime to natively manage the top-level promise chain via standard browser-level module loading.

Impact on SplitChunksPlugin Behavior

Webpack’s SplitChunksPlugin relies on module types, execution context, and shared dependencies to determine chunk boundaries. When top-level await is enabled:

  • Chunk Merging Logic: Webpack prevents certain optimizations that would normally inline a shared synchronous module into an initial entry chunk if doing so introduces an unexpected async module into a strictly synchronous entry context.
  • Shared Async Chunks: If a shared chunk contains a top-level await module, all consuming chunks must be compatible with promise-based resolution. Webpack handles the shared chunk as an asynchronous dependency, ensuring the runtime loads and awaits the shared chunk's promise before invoking dependent chunks.
