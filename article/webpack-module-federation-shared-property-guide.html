Webpack Module Federation Shared Property Guide

The shared property in Webpack Module Federation is a configuration setting that enables micro-frontends to share common npm dependencies, preventing duplicate libraries from being downloaded across different independent builds. This article details the primary purposes of the shared property, how it manages version negotiation between host and remote applications, and the essential configuration options required to maintain application stability and performance.

Preventing Redundant Downloads and Code Duplication

In a micro-frontend architecture, each independent application maintains its own build process and dependency tree. Without a sharing mechanism, if both a host application and an imported remote application rely on heavy libraries like React, Vue, or Lodash, users would be forced to download these identical packages multiple times.

The shared property informs Webpack to register specified packages into a runtime shared scope. At runtime, the applications coordinate to load the shared dependency only once, significantly reducing initial bundle sizes and network overhead.

Enforcing Singletons for State and Context Integrity

Certain libraries malfunction if multiple instances coexist within the same JavaScript execution context. Frameworks that rely on global state, React Context, or component component lifecycles (such as react and react-dom) require a single instance across the entire application runtime.

By utilizing the shared property with singleton flags, Module Federation guarantees that all federated modules consume the exact same runtime instance of the library, avoiding bugs caused by mismatched internal instances or broken context providers.

Version Negotiation and SemVer Management

When multiple micro-frontends declare the same shared dependency, Webpack uses Semantic Versioning (SemVer) to dynamically negotiate which version to load. By default:

  1. Webpack evaluates the version provided by the host and all loaded remotes.
  2. It loads the highest compatible version that satisfies the SemVer constraints defined across all participating applications.
  3. If versions are incompatible and not forced to be singletons, Webpack loads fallback copies to prevent runtime breaking changes.

Key Configuration Options

The shared property can be configured as a simple array of package names or as an object providing fine-grained control:

  • singleton: A boolean that, when set to true, ensures that only one instance of the dependency is ever loaded across all applications. If a version mismatch occurs, Webpack issues a warning instead of loading a second instance.
  • requiredVersion: Specifies the acceptable SemVer range for the shared package. This prevents incompatible major or minor releases from executing together.
  • strictVersion: When set to true alongside singleton, Webpack halts execution and throws an error if the loaded dependency version does not satisfy the requiredVersion constraint.
  • eager: By default, Webpack loads shared libraries asynchronously. Setting eager: true bundles the dependency directly into the initial entry point, which is often required in the shell/host application when asynchronous chunk splitting is not used.
