Bundle SharedWorkers and ServiceWorkers with Webpack

This article demonstrates how to bundle both a SharedWorker and a ServiceWorker in a single Webpack build pipeline. While modern web applications frequently use Service Workers for offline caching and Shared Workers for cross-tab state management, compiling them alongside main thread code can create global scope conflicts and path resolution issues. Below, you will find direct architectural strategies and concrete configurations using Webpack 5 to handle both worker types seamlessly without build errors or runtime environment leakage.

The Challenge of Multiple Worker Types

Bundling both worker types simultaneously presents two core challenges:

  1. Global Scope Differences: The main application runs in a Window context, while Service Workers run in ServiceWorkerGlobalScope and Shared Workers run in SharedWorkerGlobalScope. Standardizing Webpack's runtime to reference self rather than window is essential.
  2. URL and File Scoping: Service Workers must typically be served from the application's root scope (or an explicitly defined path) to control root-level requests, while Shared Workers can reside in nested build or chunk directories.

Method 1: Webpack 5 Native Worker Syntax (Single Compilation)

Webpack 5 natively understands worker instantiation using the ECMAScript URL constructor. When written correctly, Webpack automatically provisions an isolated worker execution context for each file without requiring worker-loader.

1. Instantiating the Workers

In your client-side application code:

// Register the Service Worker
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register(
    new URL('./workers/service.worker.js', import.meta.url),
    { type: 'module' }
  );
}

// Instantiate the Shared Worker
const sharedWorker = new SharedWorker(
  new URL('./workers/shared.worker.js', import.meta.url),
  {
    name: 'app-shared-worker',
    type: 'module'
  }
);

2. Webpack Configuration

Ensure your webpack.config.js properly configures globalObject and output parameters:

const path = require('path');

module.exports = {
  mode: 'production',
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash].js',
    path: path.resolve(__dirname, 'dist'),
    publicPath: '/',
    clean: true,
    // Ensures chunks execute safely across window and worker scopes
    globalObject: 'self', 
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: 'babel-loader',
      },
    ],
  },
};

Using new URL(..., import.meta.url) triggers Webpack's internal WorkerPlugin. It generates separate chunks for service.worker.js and shared.worker.js, manages their dependency graphs, and sets up worker-safe chunk-loading runtimes automatically.

Method 2: Multi-Compiler Configuration (Dedicated Scoping)

If your Service Worker needs a fixed filename at the root directory (such as /sw.js without a content hash) or requires independent plugins (such as WorkboxWebpackPlugin), a multi-compiler configuration is the standard pattern.

Exporting an array of configurations instructs Webpack to process tasks in parallel within the same command.

const path = require('path');

// 1. Client App & SharedWorker Configuration
const clientConfig = {
  name: 'client',
  target: 'web',
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'js/[name].[contenthash].js',
    publicPath: '/',
    globalObject: 'self',
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: 'babel-loader',
      },
    ],
  },
};

// 2. ServiceWorker Specific Configuration
const serviceWorkerConfig = {
  name: 'sw',
  target: 'webworker',
  entry: './src/workers/service.worker.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    // Kept at root level to maintain maximum registration scope
    filename: 'sw.js', 
    publicPath: '/',
    globalObject: 'self',
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: 'babel-loader',
      },
    ],
  },
};

module.exports = [clientConfig, serviceWorkerConfig];

In this setup:

  • The clientConfig processes the application and the SharedWorker via Webpack's native new URL() syntax.
  • The serviceWorkerConfig uses target: 'webworker' to ensure strict adherence to worker APIs and outputs sw.js predictably at the root of dist/.

Worker Implementation Essentials

SharedWorker Implementation (shared.worker.js)

Shared Workers communicate via ports through the onconnect event:

self.onconnect = (event) => {
  const port = event.ports[0];

  port.onmessage = (e) => {
    port.postMessage(`SharedWorker response: ${e.data}`);
  };

  port.start();
};

ServiceWorker Implementation (service.worker.js)

Service Workers act as network proxies and respond to lifecycle events:

self.addEventListener('install', (event) => {
  self.skipWaiting();
});

self.addEventListener('activate', (event) => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', (event) => {
  // Direct caching or custom network logic
  event.respondWith(fetch(event.request));
});

Summary Checklist for Production Builds

  • Target and Global Scope: Set output.globalObject: 'self' so the Webpack chunk-loading runtime avoids attempting to reference the window object within workers.
  • Service Worker Scope: Ensure the Service Worker output sits at the root path or that an appropriate Service-Worker-Allowed HTTP header is served from your origin.
  • MIME Types: Verify your web server delivers both worker output files using the application/javascript or text/javascript MIME types.
