Debugging Webpack Module Federation Runtime Issues

Webpack Module Federation allows micro-frontends to share dependencies and load remote modules dynamically, but this distributed execution often introduces complex runtime failures. Issues such as chunk loading failures, shared singleton collisions, and missing remotes can be difficult to trace across isolated builds. This article outlines practical strategies for identifying, isolating, and resolving runtime errors in Webpack Module Federation architectures.

Inspect Network Traffic and Remote Entry Scripts

Runtime execution begins with fetching the remote manifest. When an application fails to render a federated module, start by inspecting the Network tab in your browser's developer tools:

  • HTTP Status Codes: Verify that remoteEntry.js loads with a 200 OK status. Common culprits for failure include incorrect public paths (output.publicPath), CORS misconfigurations on the remote host, or incorrect deployment URLs.
  • MIME Types: Ensure the host server serves remoteEntry.js with the correct application/javascript content type.
  • Sub-chunk Fetching: After remoteEntry.js loads, inspect whether the dynamic chunk files requested upon component execution (such as src_Button_js.js) are returning 404 errors due to mismatched or hardcoded base URLs.

Verify Global Scopes in the Browser Console

Webpack registers remotes on the global window object by default. If a remote module fails to initialize, open the browser console to confirm its presence:

  1. Query the remote container name directly: window.<remote_name> (e.g., window.app2).

  2. If the object returns undefined, the script failed to run, was blocked, or the name property inside ModuleFederationPlugin differs from the identifier referenced in the host.

  3. Test initialization manually in the console:

    await window.remoteName.init(__webpack_share_scopes__.default);
const factory = await window.remoteName.get('./Component');
const Module = factory();

    Executing this manual resolution pipeline highlights whether the issue stems from initialization or dynamic chunk retrieval.

Diagnose Shared Dependency and Singleton Conflicts

Shared dependencies—particularly stateful libraries like React or Redux—frequently cause runtime errors like "Invalid hook call" when duplicated.

  • Check __webpack_share_scopes__: Run console.log(__webpack_share_scopes__.default) in the browser console. This inspects loaded library versions, loaded states, and assigned fallback versions.

  • Enforce Singletons: Ensure critical shared libraries use singleton: true in the ModuleFederationPlugin configuration of both the host and remotes:

    shared: {
  react: { singleton: true, requiredVersion: '^18.2.0' },
  'react-dom': { singleton: true, requiredVersion: '^18.2.0' }
}

  • Strict Versioning: Set strictVersion: true during development to force Webpack to throw an explicit runtime console warning/error when a version mismatch occurs, rather than quietly falling back to multiple instances.

Ensure Asynchronous Bootstrapping

A common runtime failure in host applications is the immediate execution of shared modules before the shared scope has initialized. This typically manifests as: Uncaught Error: Shared module is not available for eager consumption.

To fix this, decouple initialization by creating an asynchronous boundary:

  1. Move the application entry logic into a bootstrap.js file.

  2. In the original index.js, dynamically import the bootstrap file:

    import('./bootstrap');

This asynchronous boundary gives Webpack time to fetch all required shared dependencies and remote interfaces before executing root application code.

Implement React Error Boundaries for Remote Modules

External network failures or code-level bugs inside a remote module should not crash the entire host shell. Wrap federated components inside Error Boundaries to isolate issues:

import React, { Suspense } from 'react';
import ErrorBoundary from './ErrorBoundary';

const RemoteButton = React.lazy(() => import('remoteApp/Button'));

export default function App() {
  return (
    <ErrorBoundary fallback={<div>Failed to load remote component.</div>}>
      <Suspense fallback={<div>Loading...</div>}>
        <RemoteButton />
      </Suspense>
    </ErrorBoundary>
  );
}

This setup captures stack traces specifically tied to remote lifecycle failures without halting the host runtime.

Enable Webpack Runtime Logging

When automated resolutions fail, enable detailed runtime diagnostic outputs. Set Webpack’s infrastructure logging to verbose in webpack.config.js:

infrastructureLogging: {
  level: 'verbose',
  debug: [/ModuleFederationPlugin/],
}

This configuration prints detailed information regarding dynamic remote resolution, shared module negotiation, and fallback selections directly to the terminal during compilation and dev-server runtime.
