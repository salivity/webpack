PurgeCSS Safelist: Protect Dynamic Classes in Webpack

PurgeCSS is essential for stripping unused styles from modern web applications, but its static analysis often accidentally removes dynamic component classes generated at runtime. By configuring safelist patterns within the Webpack build pipeline, developers can explicitly instruct PurgeCSS to ignore specific class names or dynamic string patterns. This article explains why dynamic classes disappear during production builds, how to configure the PurgeCSS safelist in Webpack, and best practices for using regular expressions to protect dynamic UI states.

The Challenge of Dynamic Classes

PurgeCSS optimizes production bundles by reading source files and identifying classes that appear as complete, static strings. When frontend components use string interpolation or conditional state logic—such as class="alert-${type}" or isActive ? 'nav-active' : ''—PurgeCSS cannot predict the generated class names. Because strings like alert-success or nav-active do not exist as continuous tokens in the scanned template files, the extractor marks their corresponding CSS rules as unused and removes them from the final stylesheet.

Configuring the Webpack Safelist

To resolve this issue, the purgecss-webpack-plugin provides a safelist property. Any selector or pattern defined in this property is excluded from the purging process, regardless of whether it was detected in your source code.

The safelist property accepts either a simple array or an object for granular control:

const path = require('path');
const glob = require('glob');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');
const PurgeCSSPlugin = require('purgecss-webpack-plugin');

module.exports = {
  // ... Webpack entry and output configuration
  plugins: [
    new MiniCssExtractPlugin({
      filename: '[name].css',
    }),
    new PurgeCSSPlugin({
      paths: glob.sync(`${path.join(__dirname, 'src')}/**/*`, { nodir: true }),
      safelist: {
        standard: [
          'is-active',
          /^modal-/,
          /^btn-(primary|secondary|danger)$/,
        ],
        deep: [/^dropdown-menu/],
        greedy: [/data-theme$/],
      },
    }),
  ],
};

Safelist Pattern Types

The safelist object supports distinct matching behaviors depending on how classes are composed in the DOM:

1. Standard Patterns

The standard array targets complete selector tokens. You can supply exact string literals for static utility classes or regular expressions to capture dynamic modifiers.

  • Exact string: 'is-open' preserves only .is-open.
  • Regular expression: /^status-/ preserves .status-pending, .status-resolved, and any class starting with status-.

2. Deep Patterns

The deep array ensures that a selector and all of its nested child rules are preserved. This is particularly useful for component libraries, tooltips, or WYSIWYG editor content where the parent container class is dynamic or injected:

  • Pattern: [/^ql-editor/] preserves .ql-editor, .ql-editor p, .ql-editor strong, and all associated child selectors.

3. Greedy Patterns

The greedy array matches selectors where any part of the selector chain matches the given pattern. If a rule contains multiple chained or grouped classes, matching any part ensures the entire rule remains:

  • Pattern: [/active/] will match .button.active, .menu-item-active > a, and .is-active-item.

Best Practices for Safelisting

  • Use Explicit Dynamic Patterns: Instead of matching broad terms like /red/, match defined patterns like /^bg-red-(100|200|500)$/ to avoid preserving unrelated legacy selectors.
  • Adopt Consistent Naming Conventions: Adopt structured prefixes like is-, has-, or js- for runtime state modifications. A single regex such as /^is-/ can protect all toggled states across your application.
  • Avoid Greedy Selectors for General Terms: Using greedy expressions on common phrases defeats the purpose of PurgeCSS by unintentionally preserving large chunks of dead code. Reserve greedy configurations for third-party libraries or dynamic data attributes.
