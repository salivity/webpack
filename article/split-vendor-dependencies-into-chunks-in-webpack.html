Split Vendor Dependencies into Chunks in Webpack

Splitting vendor dependencies into separate chunks is an essential Webpack optimization technique that improves web application performance and browser caching. Because third-party libraries change much less frequently than application code, separating them prevents users from re-downloading large packages every time a minor application update is deployed. This article explains how to configure Webpack's built-in SplitChunksPlugin via the optimization.splitChunks configuration to automatically extract dependencies from node_modules into isolated vendor bundles.

The Basic Configuration

Webpack handles code splitting through the optimization section of webpack.config.js. By default, Webpack applies default split rules, but you can explicitly configure it to group all external libraries into a single vendor bundle:

// webpack.config.js
const path = require('path');

module.exports = {
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash].js',
    chunkFilename: '[name].[contenthash].chunk.js',
    path: path.resolve(__dirname, 'dist'),
    clean: true,
  },
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
      },
    },
  },
};

Key Configuration Properties

  • chunks: 'all': Tells Webpack to optimize both synchronous and asynchronous imports. By default, Webpack only optimizes dynamically imported (async) chunks.
  • cacheGroups: Custom rules that tell Webpack how to group modules into separate files.
  • test: /[\\/]node_modules[\\/]/: A regular expression ensuring that only files inside the node_modules directory are included in this chunk.
  • name: 'vendors': Sets the output bundle name. Using [contenthash] in the output configuration ensures the resulting file name includes a unique hash (e.g., vendors.a1b2c3d4.js) for long-term browser caching.

Splitting Large Libraries into Individual Chunks

Grouping all node_modules into a single file can still result in a very large bundle. To optimize further, you can split specific, heavy dependencies—such as React, Vue, or UI libraries—into their own distinct chunks by adding dedicated cache groups:

optimization: {
  splitChunks: {
    chunks: 'all',
    maxInitialRequests: Infinity,
    minSize: 20000, // 20kb
    cacheGroups: {
      reactVendor: {
        test: /[\\/]node_modules[\\/](react|react-dom)[\\/]/,
        name: 'vendor-react',
        chunks: 'all',
        priority: 20, // Must be higher than the general vendor group
      },
      defaultVendors: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendor-common',
        chunks: 'all',
        priority: 10,
        reuseExistingChunk: true,
      },
    },
  },
}
  • priority: Determines which cache group captures a module if it matches multiple rules. The group with higher priority processes the file first.
  • reuseExistingChunk: Allows Webpack to reuse existing modules rather than duplicating them if they have already been split from the main bundle.

Granular Splitting per Package

For applications with numerous dependencies, you can dynamically create a separate chunk for each node_module package automatically:

optimization: {
  splitChunks: {
    chunks: 'all',
    cacheGroups: {
      defaultVendors: {
        test: /[\\/]node_modules[\\/]/,
        name(module) {
          // Extracts the package name from node_modules/<package-name>
          const packageName = module.context.match(/[\\/]node_modules[\\/](.*?)([\\/]|$)/)[1];
          // NPM package names are URL-safe, but some servers do not like '@' symbols
          return `npm.${packageName.replace('@', '')}`;
        },
      },
    },
  },
}

This approach generates files such as npm.lodash.[contenthash].js and npm.axios.[contenthash].js, ensuring that modifying or updating a single library only invalidates the cache for that specific package.
