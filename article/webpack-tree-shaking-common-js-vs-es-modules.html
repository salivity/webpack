Webpack Tree Shaking: CommonJS vs ES Modules

Tree shaking is Webpack's process of eliminating dead code to produce leaner production bundles. While the mechanism functions seamlessly with the static structure of ECMAScript Modules (ESM), handling CommonJS (CJS) modules introduces distinct challenges due to their dynamic runtime execution. This article examines how Webpack processes both formats, detailing why ESM is natively optimized for tree shaking, how Webpack 5 attempts to handle CommonJS, and the architectural differences between them.

Tree Shaking in ES Modules (ESM)

ES Modules are static by design. Statements using import and export must appear at the top level of a file and cannot be conditioned inside if blocks or functions. Because the imports and exports cannot change at runtime, Webpack can reliably analyze the entire dependency tree at compile time.

During the build process in production mode, Webpack evaluates ES Modules using a multi-step pipeline:

  1. Static Analysis: Webpack parses the abstract syntax tree (AST) of each module and tracks every exported and imported identifier.
  2. Flagging Unused Exports: Using the optimization.usedExports configuration (enabled by default in production), Webpack determines which exports are never referenced by an import statement anywhere in the dependency graph.
  3. Dead-Code Annotation: Webpack wraps the bundle output with annotations (e.g., /* unused harmony export */), leaving the declaration intact but stripping references to it.
  4. Minification: A minifier, such as Terser or SWC, runs on the final bundle and safely drops the annotated, unreferenced variables and functions.

Furthermore, ESM allows the use of the "sideEffects": false property in package.json. This signals to Webpack that entire files can be dropped completely if none of their exports are consumed, even if the file contains top-level executions.

Tree Shaking in CommonJS (CJS)

CommonJS modules rely on require() and module.exports. Unlike ESM, CommonJS is dynamic:

  • require() calls can be executed conditionally inside functions or control blocks.
  • module.exports is a plain JavaScript object that can be mutated at runtime, assigned dynamically via loops (exports[key] = val), or overwritten entirely at any point during code execution.

Because a compiler cannot definitively predict runtime object mutations without executing the code, Webpack historically treated all CommonJS modules as dynamic black boxes, preserving the entire module in the final bundle.

Webpack 5 CommonJS Analysis

Starting with Webpack 5, the bundler incorporates static analysis heuristics to perform limited tree shaking on CommonJS modules. Webpack inspects common CJS patterns, such as:

exports.foo = function () { /* ... */ };
exports.bar = function () { /* ... */ };

Or:

module.exports = {
  foo: function () { /* ... */ },
  bar: function () { /* ... */ }
};

If an importer references a specific property using destructuring or direct property access:

const { foo } = require('./math');
// or
const foo = require('./math').foo;

Webpack 5 tracks that bar was not referenced and flags it as unused, allowing the minifier to drop it.

Bailout Scenarios in CommonJS

CommonJS tree shaking is fragile. Webpack immediately bails out of optimization if it encounters dynamic patterns, including:

  • Computed Property Names: exports[dynamicKey] = value;
  • Whole-Object Reassignment: Reassigning module.exports after defining properties.
  • Passing Module References: Passing module.exports or exports as an argument to another function.
  • Dynamic Access: Using const math = require('./math'); math[dynamicMethod]();

When a bailout occurs, Webpack assumes the entire module is used and bundles all exported properties to prevent breaking runtime behavior.

Key Differences

Feature ES Modules (ESM) CommonJS (CJS)
Analysis Timing Static (Compile-time) Dynamic (Inferred via compile-time heuristics)
Reliability Deterministic and guaranteed Best-effort; prone to bailouts
Import Semantics Static bindings via import Runtime evaluation via require()
Unused File Elimination Supported via sideEffects flag Not reliably supported
Export Modification Immutable exports Mutable module.exports object

Practical Implications

To achieve maximum tree shaking efficiency in Webpack, source code and third-party dependencies should use ES Modules syntax. While Webpack 5 provides fallback analysis for CommonJS, it only succeeds with strict, static coding patterns. Relying on CommonJS for dead-code elimination introduces bundle-size unpredictability due to the ease with which runtime patterns bypass static inspection.
