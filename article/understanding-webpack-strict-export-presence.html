Understanding Webpack strictExportPresence

The strictExportPresence configuration option in Webpack controls how the bundler handles imports of missing exports. By default in older versions of Webpack, attempting to import a named export that does not exist results only in a warning, which can lead to silent runtime bugs. Enabling strictExportPresence elevates these warnings into fatal build errors, preventing broken code from ever reaching production.

What Does strictExportPresence Do?

When working with ES modules, you might accidentally import a variable, function, or class that does not exist in the target file—often due to a typo or an incomplete refactor:

// utils.js
export const calculateTotal = () => { /* ... */ };

// app.js
import { calculateTotals } from './utils'; // Typo in export name

Without strictExportPresence, Webpack may compile this code successfully and assign undefined to calculateTotals. The build succeeds, but the application crashes at runtime with a TypeError: calculateTotals is not a function.

Setting strictExportPresence: true forces Webpack to fail the build immediately whenever an imported export is not found in the referenced module.

How to Configure strictExportPresence

The option lives inside the module property of your webpack.config.js file:

module.exports = {
  // ...
  module: {
    strictExportPresence: true,
    rules: [
      // your loader rules here
    ],
  },
};

Differences Between Webpack 4 and Webpack 5

  • Webpack 4 and earlier: strictExportPresence defaults to false. Missing exports only generate a warning unless explicitly set to true.
  • Webpack 5: strictExportPresence defaults to true. The bundler automatically treats missing exports as hard errors out of the box, aligning with the official ECMAScript module specification.

Key Benefits

  1. Early Error Detection: Catches broken imports during compilation or continuous integration (CI) checks rather than during manual testing or in production.
  2. Safer Refactoring: If an exported function is renamed or removed, any consumer that hasn't been updated will immediately fail to build.
  3. Spec Compliance: Mirrors the strictness of native ES modules, ensuring predictable module resolution across your codebase.
