Webpack recordsPath Explained: Long-Term Caching

Webpack's recordsPath configuration option provides a mechanism to persist module and chunk identities across separate compilation runs by saving their state into a JSON file. Historically, this feature was an essential tool for achieving long-term browser caching in production environments, as it prevented Webpack from renumbering internal module IDs whenever dependencies changed. This article explains what recordsPath does, why it was historically vital for caching, and how modern Webpack configurations have evolved past the need for it.

What is recordsPath?

In Webpack, recordsPath is a configuration property that accepts an absolute file path pointing to a JSON file. During the build process, Webpack uses this file to track and store metadata about the build, primarily:

  • Module IDs: Numerical identifiers assigned to individual source files and dependencies.
  • Chunk IDs: Identifiers assigned to split bundles or entry points.

When a build starts, Webpack reads the existing file specified by recordsPath (or recordsInputPath). It uses those stored identifiers for modules and chunks that already exist, and it writes the updated state back to the file (or recordsOutputPath) when the build finishes.

The Historical Caching Problem

In early versions of Webpack (v1 through v3), Webpack assigned module and chunk IDs using simple incrementing integers (e.g., 0, 1, 2, ...). These integers were directly embedded in the compiled JavaScript bundle files and the Webpack bootstrap runtime.

This approach created a major problem for HTTP caching:

  1. If a developer added a new import or rearranged imports, the sequential assignment of module IDs shifted.
  2. Even if a bundle's source code remained unchanged, its internal module IDs—or the IDs of external chunks it referenced—would change.
  3. This shift altered the compiled bundle's content, changing its cryptographic content hash (e.g., app.a1b2c3.js became app.d4e5f6.js).
  4. End users' browsers were forced to re-download scripts that had no real business logic changes, defeating the purpose of long-term asset caching.

How recordsPath Solved the Caching Issue

By defining a recordsPath, developers could maintain a stateful history between builds.

// webpack.config.js (historical usage)
const path = require('path');

module.exports = {
  // ...
  recordsPath: path.join(__dirname, 'webpack-records.json'),
};

When building updates:

  1. Webpack inspected webpack-records.json.
  2. Any module previously mapped to an ID retained that exact ID, regardless of where new modules were inserted.
  3. Only newly introduced modules received new sequential IDs appended to the list.
  4. Because existing module and chunk IDs remained constant, the compiled output for untouched files remained byte-for-byte identical.
  5. As a result, the generated file hashes did not change, allowing browsers and CDNs to serve cached assets without re-fetching.

Why recordsPath Fell Out of Favor

While effective locally, using recordsPath in automated Continuous Integration and Continuous Deployment (CI/CD) pipelines proved difficult:

  • State Management: It required persisting the records.json file across ephemeral build environments (like Docker containers or CI workers) via storage buckets or git commits.
  • Concurrency: Parallel builds on different branches could lead to conflicting records or race conditions.

To resolve these operational hurdles, Webpack introduced deterministic hashing methods:

  • Webpack 3/4: Introduced HashedModuleIdsPlugin (and later NamedModulesPlugin), which derived module IDs from the relative path of the file rather than a sequential counter.
  • Webpack 5: Introduced native deterministic ID generation via optimization.moduleIds: 'deterministic' and optimization.chunkIds: 'deterministic'. These settings generate short, stable hashes based on filenames by default in production.

Modern deterministic IDs achieve the exact same caching benefits that recordsPath once provided, but they do so completely statelessly without requiring a persistent tracking file between builds.
