Migrating Ejected Create React App to Modern Tools

Migrating an ejected Create React App (CRA) project to modern build tools like Vite, Next.js, or Rsbuild offers faster build times, modern standards, and better developer experience. However, the migration process is rarely a simple drop-in replacement. Once a CRA project is ejected, it exposes a complex, highly coupled Webpack configuration that often accumulates bespoke plugins, loaders, and dependencies over time. Understanding the technical hurdles involved—such as polyfill removal, module resolution conflicts, and environment variable discrepancies—is critical for a smooth transition.

Untangling Custom Webpack Loaders and Plugins

When a project is ejected, developers usually modify the webpack.config.js to support specific requirements, such as custom SVG loaders, worker threads, or alternative styling solutions (e.g., Less or custom PostCSS pipelines). Modern tools like Vite rely on Rollup or native Rust/Go pipelines rather than Webpack loaders. Every custom Webpack loader must be audited and translated into its modern counterpart, such as replacing @svgr/webpack with Vite-specific SVGR plugins or reconfiguring PostCSS independently.

CommonJS vs. ESM and Node Polyfills

Ejected CRA configurations rely heavily on Webpack’s automatic polyfills and forgiving handling of mixed CommonJS (CJS) and ECMAScript Modules (ESM). Modern bundlers default to native ESM and do not polyfill Node.js core modules (Buffer, process, stream) by default. If legacy dependencies or internal modules rely on these Node primitives or use malformed CJS/ESM interop, modern tools will throw runtime or compilation errors. Resolving this requires either manually injecting polyfills or upgrading legacy packages to modern ESM-compatible versions.

Environment Variable Format Shifts

CRA enforces the REACT_APP_ prefix for client-exposed environment variables and injects them automatically via Webpack's DefinePlugin. Modern frameworks use different conventions:

  • Vite requires the VITE_ prefix and accesses variables through import.meta.env.
  • Next.js uses NEXT_PUBLIC_.

Migrating requires not only renaming environment variables in .env files and CI/CD pipelines, but also refactoring all instances of process.env.REACT_APP_* across the entire codebase to match the target tool's syntax.

Path Aliases and Module Resolution

Ejected CRA setups frequently include customized module resolution paths, such as NODE_PATH=src or custom Webpack resolve.alias entries. While modern tools support aliases, they require strict configurations that mirror both the bundler settings and tsconfig.json or jsconfig.json. Mismatches in resolution behavior can lead to broken absolute imports, circular dependency bugs, or failures in resolving extensions automatically.

Decoupling Testing and Linting Configurations

CRA bundles Jest, Babel, and ESLint configs into the ejected files, often with pre-configured transforms (like babel-jest) that mask underlying setup complexities. Migrating the bundler often necessitates migrating the testing pipeline—for example, switching from Jest to Vitest, or reconfiguring Jest to run without CRA's default react-scripts transforms. Decoupling test runners from the old build pipeline frequently surfaces hidden Babel configuration dependencies that break existing test suites.

HTML Entry Points and Asset Inlining

In CRA, the single-page application entry point is managed by HtmlWebpackPlugin, with an HTML template located in the public folder and dynamic script injection. Tools like Vite invert this model by using index.html at the project root as the primary entry point. Moving this file, adjusting path variables (like %PUBLIC_URL%), and handling statically imported assets—such as fonts, images, and manifests—requires structural refactoring to conform to modern static asset handling conventions.
