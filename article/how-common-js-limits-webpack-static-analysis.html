How CommonJS Limits Webpack Static Analysis

Webpack relies heavily on static code analysis to build dependency graphs, eliminate dead code, and optimize production bundles. While modern ECMAScript Modules (ESM) offer a predictable, declarative syntax that facilitates these optimizations, the legacy CommonJS (CJS) specification relies on dynamic runtime execution. This article examines the core limitations CommonJS imposes on Webpack's static analysis algorithms, specifically regarding dynamic dependency resolution, tree shaking failures, and hindered scope hoisting.

Dynamic Module Resolution

The primary challenge CommonJS presents to static analysis is that require() is an arbitrary JavaScript function rather than a declarative statement. In CommonJS, dependency paths do not need to be static strings; they can be variables, concatenated expressions, or the result of function calls (for example, require('./locales/' + lang + '.js')).

When Webpack encounters non-deterministic expressions, it cannot identify the exact target file during compile time. To avoid breaking runtime execution, Webpack must either generate a context module—bundling every potential file matching a regular expression within that directory—or issue a warning and fail to bundle the dependency accurately. This inflates bundle size and slows down build performance.

Dynamic and Conditional Exports

In CommonJS, exports are defined by assigning properties to a mutable object via module.exports or exports. These assignments can occur anywhere in a file, including inside conditionals, loops, or delayed callbacks.

Because the exported interface is defined imperatively at runtime, Webpack cannot reliably infer the module's public API at compile time. In contrast to ESM, where export statements are fixed and statically validated, Webpack must treat a CommonJS module's exports as an unknown, dynamic object.

Prevention of Tree Shaking (Dead Code Elimination)

Tree shaking depends on the compiler knowing exactly which named exports a file provides and which named imports the consuming module uses. Because CommonJS exports a single mutable object and imports via reference assignment (such as const utils = require('./utils')), Webpack cannot reliably guarantee that a particular property will not be accessed dynamically at runtime (e.g., utils[someVariable]).

As a result, Webpack adopts a conservative approach: if any part of a CommonJS module is imported, the entire module and its exports must be included in the final bundle. This inability to track named exports statically makes dead code elimination largely ineffective for CommonJS dependencies.

Obstacles to Scope Hoisting

Webpack uses the ModuleConcatenationPlugin (scope hoisting) to merge multiple modules into a single closure. This reduces runtime overhead, lowers memory footprint, and shrinks bundle size.

Scope hoisting requires strict guarantees about variable declarations, namespace pollution, and deterministic import/export bindings. Because CommonJS modules rely on the module wrapper function (function(module, exports, require)) and mutable runtime objects, Webpack often has to bail out of scope hoisting whenever a module boundary touches CommonJS code, keeping modules isolated in expensive runtime wrappers.

Cyclic Dependencies and Indeterminate Binding

CommonJS evaluates modules synchronously when they are first required and caches the exported value immediately. In circular dependency scenarios, a module may receive an incomplete, partially evaluated exports object. Because static analysis cannot easily simulate the exact runtime execution path without executing the code, Webpack cannot safely reorder, optimize, or inline CommonJS dependencies with cycles as it can with ESM's live-binding model.
