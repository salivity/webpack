Client vs Server Components in Webpack RSC

React Server Components (RSC) introduce a hybrid architecture that splits application rendering between the server and the browser. In a Webpack RSC pipeline, Client Components and Server Components are treated as fundamentally distinct module graphs, with Webpack responsible for compiling, chunking, and linking them across the network boundary. Understanding how Webpack processes these two component types clarifies their differences in bundle size, execution environment, and interactivity.

Execution Environment and Output

Server Components execute exclusively on the server (either at build time or per request). In the Webpack pipeline, their source code and non-client dependencies are never compiled into the client-side JavaScript bundle. Instead, Webpack and the RSC compiler transform Server Components into a serialized stream of UI instructions—often referred to as the React Server Component payload (or Flight response). This stream contains rendered HTML tags, structural component trees, and placeholder references for any nested Client Components.

Client Components execute on the client, although they can also be pre-rendered to static HTML during a server-side rendering (SSR) pass. When Webpack encounters a Client Component—typically denoted by the 'use client' directive—it extracts the component and its downstream dependencies into a standard browser bundle that downloads, parses, and hydrates in the user's browser.

The Webpack RSC Compilation Pipeline

A Webpack RSC setup generally requires two coordinated compilation passes (or a dual-environment configuration) managed by plugins such as react-server-dom-webpack:

  1. The Client Compilation: Webpack processes all modules marked with 'use client', producing the production browser chunks, source maps, and a client manifest. This manifest maps unique module IDs and export names to their corresponding output bundle paths.
  2. The Server Compilation: Webpack compiles the Server Components for the server runtime (e.g., Node.js or edge runtimes). When a Server Component imports a Client Component, the Webpack loader replaces the actual implementation with a lightweight proxy or "module reference" derived from the client manifest.

During runtime on the server, whenever the renderer hits a Client Component reference, it emits a special serialized marker containing the chunk ID and props rather than rendering the component's internal logic. The browser uses this marker to look up, fetch, and execute the actual JavaScript chunk produced by the client build.

Capabilities and Technical Limitations

The architectural division enforces strict boundaries on what each component type can do within the pipeline:

  • Server Components: Can directly access server-only resources such as databases, internal microservices, and file systems. They can be written as native asynchronous functions (async/await). However, because their JavaScript is never shipped to the client, they cannot use React state (useState, useReducer), lifecycle hooks (useEffect), or DOM event listeners (onClick, onChange).
  • Client Components: Provide full interactivity, supporting all React hooks, custom state management libraries, and browser-specific APIs (such as window, localStorage, or WebSockets). However, every library imported into a Client Component directly increases the JavaScript payload delivered to the end user.

Data Serialization Across the Boundary

In a Webpack RSC pipeline, data passed from a Server Component to a Client Component as props must cross the network boundary. Consequently, these props must be serializable by the RSC protocol. Supported types include JSON-serializable primitives, plain objects, arrays, and React elements (including other Server Components passed as children). Functions, non-plain classes, and symbols cannot be passed as props across this boundary, maintaining a strict separation between server execution context and client runtime memory.
