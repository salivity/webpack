Load Dynamic Remotes at Runtime in Webpack

Dynamic remote loading in Webpack Module Federation allows host applications to integrate micro-frontends on the fly without defining hardcoded URLs or remote names in build-time configuration files. This guide details how to bypass static Webpack declarations by leveraging dynamic script injection, the Webpack sharing scope API, and runtime container initialization to dynamically load remote micro-frontends based on dynamic runtime data.

The Problem with Static Declarations

Typically, Webpack Module Federation requires remotes to be declared directly inside the ModuleFederationPlugin configuration:

new ModuleFederationPlugin({
  name: 'host',
  remotes: {
    mfeApp: 'mfeApp@https://example.com/remoteEntry.js',
  },
})

While functional, this approach tightly couples the host application to a specific URL at build time. It prevents environments from swapping endpoints dynamically, resolving micro-frontends through an API manifest, or implementing multi-tenant architectures where different remotes are loaded depending on the active user.

The Runtime Loading Mechanism

Webpack exposes low-level APIs to initialize and consume remote containers at runtime:

  1. __webpack_init_sharing__('default'): Initializes the global shared scope across the host and remotes, ensuring shared dependencies (like React or Lodash) resolve correctly.
  2. __webpack_share_scopes__.default: The shared dependency registry passed to the remote container.
  3. Container Interface: Every Webpack remote entry exposes a global container object with two primary methods: init(shareScope) to receive dependencies and get(module) to provide the requested federated module.

Step-by-Step Implementation

To load a remote container dynamically, you must append the remoteEntry.js script to the DOM, initialize the remote container, and resolve the federated module via standard JavaScript Promises.

1. Dynamic Script Loader

Create a helper function that injects the remote script tag into the document head:

function loadScript(url) {
  return new Promise((resolve, reject) => {
    const existingScript = document.querySelector(`script[src="${url}"]`);
    if (existingScript) {
      resolve();
      return;
    }

    const script = document.createElement('script');
    script.src = url;
    script.type = 'text/javascript';
    script.async = true;

    script.onload = () => resolve();
    script.onerror = () => reject(new Error(`Failed to load script: ${url}`));

    document.head.appendChild(script);
  });
}

2. Container Initializer and Module Resolver

Once the script has executed, access the global variable exposed by the remote container, initialize its shared scope, and request the exposed module:

async function loadDynamicRemote({ url, scope, module }) {
  // Step 1: Load the remote script
  await loadScript(url);

  // Step 2: Initialize Webpack's shared scope
  await __webpack_init_sharing__('default');

  // Step 3: Access the container attached to the window object
  const container = window[scope];
  if (!container) {
    throw new Error(`Container '${scope}' not found on window.`);
  }

  // Step 4: Initialize the container with the host's shared scope
  await container.init(__webpack_share_scopes__.default);

  // Step 5: Extract the federated module
  const factory = await container.get(module);
  return factory();
}

Consuming Dynamic Modules in Applications

You can consume these dynamic modules directly using async workflows or integrate them natively into framework components.

React Implementation

For React applications, combine the loader with React.lazy to mount components dynamically:

import React, { lazy, Suspense } from 'react';

function DynamicRemoteComponent({ url, scope, module }) {
  const Component = lazy(() => loadDynamicRemote({ url, scope, module }));

  return (
    <Suspense fallback={<div>Loading remote component...</div>}>
      <Component />
    </Suspense>
  );
}

// Usage
export default function App() {
  return (
    <div>
      <h1>Host Application</h1>
      <DynamicRemoteComponent
        url="https://cdn.example.com/analytics/remoteEntry.js"
        scope="analyticsApp"
        module="./Widget"
      />
    </div>
  );
}

Key Considerations for Runtime Federation

  • Error Handling: Network interruptions or missing remote entries will trigger standard promise rejections. Implement robust error boundaries or fallback states to prevent application crashes.
  • Shared Scope Race Conditions: __webpack_init_sharing__('default') caches its initialization promise, making it safe to execute multiple times across concurrent component loads.
  • Idempotency: Webpack containers throw an error if .init() is called more than once on the same container. In production implementations, store loaded container states in a local cache to avoid re-initialization.
