How to Invalidate Webpack Persistent Cache in Plugins

Webpack 5 introduced persistent filesystem caching to dramatically accelerate repeated build times, but plugins that rely on external files, environment configurations, or custom transformations risk serving stale code if these assets change. To prevent incorrect builds, plugins must formally declare their external resources as build dependencies to trigger safe, automatic cache invalidation. This guide explains how custom Webpack plugins can hook into the compilation lifecycle to register build dependencies and invalidate persistent caches reliably.

Build Dependencies vs. File Dependencies

Webpack distinguishes between two primary types of dependencies during execution:

  • File Dependencies (compilation.fileDependencies): Monitored during watch mode (--watch). Changes to these files trigger an incremental recompilation of affected modules without purging the entire cache snapshot.
  • Build Dependencies (compilation.buildDependencies): Determine the validity of the persistent cache itself. If any file in this collection changes, Webpack invalidates the cached filesystem snapshot, discarding stale artifacts and executing a clean build.

Plugins that load external configuration files, generate global styles, or inject runtime scripts should register those source files as build dependencies.

Accessing and Adding to compilation.buildDependencies

The most direct way a plugin can invalidate the persistent cache is by hooking into the thisCompilation event and populating the buildDependencies collection with absolute paths.

compilation.buildDependencies is a Set<string>. You can append absolute file paths directly to this set:

const path = require('path');

class CustomConfigPlugin {
  constructor(options = {}) {
    this.configPath = path.resolve(options.configFile || 'custom.config.json');
  }

  apply(compiler) {
    compiler.hooks.thisCompilation.tap('CustomConfigPlugin', (compilation) => {
      // Register the file as a build dependency
      compilation.buildDependencies.add(this.configPath);
    });
  }
}

module.exports = CustomConfigPlugin;

When Webpack writes the cache snapshot to disk at the end of the build, it computes a hash of every path stored in buildDependencies. On subsequent executions, Webpack checks the timestamps and hashes of these registered files before resolving items from the cache.

Modifying compiler.options.cache.buildDependencies

If a plugin needs to register dependencies before the compilation lifecycle begins, it can safely modify the compiler configuration inside its apply method:

const path = require('path');

class DependencyInjectorPlugin {
  apply(compiler) {
    const cacheOptions = compiler.options.cache;

    // Only mutate if filesystem caching is active
    if (cacheOptions && cacheOptions.type === 'filesystem') {
      cacheOptions.buildDependencies = cacheOptions.buildDependencies || {};
      cacheOptions.buildDependencies.myPluginConfig = [
        path.resolve(__dirname, 'plugin-rules.json'),
        path.resolve(process.cwd(), 'external-schema.gql'),
      ];
    }
  }
}

module.exports = DependencyInjectorPlugin;

This approach mirrors user-level definitions typically declared inside webpack.config.js under cache.buildDependencies.config.

Invalidating Caches with Dynamic Values Using cache.version

Sometimes plugin behavior depends on values that are not stored in static files, such as environment variables, API responses, or package versions. In these scenarios, registering a file path is impractical. Instead, append a composite hash or string directly to compiler.options.cache.version:

class EnvCacheBusterPlugin {
  constructor(envFlags) {
    this.envFlags = envFlags;
  }

  apply(compiler) {
    if (compiler.options.cache && compiler.options.cache.type === 'filesystem') {
      const serializedFlags = JSON.stringify(this.envFlags);
      compiler.options.cache.version = `${compiler.options.cache.version || ''}_${serializedFlags}`;
    }
  }
}

module.exports = EnvCacheBusterPlugin;

Any modification to cache.version forces Webpack to invalidate all filesystem caches across the entire build.

Best Practices for Plugin Cache Safety

  1. Always Use Absolute Paths: Webpack requires absolute system paths in buildDependencies. Relative paths will cause snapshot resolution failures.
  2. Watch Plugin Dependencies: If your plugin itself relies on internal definitions that can change during development, add __filename or the plugin’s package.json to buildDependencies.
  3. Avoid Dynamic Salts: Never inject non-deterministic values (such as Date.now() or random strings) into cache.version or buildDependencies, as this renders persistent caching ineffective by destroying the cache on every run.
