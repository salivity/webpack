How react-server-dom-webpack Bundles RSC in Webpack

react-server-dom-webpack is the official integration layer that enables React Server Components (RSC) to function within Webpack's module bundling system. It bridges the gap between server-side execution and client-side hydration by splitting compilation into distinct graphs, generating reference manifests, and providing the serialization protocol needed to stream server-rendered component trees to the browser without duplicating code.

Dual-Graph Compilation

React Server Components require two distinct runtime environments: a server environment that executes server logic and accesses backend resources, and a client environment that runs interactive UI code in the browser.

Webpack natively resolves dependencies in a single traversal, but react-server-dom-webpack introduces configuration hooks that allow Webpack to maintain two separate dependency graphs:

  1. The Server Graph: Includes Server Components, backend utilities, and database drivers.
  2. The Client Graph: Includes interactive Client Components, browser-specific libraries, and client-side state hooks.

Handling Component Boundaries with Directives

When bundling, the react-server-dom-webpack Webpack plugin scans modules for boundary directives, primarily 'use client':

  • Client Reference Generation: When a Server Component imports a file marked with 'use client', the plugin intercepts the import on the server. Instead of bundling the client component's full implementation into the server bundle, it replaces the component with a lightweight "Client Reference" proxy object.
  • Manifest Creation: The plugin generates a client manifest JSON file during the client build. This manifest maps each Client Component’s file path and exported symbol to its corresponding Webpack module ID, chunk ID, and output asset URL.

The Flight Protocol and Serialization

At runtime, the server-side portion of the package (react-server-dom-webpack/server) renders the React tree into an intermediate, streamable format known internally as the "Flight" format.

Because standard JSON cannot serialize functions, promises, or React element structures natively:

  • Server Components are executed and rendered down to pure HTML-like UI descriptions.
  • Client Components are serialized as metadata references pointing to the module ID and chunk file defined in the manifest.
  • Props passed from Server Components to Client Components are serialized, preserving types like typed arrays and Promises.

This stream is progressively flushed to the client over HTTP as chunks resolve.

Deserialization and Hydration in the Browser

On the client side, react-server-dom-webpack/client consumes the incoming Flight stream:

  1. Chunk Loading: As the stream is parsed, the runtime encounters Client Reference tokens. It reads the module ID and dynamically instructs Webpack’s runtime (__webpack_require__ or import()) to fetch and execute the necessary client JavaScript bundles.
  2. Tree Reconstruction: The deserializer substitutes the server placeholders with the dynamically loaded Client Components and injects the serialized props.
  3. Seamless Hydration: React reconstitutes the complete virtual DOM tree on the client, preserving server-rendered content while attaching event listeners only to the interactive Client Components.
