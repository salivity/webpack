Babel useBuiltIns: usage vs entry Explained

When configuring modern JavaScript compilation with Webpack and @babel/preset-env, the useBuiltIns option determines how polyfills from core-js are integrated into your bundle. Setting useBuiltIns: 'entry' replaces direct global imports of core-js with individual imports targeting your specified browser environments, regardless of whether your code actually uses those features. In contrast, useBuiltIns: 'usage' analyzes each file individually and injects only the specific polyfills required by the actual code you wrote, optimizing for the smallest possible bundle size.

What is useBuiltIns?

@babel/preset-env uses useBuiltIns to manage browser polyfills through the core-js library. Without this setting (or when set to false), Babel will transform modern JavaScript syntax (such as arrow functions or optional chaining) into older syntax, but it will not polyfill missing global objects or methods (such as Promise, Map, or Array.prototype.includes).

To add polyfills, useBuiltIns must be set to either 'entry' or 'usage'.

useBuiltIns: 'entry'

With 'entry', you must manually import core-js at the root entry point of your application:

// index.js (Application entry)
import "core-js/stable";
import "regenerator-runtime/runtime";

How It Works

When Babel encounters this import, it evaluates your targets (like your Browserslist config) and replaces the single import with individual polyfill imports for every feature your targeted browsers lack.

Characteristics

  • Target-driven: Polyfills are added based purely on what your target browsers do not support natively.
  • Larger bundle size: It includes polyfills for all unsupported features in your target environments, even if your application never uses those APIs.
  • Safer for third-party libraries: Because all required polyfills are loaded upfront in the global scope, any node_modules dependencies requiring older polyfills will work correctly, even if Babel does not transpile them.

useBuiltIns: 'usage'

With 'usage', you do not import core-js manually in your application files. Babel handles the polyfill imports automatically.

How It Works

Babel inspects every individual file it processes. If it finds a modern API usage (such as [].includes() or new Set()) that is unsupported by your target browsers, it automatically adds the specific core-js import at the top of that specific file.

// Your source code
const exists = list.includes("item");

// Babel output (conceptually)
import "core-js/modules/es.array.includes.js";
const exists = list.includes("item");

Characteristics

  • Usage-driven: Polyfills are added strictly based on the intersection of what your code uses and what your targets need.
  • Optimal bundle size: Unused APIs are never polyfilled, keeping your production bundle as small as possible.
  • Dependency risk: Babel usually ignores node_modules by default in Webpack configurations. If an external package relies on an API that your application code does not use, Babel will not inject the polyfill for it, potentially leading to runtime errors in older browsers unless you explicitly transpile that package.

Key Differences Summary

Feature useBuiltIns: 'entry' useBuiltIns: 'usage'
Manual Import Required Yes (import "core-js/stable") No
Polyfill Inclusion Logic Targets-based (browser list) Code-based (actual usage)
Bundle Size Larger Minimal
Third-Party Safety High (polyfills globals upfront) Lower (misses uncompiled dependencies)
Configuration Complexity Simple Requires attention to dependency transpilation

Choosing the Right Option

Choose useBuiltIns: 'usage' if your priority is minimal bundle size and you have standard application code with well-maintained, pre-transpiled dependencies.

Choose useBuiltIns: 'entry' if you target older environments and experience runtime issues with untranspiled third-party packages, or if you prefer a predictable, fail-safe environment where all missing standard features are polyfilled globally.
