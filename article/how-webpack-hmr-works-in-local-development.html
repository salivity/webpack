How Webpack HMR Works in Local Development

Hot Module Replacement (HMR) is a Webpack feature that updates modules in a running application without requiring a full browser refresh. By exchanging, adding, or removing modules on the fly, HMR significantly speeds up the local development feedback loop while preserving application state, such as form inputs or UI toggles. Understanding how Webpack orchestrates HMR involves looking at the interplay between the Webpack compiler, the development server, a WebSocket connection, and the client-side runtime.

1. The Core Architecture

During local development, HMR relies on several key components:

  • Webpack Compiler: Watches the project files for modifications and compiles delta updates rather than rebuilding the entire bundle.
  • Webpack Dev Server (WDS): Serves the assets in memory and maintains a persistent communication channel (via WebSockets or Server-Sent Events) with the browser.
  • HMR Runtime: A small runtime library injected directly into the client bundle that listens for update events and applies incoming code changes.

2. Detecting Changes and Compiling Deltas

When a developer edits and saves a source file, Webpack's file watcher triggers a partial compilation:

  1. Change Detection: The compiler identifies which specific module was altered.
  2. Manifest Generation: Webpack generates two primary artifacts:
    • An HMR Manifest (JSON file) containing the new compilation hash and a list of updated chunk IDs.
    • One or more HMR Chunks (JavaScript files) containing the updated code for only the affected modules.
  3. Memory Storage: These files are retained in memory via memfs rather than written to disk, ensuring near-instant access.

3. Communicating with the Client

Once compilation finishes, the development server broadcasts an update message across the active WebSocket connection to the browser:

  • The server sends an invalid message when compilation starts, followed by a hash message containing the new build hash.
  • Finally, it emits an ok message indicating that the new assets are ready to be fetched.

4. Fetching the Update

When the HMR runtime inside the browser receives the notification:

  1. Requesting the Manifest: The runtime sends an HTTP request for the update manifest ([hash].hot-update.json).
  2. Requesting the Chunks: If the manifest contains module changes, the runtime downloads the corresponding delta chunks ([id].[hash].hot-update.js) via standard JSONP or fetch/script injection.

5. Applying Module Updates (Bubble and Accept)

Once the new module code arrives, the HMR runtime attempts to apply it using the module graph:

  • Opt-in Mechanism: Modules must explicitly declare support for HMR using the module.hot.accept() API. Framework integrations (like React Fast Refresh or Vue Loader) inject these handlers automatically under the hood.
  • Bubbling: If the changed module does not have a module.hot.accept() handler, the runtime bubbles the update up to its parent module in the dependency graph. This search continues upward until a parent module accepts the update.
  • Replacement: When an acceptance handler is found, the old module is flagged for disposal via module.hot.dispose(), allowing cleanup logic (such as clearing event listeners or timers) to execute. The new code then replaces the old module in the internal cache, and the acceptance callback runs to re-render the affected component.
  • Fallback to Reload: If the update bubbles all the way to the root entry file without finding an accepting module, the runtime aborts the hot replacement and triggers a full browser reload to ensure the application does not run in an inconsistent state.
