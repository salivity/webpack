Webpack ModuleFederationPlugin Configuration Guide

This article provides an overview of Webpack's container.ModuleFederationPlugin, detailing its purpose in modern JavaScript development and breaking down its core configuration options. You will learn how this plugin enables micro-frontend architectures through runtime code sharing, along with how to configure settings such as name, filename, exposes, remotes, and shared to orchestrate distributed applications effectively.

What is container.ModuleFederationPlugin?

container.ModuleFederationPlugin is a built-in feature introduced in Webpack 5 that allows multiple separate Webpack builds to work together seamlessly at runtime. Often referred to simply as Module Federation, it serves as an architectural foundation for micro-frontends.

Unlike traditional package-based sharing—where shared code must be built, published to a registry (like npm), and re-bundled by the host application—Module Federation dynamically loads code from independent deployments over the network. Applications can act as "hosts" (consuming external code), "remotes" (exposing code to others), or both simultaneously (bi-directional sharing), without needing to rebuild or redeploy the consuming systems.

Core Configuration Options

To use the plugin, import it from Webpack and include it in the plugins array of your webpack.config.js:

const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      // configuration options go here
    }),
  ],
};

The plugin relies on several critical configuration properties to manage how components and modules are exposed, consumed, and shared.

1. name

  • Type: string
  • Description: Defines the unique identity of the current container. When other applications import from this build, they will reference this name. The name is also exposed as a global variable in the browser runtime (unless another library target is defined).

2. filename

  • Type: string (Optional for pure host applications)
  • Description: Specifies the output file name for the remote entry manifest (commonly remoteEntry.js). This entry file contains the manifest of exposed modules and metadata required by host applications to resolve dependencies at runtime.

3. exposes

  • Type: object
  • Description: Defines the list of modules that this container makes available to external applications. The keys represent the path or alias by which the host will request the module, and the values point to the local file path.
exposes: {
  './Button': './src/components/Button.jsx',
  './Navigation': './src/components/Navigation.jsx',
}

4. remotes

  • Type: object
  • Description: Defines the external containers that this application consumes. The key represents the local alias used in your import statements, and the value defines the remote container's global scope name and the URL of its remoteEntry.js file.
remotes: {
  authApp: 'authApp@https://auth.example.com/remoteEntry.js',
  dashboardApp: 'dashboardApp@https://dashboard.example.com/remoteEntry.js',
}

With this configuration, your application can consume components using standard dynamic or static imports:

import RemoteButton from 'authApp/Button';

5. shared

  • Type: array | object
  • Description: Configures libraries and dependencies that should be shared across the host and remotes to prevent users from downloading duplicate vendor code (e.g., React, Lodash).

The shared property can be configured as a simple list of package names or as an object with advanced controls:

  • singleton (boolean): Ensures that only one instance of the shared library is loaded across all containers. This is essential for libraries that rely on a single global state, such as react or react-dom.
  • requiredVersion (string): Sets the semver version requirement. It usually references your package.json dependencies (e.g., dependencies['react']).
  • strictVersion (boolean): When set to true, Webpack rejects the shared module if the version does not strictly match requiredVersion, instead of falling back to loading a local copy.
  • eager (boolean): When true, forces the shared module to be included directly in the initial chunk rather than loaded asynchronously. This is rarely needed and can disable code-splitting benefits, but it is useful for specific bootstrap entry strategies.
shared: {
  react: {
    singleton: true,
    requiredVersion: '^18.2.0',
  },
  'react-dom': {
    singleton: true,
    requiredVersion: '^18.2.0',
  },
}

Summary of Operation

When configured, container.ModuleFederationPlugin negotiates shared dependencies at runtime using the generated remoteEntry.js files. If a remote requires a version of a library that the host has already loaded, it reuses that instance. If the remote requires an unprovided or incompatible dependency, it fetches its own copy. This allows distinct development teams to deploy applications independently while maintaining shared runtime performance and modularity.
