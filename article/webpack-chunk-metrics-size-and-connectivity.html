Webpack Chunk Metrics: Size and Connectivity

Webpack’s compilation statistics provide low-level visibility into how an application is bundled, split, and distributed across distinct assets. Within the compilation object, chunk metadata reveals crucial operational information, including total payload weights and the structural graph tying chunks to one another. This guide examines the specific properties inside stats.compilation.chunks that expose raw chunk size and describe chunk connectivity.

Metrics Revealing Chunk Size

Evaluating chunk size directly from the compilation object requires inspecting properties that reflect both aggregate module weights and individual asset types.

  • size / chunk.size(): In the serialized stats output, the size property represents the total estimated byte size of the chunk based on all enclosed modules. Programmatically on the raw Chunk instance in the compilation, calling chunk.size(options) or querying compilation.chunkGraph.getChunkSize(chunk) returns this numeric byte count.
  • sizes / chunk.sizes: Webpack splits module footprints by source type (such as JavaScript, CSS, or WebAssembly). The sizes property maps each distinct type to its respective byte length (e.g., { javascript: 142050, css: 12400 }), offering a granular breakdown rather than an undifferentiated total.

Metrics Revealing Chunk Connectivity

Connectivity refers to the parent-child-sibling relationships formed through dynamic imports, runtime splits, and multi-entry configurations. Several properties inside the chunk data expose these relationships:

  • parents: Identifies chunk IDs that must be loaded prior to the current chunk or that dynamically triggered the creation of the current chunk via an asynchronous split point (e.g., import()).
  • children: Lists chunk IDs spawned directly by dynamic boundaries located inside the current chunk's modules.
  • siblings: Denotes chunks that share the same parent chunk or entry point and are typically loaded in parallel.
  • origins: An array of records highlighting the origin of the chunk. Each origin entry contains references to the originating module, the source location (line and column), the AST expression that triggered the split, and the associated chunk name.
  • _groups / groups: Chunks belong to one or more ChunkGroup objects (such as Entrypoint). Inspecting the chunk's groups links to the ChunkGroup graph, which exposes parentsIterable and childrenIterable in the raw compilation graph to trace how different routes connect at runtime.
  • modules / chunkGraph.getChunkModules: While not directly listing other chunks, inspecting the underlying module list reveals shared modules across chunks, pinpointing overlap and deduplication opportunities between split bundles.
