Understanding Webpack watchOptions.poll in Docker

Webpack's watchOptions.poll setting provides an alternative file-watching mechanism that repeatedly checks the file system for modifications instead of relying on native operating system events. This configuration is critical when developing inside containerized or virtualized setups—such as Docker or network-mounted file systems—where standard operating system file-change notifications often fail to propagate to the container, preventing automatic rebuilds during active development.

What is watchOptions.poll?

By default, Webpack relies on native operating system file system notifications (such as inotify on Linux or FSEvents on macOS) to detect when a file has been created, modified, or deleted. This event-driven approach is efficient because it consumes virtually no CPU resources while idling.

When watchOptions.poll is enabled, Webpack bypasses or supplements native events by actively polling files at a designated interval to see if their timestamps or contents have changed.

You can configure it in your webpack.config.js file:

module.exports = {
  // ...
  watchOptions: {
    poll: 1000, // Check for changes every 1000 milliseconds (1 second)
    aggregateTimeout: 300, // Delay rebuild after first change (in ms)
    ignored: /node_modules/, // Exclude heavy directories from polling
  },
};

You can set poll to a boolean (true, which defaults to checking every 5007 milliseconds) or an integer representing the polling interval in milliseconds.

When is watchOptions.poll Necessary?

Native file system notifications rely on OS-level hooks. When virtualization boundaries or network protocols intercept these actions, events are frequently lost. Polling is necessary in the following scenarios:

1. Docker with Bind Mounts

When running Webpack inside a Docker container while editing source code on the host machine (macOS or Windows), the host shares files with the Linux container via a bind mount. Virtualization bridges (such as VirtioFS, gRPC FUSE, or WSL2 cross-OS mounts) frequently fail to forward native file-system change events into the container's Linux kernel. Because the containerized Linux kernel never receives the inotify signal, Webpack never triggers a rebuild unless polling is active.

2. Network File Systems (NFS, Samba, CIFS, Vagrant)

If your source code is hosted on a remote server, shared network folder, or managed within a Vagrant virtual machine using synced folders, standard file-change notifications are generally not transmitted over the network protocol. Polling ensures the guest environment detects changes made by host editors.

3. Inotify Watch Limit Exhaustion

On Linux systems, the kernel limits how many files a user can monitor via fs.inotify.max_user_watches. If a large project exceeds this limit and modifying system-level sysctl configurations is not permitted (such as in restricted shared hosting or certain CI/CD environments), watchOptions.poll circumvents the limit entirely.

Performance Considerations

Because polling continuously queries file statuses, it is far more CPU- and battery-intensive than event-driven file watching. When using watchOptions.poll:

  • Always ignore unnecessary folders: Exclude node_modules, build artifacts (dist, build), and .git folders using the ignored property so Webpack only polls your actual source files.
  • Tune the interval: Avoid extremely low polling values (like 100ms), which cause severe CPU spikes on larger repositories. An interval between 1000ms and 2000ms typically offers a good balance between responsiveness and system resource usage.
