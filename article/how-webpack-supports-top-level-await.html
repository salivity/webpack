How Webpack Supports Top-Level Await

This article provides an overview of how Webpack implements Top-Level Await through its experimental configuration flag. It covers how Webpack classifies modules with top-level await expressions, transforms synchronous dependency graphs into asynchronous execution chains, and manages runtime Promise orchestration across output bundles.

Enabling Top-Level Await

Top-Level Await allows developers to use the await keyword outside of async functions at the root level of a module. In Webpack 5, this capability is activated via the experiments configuration option:

// webpack.config.js
module.exports = {
  experiments: {
    topLevelAwait: true,
  },
};

While enabled by default in recent Webpack 5 minor releases when targeting modern environments, setting this flag explicitly instructs the Webpack parser and compiler to treat top-level await statements as valid syntax rather than throwing a build-time parsing error.

Asynchronous Module Classification

When Webpack parses an ECMAScript module (ESM) and encounters a root-level await, it automatically marks that module as an Async Module.

In standard Webpack bundling, modules execute synchronously during the initial evaluation phase. When a module is classified as asynchronous, Webpack fundamentally changes how that module's code is wrapped inside the bundle:

  1. Promise Wrapping: The module’s execution body is wrapped in an internal runtime structure that returns a Promise.
  2. Export Deferral: Exports from the module are not immediately available until the returned Promise resolves.

Dependency Graph Propagation

Top-Level Await is "contagious" across the dependency graph. When Module A imports Module B, and Module B contains a top-level await, Module A also becomes an asynchronous module by extension.

Webpack handles this propagation during the compilation phase:

  • Graph Analysis: Webpack traces all static imports back to the module containing the await.
  • Execution Ordering: Webpack builds a topological execution order ensuring that child dependencies start evaluating and resolving their top-level Promises before parent modules attempt to access their exports.
  • Sibling Parallelism: Independent async modules are executed concurrently using standard JavaScript microtask queues, preventing unnecessary blocking of unrelated code paths.

Runtime Orchestration

To support this behavior in environments that do not natively execute ESM, Webpack injects specialized runtime helpers.

Instead of calling the standard synchronous execution function, the runtime uses a helper (commonly referenced internally as __webpack_require__.a). This helper:

  • Collects the promises returned by all asynchronous dependencies of a module.
  • Uses Promise.all internally to wait for those dependencies to resolve.
  • Catches errors in asynchronous modules and forwards them down the execution chain, rejecting the parent module's promise appropriately.

Target Output and Module Formats

Webpack's handling of Top-Level Await varies depending on the target and output.module settings:

  • ESM Output (output.module: true): Webpack emits modern ES modules where the browser or runtime engine handles the top-level await natively.
  • Non-ESM Targets (CommonJS, traditional Webpack bundles): Webpack converts the entire chunk into a Promise-based initialization process. In these environments, you cannot statically require() an async module; it must instead be loaded dynamically using import().
