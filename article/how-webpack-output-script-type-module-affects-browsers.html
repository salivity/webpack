How Webpack output.scriptType module Affects Browsers

Setting output.scriptType = 'module' in Webpack configures the build system to treat output scripts as native ECMAScript Modules (ESM). This setting changes how browsers load and execute JavaScript bundles by altering the injected HTML script tags, enforcing implicit deferred execution, applying strict mode by default, strictly enforcing CORS rules, and isolating the global execution scope.

Native <script type="module"> Tag Injection

When output.scriptType is set to 'module', plugins like HtmlWebpackPlugin generate script tags with the type="module" attribute instead of the default classic <script> format. This instructs modern browsers to parse and run the bundle using their native ES module loaders rather than standard global script pipelines.

Implicit Deferred Execution

Standard <script> tags halt HTML parsing while the script is downloaded and executed, unless explicitly modified with async or defer. Modules behave differently:

  • Automatic Deferral: Browsers automatically treat all module scripts as deferred. The browser downloads the bundle in parallel with HTML parsing.
  • Execution Timing: The script only executes after the document has finished parsing, immediately before the DOMContentLoaded event fires. This eliminates parser-blocking behavior without requiring an explicit defer attribute.

Automatic Strict Mode

Classic scripts execute in "sloppy mode" unless an explicit "use strict"; directive is placed at the top of the file or function. Browsers automatically execute native ES modules in strict mode. This enforces stricter parsing rules, such as:

  • Disallowing the accidental creation of global variables.
  • Throwing errors on invalid assignments to non-writable properties.
  • Setting this to undefined at the top-level scope instead of referencing the window object.

Strict CORS Requirements

Classic scripts can be fetched from external domains without CORS headers unless the crossorigin attribute is present. ES modules, however, are subject to mandatory Cross-Origin Resource Sharing (CORS) enforcement:

  • Any bundle served from a different origin, domain, or port must include appropriate headers, such as Access-Control-Allow-Origin.
  • ES modules cannot be loaded directly from the local filesystem using the file:// protocol in most browsers; they must be served over http:// or https://.

Lexical Scoping and Global Isolation

In a classic script, variables and functions declared at the top level automatically become properties of the global window object. With native ES module execution:

  • Every file has its own lexical module scope.
  • Top-level declarations (const, let, var, function) remain scoped exclusively to the module itself.
  • Nothing leaks into the global namespace unless it is explicitly attached to window.

Execution Deduplication

When a browser encounters multiple references to the same script URL, a classic script downloads and executes multiple times. With native modules, the browser caches the module definition and guarantees that any given module URL will only be evaluated once per page lifecycle, regardless of how many times it is imported or referenced.
