Webpack Multi-Compiler Dependencies Explained

In Webpack, a multi-compiler configuration allows developers to define and run multiple independent build configurations simultaneously within a single build process. The dependencies property in this setup explicitly controls the execution order between these compilers, ensuring that designated builds do not execute until their prerequisite compilers have successfully completed. This article explains how the dependencies array functions, why it is necessary for shared assets, and how it prevents race conditions in complex build environments.

The Challenge of Default Parallel Execution

When you export an array of configuration objects in a webpack.config.js file, Webpack activates its MultiCompiler mode. By default, Webpack attempts to execute these builds concurrently to optimize build speed.

While parallel execution works well for truly isolated builds—such as compiling localized bundles for different languages—it fails when one build relies on the output of another. Without a defined order, tasks execute unpredictably, causing dependent builds to fail or bundle outdated files.

The Role of the dependencies Option

The primary purpose of the dependencies property is to enforce a sequential dependency graph across your multi-compiler targets. By providing an array of compiler names that a specific configuration relies on, Webpack creates a topological sort to schedule the builds.

A compiler with dependencies will remain idle until all configurations listed in its dependencies array finish emitting their assets.

Key Use Cases

1. Manifest and Metadata Generation

A common scenario is a Server-Side Rendering (SSR) setup involving a client compiler and a server compiler. The server configuration often requires a client-generated manifest (such as manifest.json or loadable-stats.json) to map dynamic chunks to HTML script tags. Setting the client compiler as a dependency for the server compiler guarantees that the manifest exists on the file system before the server bundle begins compiling.

2. Micro-Frontends and Shared DLLs

When using Module Federation or DLL plugins, a core library or shared shell must compile first so that downstream micro-apps or consumers can validate and reference the exposed remote containers or vendor manifests.

3. Service Workers and Pre-caching

Service workers need an accurate list of all emitted production assets to cache them for offline use. By setting the service worker build to depend on the main application build, the service worker compiler can inspect the final build directory and generate an accurate cache manifest without race conditions.

How to Implement Dependencies

To use this feature, each configuration object must have a unique name property. The dependent configuration then references this name in its dependencies array:

module.exports = [
  {
    name: 'client',
    entry: './src/client.js',
    output: {
      path: path.resolve(__dirname, 'dist/client'),
      filename: '[name].[contenthash].js',
    },
    // Plugins generating manifests run here
  },
  {
    name: 'server',
    dependencies: ['client'],
    entry: './src/server.js',
    output: {
      path: path.resolve(__dirname, 'dist/server'),
      filename: 'server.js',
    },
    // Reads client build assets safely
  },
];

Behavior in Watch Mode

In development or watch mode, the dependencies field continues to regulate the build pipeline. If a file in the prerequisite build changes, Webpack re-compiles that compiler first. Once that build completes, Webpack triggers a re-compilation of the dependent compiler, maintaining synchronization across code changes automatically.
