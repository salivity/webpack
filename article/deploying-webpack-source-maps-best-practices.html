Deploying Webpack Source Maps: Best Practices

Webpack source maps are critical for translating minified, bundled production code back into readable source code for debugging, but leaving them publicly accessible exposes proprietary logic, internal APIs, and architectural vulnerabilities. This guide outlines the recommended Webpack configuration types, file permissions, web server access controls, and deployment strategies needed to secure source maps in production environments.

1. Webpack Configuration for Production

The first step in securing source maps is generating them without publicly announcing their location in your client-side bundles.

  • hidden-source-map: Generates standard .map files but omits the //# sourceMappingURL= comment from the bundled JavaScript files. This prevents browsers from automatically fetching source maps, while still allowing error-monitoring services (like Sentry, Datadog, or Bugsnag) to map stack traces if the files are uploaded directly.
  • nosources-source-map: Generates source maps that map lines and columns back to original filenames without including the original source code content inside the map.
  • Avoid eval or inline options: Options like eval-source-map or inline-source-map embed source maps directly into the production code, instantly exposing your original source files to anyone using browser developer tools.
// webpack.config.js
module.exports = {
  mode: 'production',
  devtool: 'hidden-source-map',
  // ... other configurations
};

2. File System Permissions

If source maps are deployed alongside your static assets on a Linux/Unix server, adhere to the principle of least privilege:

  • File Permissions: Set .map files to standard secure read permissions (e.g., chmod 640 or chmod 644). The files should be owned by the deployment user and readable by the web server process (e.g., www-data or nginx).
  • Directory Permissions: Ensure directories containing assets have standard directory execution and read permissions (e.g., chmod 755).
  • File permissions alone will not prevent external users from accessing files if the web server is configured to serve them; access must be restricted at the web server or network layer.

3. Web Server Access Controls

If source map files must reside on the same server as production bundles, explicitly block public HTTP access to them.

Nginx

Block all requests ending in .map or restrict access to an internal corporate network:

# Deny all external access to .map files
location ~* \.map$ {
    deny all;
    return 404;
}

# Alternatively: Allow only internal IPs / VPN
location ~* \.map$ {
    allow 192.168.1.0/24;
    deny all;
}

Apache

Add a rule in your .htaccess or virtual host configuration:

<FilesMatch "\.map$">
    Require all denied
</FilesMatch>

4. Recommended Deployment Workflows

The most secure deployment approach is to prevent source maps from ever reaching public web servers or CDNs.

Option A: Upload to Error Monitoring and Discard

  1. Build the production application using hidden-source-map.

  2. Use CI/CD plugins (such as Sentry Webpack Plugin or Datadog CLI) to upload the generated .map files directly to your error-tracking platform.

  3. Run a build step to delete all .map files before uploading the static assets to your public web server, S3 bucket, or CDN:

    find ./dist -name "*.map" -type f -delete

Option B: Private Source Map Server

If internal developers need to debug live production environments using browser developer tools:

  1. Build assets using hidden-source-map so public users are not directed to any map URLs.
  2. Deploy .map files to an isolated, authenticated server accessible only via VPN or corporate SSO.
  3. Configure the browser’s developer tools to map resource URLs to the secure internal source map endpoint manually when debugging.
