Webpack HMR Failure: How Live Reloading Works

Hot Module Replacement (HMR) in Webpack accelerates development by updating modules in the browser without requiring a full page refresh. However, when an HMR update cannot be safely applied to a specific module or its dependency tree, Webpack aborts the hot replacement process and initiates a full page reload as a safety mechanism. This article explains how Webpack detects HMR failures through its bubbling mechanism, communicates with the development server, and executes live reloading as a fallback.

The Bubble Mechanism and HMR Acceptance

For HMR to work, a module or one of its parent modules must explicitly register that it can handle updates using module.hot.accept(). When a file changes, Webpack compiles a new manifest and a chunk containing the modified code.

The client runtime attempts to apply this update:

  1. If the modified module accepts itself via module.hot.accept(), the runtime executes the callback and replaces the module in memory.
  2. If the module does not accept itself, the update "bubbles" up to the parent modules that imported it.
  3. If a parent module accepts the update on behalf of the child, the parent re-evaluates and the update succeeds.
  4. If the update bubbles all the way to the application's root entry point without encountering an acceptance handler, the HMR runtime marks the update as unaccepted.

Transitioning from HMR Failure to Live Reload

When an update cannot be accepted, or if an uncaught runtime error occurs inside an acceptance callback, the HMR runtime transitions its internal state to abort or fail.

At this point, the integration between the Webpack client runtime and webpack-dev-server takes over:

  • Signal Transmission: The HMR runtime logs a warning to the browser console stating that the update could not be applied (e.g., [HMR] Cannot apply update... Need to do a full reload!).
  • Fallback Evaluation: webpack-dev-server checks its configuration to see if fallback reloading is permitted. By default, the liveReload option is set to true.
  • Browser Reload: Because the module state is now out of sync and cannot be safely patched in place, the runtime calls window.location.reload(). This re-fetches the entire bundle, resetting the application state and ensuring that the developer is not viewing a corrupted or partially updated interface.

Preventing Fallback with "Hot Only" Mode

In some debugging scenarios, developers prefer that Webpack does not automatically trigger a full reload when an update fails, as a reload clears console error logs and network history.

Webpack accommodates this through the server configuration:

  • Setting hot: true enables HMR with fallback to live reloading enabled.
  • Setting hot: 'only' enables HMR but explicitly blocks the automatic fallback to a full browser reload upon failure.

When hot: 'only' is configured and an update fails, Webpack halts the update process, displays the failure details in the browser console, and leaves the application running in its current state.
