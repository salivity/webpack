How Next.js Customizes Webpack for Hybrid Rendering

Next.js delivers its hybrid rendering model—spanning Server-Side Rendering (SSR), Static Site Generation (SSG), Incremental Static Regeneration (ISR), and React Server Components (RSC)—by heavily extending Webpack behind the scenes. Rather than using a single static bundling configuration, Next.js programmatically orchestrates multiple isolated Webpack compiler instances, implements modern module layering, and injects custom loaders and plugins. This architecture allows a single application codebase to be parsed into distinct environments, ensuring server-only code never reaches the browser while client-side hydration scripts are kept as lightweight as possible.

Multi-Compiler Architecture

The foundation of hybrid rendering in Next.js relies on running multiple Webpack compilers in parallel. Instead of a single build target, Next.js configures at least two primary compiler targets for every build:

  1. Client Compiler (target: 'web'): Produces the browser-executable bundles, static assets, and runtime scripts necessary for progressive enhancement and hydration.
  2. Server Compiler (target: 'node' or edge runtime): Compiles the application into server-executable modules responsible for pre-rendering HTML on request or during build time.

Because these compilers run simultaneously, Next.js can evaluate the exact same React components in both environments while emitting entirely different artifacts. The server build packages your application logic to render HTML strings, while the client build compiles only the JavaScript needed to attach event listeners and manage client-side state.

Webpack Layers and React Server Components

With the App Router and React Server Components, Next.js pioneered the use of Webpack's experimental module layers (experiments.layers). A standard bundler treats all imported modules as part of a single dependency graph. Next.js, however, bifurcates this graph into isolated layers within the same build:

  • Server Layer (rsc): Compiles components that execute purely on the server. These components can directly access databases, file systems, and internal microservices.
  • Client Layer (action / ssr / client): Compiles components marked with the 'use client' directive.

Webpack layers allow Next.js to intercept imports across the network boundary. When a Server Component imports a Client Component, a custom Next.js Webpack plugin replaces the component with a lightweight reference (a client manifest entry). On the client side, Webpack bundles the actual component code for hydration; on the server side, it bundles a placeholder that emits the necessary serialization payload.

Selective Code Elimination via Custom Loaders

To enable features like getStaticProps, getServerSideProps, and route handlers without bloating the client footprint, Next.js customizes Webpack’s loader pipeline.

Through custom Babel or SWC-based loaders (such as next-swc-loader), Next.js analyzes the Abstract Syntax Tree (AST) of page files. For client bundles, the loader automatically strips out server-specific functions, data-fetching logic, and server-only modules (like fs, path, or database clients).

If a module marked with server-only is imported into a client bundle graph, Next.js's Webpack configuration halts the build with an error, preventing accidental leaks of sensitive logic or environment variables to public-facing scripts.

Chunk Splitting and Hydration Manifests

Standard Webpack configurations typically optimize for long-term caching using general chunking strategies. Next.js heavily modifies SplitChunksPlugin to accommodate hybrid rendering mechanics:

  • Framework and Shared Chunks: Standard libraries like React and ReactDOM are segregated into persistent framework chunks that rarely change across deployments.
  • Per-Route Chunks: Each page or route segment is mapped to its own isolated Webpack entry point. Code-splitting occurs strictly at the route level to minimize the Initial Server Response and Time to Interactive (TTI).

During the build process, Next.js plugins listen to Webpack's compilation hooks and output several critical manifest files:

  • build-manifest.json: Maps routes to their required client-side Webpack chunks.
  • server-reference-manifest.json: Tracks Server Actions and entry points.
  • react-loadable-manifest.json: Tracks dynamic imports using next/dynamic.

During SSR or SSG, the server runtime reads these manifests to calculate the exact <script> and <link rel="preload"> tags to inject directly into the pre-rendered HTML. This guarantees the browser downloads only the JavaScript strictly required to hydrate the specific route being viewed.

Virtual Modules and Runtime Routing

Next.js bypasses standard Webpack file-resolution limits by creating dynamic entry points and virtual modules in memory. Instead of pointing Webpack to a single index.js, Next.js injects its own runtime framework—including the router, error boundaries, and hydration bootstrapper—around your components at the AST level.

By abstracting Webpack through these compiler hooks, Next.js allows developers to write straightforward React code that dynamically shifts execution between build-time generation, edge workers, Node.js servers, and client browsers without manual bundler intervention.
