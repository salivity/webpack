HMR in Webpack Module Federation Explained

Webpack Module Federation allows distinct builds to form a single application by dynamically loading code at runtime, but maintaining a seamless developer experience requires Hot Module Replacement (HMR) across application boundaries. This article details the underlying mechanics Webpack uses to handle hot reloading between host and remote containers, explains how updates propagate across independent development servers, and highlights the configurations necessary to enable frictionless live development across distributed frontends.

The Challenge of Distributed Development

In a standard single-page application, Webpack manages a single dependency graph where an embedded WebSocket client listens to the webpack-dev-server (WDS). When a file changes, the server compiles an update manifest and a chunk patch, which the runtime replaces in memory via HMR without triggering a full page refresh.

With Module Federation, this model is fragmented. The host application and each remote application operate with their own isolated Webpack build pipelines, independent entry points, and separate development servers running on different ports or domains. Because the host consumes remotes over network boundaries via remote entry scripts (such as remoteEntry.js), the primary challenge is establishing a communication channel that lets changes inside a remote trigger HMR events in the host.

Independent WebSocket Connections

Webpack does not route remote updates through the host’s development server. Instead, it relies on multi-client WebSocket connections.

When the host application loads a remote component, it also loads the runtime code associated with that remote. If the remote was built in development mode with HMR enabled, its runtime establishes its own WebSocket connection back to the remote’s specific webpack-dev-server.

When a developer modifies source code within a remote:

  1. The remote's development server detects the file change and recompiles only the affected module.
  2. The remote dev server broadcasts an update notification through its dedicated WebSocket connection.
  3. The remote runtime running inside the host’s browser tab receives the message.
  4. The remote runtime requests the HMR manifest (.hot-update.json) and the updated JavaScript chunk (.hot-update.js) directly from the remote’s origin.

Runtime Module Replacement Across Boundaries

Once the updated chunk is fetched from the remote server, Webpack’s runtime evaluates the patch inside the shared runtime environment:

  1. Module Scope Invalidation: The remote runtime marks the modified module as outdated within the remote container's internal module registry.
  2. Bubble Up Process: The HMR runtime bubbles the update up through the module’s import chain. If the boundary of change remains entirely within the remote's internal dependency tree and an import.meta.webpackHot.accept (or framework-specific tool like React Refresh) boundary accepts it, the component re-renders locally inside the host application.
  3. Host Boundary Handling: If the modified module is the entry point exposed directly to the host (the exposes configuration in Module Federation), the update bubbles up to the boundary where the host consumed the dynamic import (e.g., import('remoteApp/Component')). If the host handles dynamic updates or utilizes asynchronous component wrappers with error boundaries, the updated remote component is swapped in place. If no boundary catches the update, the browser falls back to a full window reload.

Essential Webpack Configuration for Remote HMR

For hot reload to function reliably across origins, several Webpack configuration options must be defined explicitly in both host and remote configurations:

1. Public Paths

The remote application must define a fully qualified publicPath rather than an automatic or relative path. This ensures that the remote HMR runtime requests hot update chunks from the remote's dev server rather than attempting to fetch them from the host's server origin.

// remote webpack.config.js
output: {
  publicPath: 'http://localhost:3001/',
}

2. Cross-Origin Resource Sharing (CORS)

Because the host application (running on one origin) fetches hot update manifests and chunk files from the remote dev server (running on another origin), the remote's dev server must allow cross-origin requests.

// remote webpack.config.js
devServer: {
  port: 3001,
  headers: {
    'Access-Control-Allow-Origin': '*',
  },
}

3. WebSocket Client Configuration

Modern versions of webpack-dev-server require configuring the client connection settings explicitly when consumed inside a different host domain. This prevents the remote's runtime from incorrectly attempting to connect to the host's WebSocket port.

// remote webpack.config.js
devServer: {
  client: {
    webSocketURL: 'ws://localhost:3001/ws',
  },
}

Shared Dependencies and HMR

Shared libraries (such as React, Vue, or state stores) defined under the shared key in the ModuleFederationPlugin introduce another layer of complexity.

Webpack reconciles shared dependencies using a shared scope object (__webpack_share_scopes__). If a remote attempts to hot-reload a module that relies on a singleton shared dependency provided by the host, the remote retains the reference to the host's shared instance. This prevents duplicate instances of stateful libraries from breaking the application during runtime patching, provided that version resolution constraints are satisfied.
