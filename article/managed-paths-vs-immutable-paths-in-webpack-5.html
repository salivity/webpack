managedPaths vs immutablePaths in Webpack 5

Webpack 5 uses cache snapshots to optimize build speeds by determining when files have changed and when cached artifacts can safely be reused. Two key configuration options governing this behavior are snapshot.managedPaths and snapshot.immutablePaths. This article explains the technical differences between these two options, how Webpack treats them during the build process, and when to use each to improve persistent caching performance.

Understanding Webpack 5 Snapshots

When Webpack builds an application with persistent caching enabled, it creates snapshots of file system states to verify if files were modified between builds. Creating snapshots for every single file inside large dependency trees is resource-intensive. To eliminate redundant file hashing and timestamp checks, Webpack allows you to classify dependency directories into managed paths or immutable paths.

What is snapshot.managedPaths?

The snapshot.managedPaths option specifies an array of paths that are managed exclusively by a package manager (such as npm, Yarn, or pnpm). By default, this is configured to include ['./node_modules'].

When a directory is marked as a managed path, Webpack makes the assumption that files inside are only modified when a package manager installs, updates, or deletes packages. Instead of tracking timestamps or calculating hashes for every individual file in these directories, Webpack only monitors the package's top-level metadata (such as the version and name fields inside package.json).

If the package.json version remains unchanged, Webpack assumes the package contents have not been modified. If you manually edit a file inside a managed path without altering the package's version number, Webpack will not detect the change unless you explicitly remove the path from managedPaths.

What is snapshot.immutablePaths?

The snapshot.immutablePaths option specifies an array of paths where the contents are strictly immutable and will never change over time. By default, this array is empty ([]).

Immutable paths represent the highest level of caching trust in Webpack. Unlike managed paths, Webpack does not even check the package.json file or package metadata for changes inside an immutable directory. Once a file in an immutable path is cached, Webpack permanently assumes it is up to date and skips all subsequent verification.

This configuration is primarily intended for package managers that use content-addressable storage or unique version-encoded directory structures, such as Yarn PnP (Plug'n'Play) cache directories or global npm/pnpm stores where files are strictly read-only and never modified in place.

Key Differences

Feature snapshot.managedPaths snapshot.immutablePaths
Default Value ['./node_modules'] []
Verification Level Tracks package metadata (package.json versions). Skips all checks entirely after initial snapshot.
Change Detection Detects updates if package version or dependencies change. Never detects updates; contents are assumed permanent.
Primary Use Case Standard node_modules folders. Content-addressable caches, Yarn PnP stores, or hashed file paths.
Overhead Minimal (reads package metadata). None (zero file system operations).

When to Use Which

Use snapshot.managedPaths for standard dependency directories like node_modules where packages might be updated in place via package manager commands. If you are developing local packages or using tools like npm link, you should exclude those specific directories from managedPaths so Webpack continues monitoring their files for real-time changes.

Use snapshot.immutablePaths only when you can guarantee that the directory path uniquely represents the exact content inside it, such that any update to the code would result in a completely different file path. Misconfiguring mutable code as immutable will prevent Webpack from ever seeing updates, leading to stale builds.
