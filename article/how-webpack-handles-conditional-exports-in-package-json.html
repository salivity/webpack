How Webpack Handles Conditional Exports in package.json

This article explores how Webpack 5 natively parses and resolves the exports field in modern package.json files. You will learn the mechanics behind Webpack's condition matching—such as differentiating between CommonJS and ES modules or browser and Node.js runtimes—how configuration settings like target affect these decisions, and how to customize condition resolution using the resolve.conditionNames option.

Understanding the exports Field

The exports field in package.json is a modern alternative to main, providing encapsulation and the ability to define conditional entry points based on the consumer's environment. A basic package structure looks like this:

{
  "name": "example-package",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.cjs"
    }
  }
}

When an external module executes import from 'example-package' or require('example-package'), modern bundlers and runtimes use these conditions to select the correct file.

Native Support in Webpack 5

Webpack 5 natively supports the Node.js exports specification out of the box (Webpack 4 required third-party plugins or experimental flags). When Webpack encounters an import or require statement pointing to a dependency, its internal resolver (enhanced-resolve) checks the package's exports field before falling back to module or main.

If an exports field exists:

  1. Subpath imports that are not explicitly defined in exports are blocked, preventing consumers from reaching internal files.
  2. Webpack matches the current build context against the keys provided in the conditions object.

How Webpack Matches Conditions

Webpack determines which export branch to load based on several factors:

1. Import Syntax (import vs. require)

Webpack checks how the file is imported in the source code:

  • An import statement or dynamic import() enables the import condition.
  • A CommonJS require() call enables the require condition.

2. Build Target (target)

The target specified in webpack.config.js dictates environmental conditions:

  • target: 'web' (or webworker) automatically enables the browser condition.
  • target: 'node' disables browser and matches Node-specific conditions where applicable.

3. Execution Context

Conditions such as production or development can be matched based on the active Webpack mode. The default condition acts as a catch-all and is matched when no other specific condition applies.

Evaluation Order

Order matters in conditional exports. Webpack follows the Node.js export resolution specification: conditions are evaluated in the order they are defined in package.json, not by specificity.

If a key like default or a broad condition appears before a narrower one like import, the earlier condition takes precedence if it matches the current environment.

Customizing Resolution via resolve.conditionNames

You can manually control which condition names Webpack evaluates by modifying the resolve.conditionNames array in your webpack.config.js.

By default, Webpack configures condition names based on your target and module type. You can extend or override this behavior to support custom flags (such as source, development, or custom runtime environments):

// webpack.config.js
module.exports = {
  // ...
  resolve: {
    // Webpack will match 'custom-condition' first, then 'import', then any defaults
    conditionNames: ['custom-condition', 'import', 'require', 'node']
  }
};

If you wish to maintain Webpack’s default condition list while prepending a custom condition, you can use the spread operator with ...:

// webpack.config.js
module.exports = {
  resolve: {
    conditionNames: ['custom-condition', '...']
  }
};

Disabling exports Field Resolution

If you need to bypass the exports field entirely—for instance, to support legacy packages with broken export maps—you can disable it globally in the resolver:

// webpack.config.js
module.exports = {
  resolve: {
    exportsFields: [] // Defaults to ['exports']
  }
};

Setting exportsFields to an empty array forces Webpack to resolve files using standard legacy fields like module and main.
