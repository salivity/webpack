How Webpack Resolves URLs in Nested Sass Imports

Webpack resolves asset URLs in deeply nested Sass imports by combining the Dart Sass compiler with a specialized loader pipeline—most notably sass-loader, resolve-url-loader, and css-loader. Because the Sass specification leaves url() statements untouched during compilation, paths written relative to an imported partial become broken once compiled to the root stylesheet. Webpack solves this problem by using source maps to trace the original file location of each asset declaration, recalculating relative paths before standard module resolution begins.

The Problem with Sass and Relative Paths

When using @import (or modern @use) statements across nested directories, Sass compiles all referenced stylesheets into a single CSS output. However, Sass does not alter the paths inside CSS url() functions.

If an entry file located at src/styles/main.scss imports a deeply nested partial at src/components/button/_button.scss, any asset reference such as url('./icon.png') inside _button.scss will be output verbatim as url('./icon.png'). When css-loader later inspects the compiled CSS to resolve modules, it treats ./icon.png as relative to main.scss rather than _button.scss, causing compilation to fail with a module not found error.

The Resolution Chain

To resolve these nested URLs correctly, Webpack relies on a multi-stage loader configuration executed from bottom to top:

  1. sass-loader with Source Maps Enabled: The process begins by passing the SCSS tree to sass-loader. For URL resolution to work across nested layers, sourceMap: true must be enabled. The Sass compiler compiles the SCSS into CSS and generates an inline or external source map that maps every declaration back to its original partial file.
  2. resolve-url-loader: This loader is placed immediately after sass-loader. It inspects the compiled CSS and uses the source maps provided by sass-loader to determine the exact disk location of the file where each url(...) was authored. It then calculates the correct relative path between that source file and the root context, rewriting the url() target dynamically into an absolute path or a properly adjusted relative path.
  3. css-loader: Once the URLs are rewritten, css-loader parses the CSS. It treats the corrected url() paths as ES module dependencies, equivalent to JavaScript import or require() statements.
  4. Asset Modules: Webpack 5's built-in Asset Modules (or legacy file-loader/url-loader) take over the resolved file path, emit the final asset to the output directory with the appropriate hash, and replace the CSS url() with the final public URI.

Module Aliases and Root Paths

For projects utilizing Webpack aliases (configured under resolve.alias), nested asset URLs can also be resolved by bypassing relative paths entirely. In standard Webpack setups, prefixing a path with a configured alias allows css-loader and Webpack’s resolver to identify the file starting from an explicit project root, regardless of how deeply nested the importing Sass partial happens to be.
