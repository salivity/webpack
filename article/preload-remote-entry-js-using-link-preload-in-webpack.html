Preload remoteEntry.js Using Link Preload in Webpack

Preloading remoteEntry.js files using <link rel="preload"> allows Webpack Module Federation architectures to fetch critical remote manifests early in the page lifecycle, eliminating network waterfalls and speeding up initial rendering. This guide outlines why this optimization is necessary and provides direct implementation methods to configure <link rel="preload"> tags for both static and dynamic remote entry points.

Why Preload remoteEntry.js?

In a standard Webpack Module Federation setup, the host application must first download, parse, and execute its own JavaScript bundles before it knows which remoteEntry.js files are needed. This creates a sequential network waterfall:

  1. Host index.html loads.
  2. Host main bundle downloads and executes.
  3. Host discovers federated dependencies and triggers requests for remoteEntry.js.
  4. Remote bundles download and execute.

Using <link rel="preload" as="script"> tells the browser to fetch the remote manifest file in parallel with the host’s initial assets, dramatically reducing the Total Blocking Time (TBT) and Largest Contentful Paint (LCP).

Method 1: Static Preloading via HTML

If the remote entry URLs are known at build time, inject the <link rel="preload"> tag directly into your host application's index.html template.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8" />
  <title>Host Application</title>
  
  <!-- Preload the remoteEntry.js -->
  <link 
    rel="preload" 
    href="https://cdn.example.com/remoteApp/remoteEntry.js" 
    as="script"
    crossorigin="anonymous"
  />
</head>
<body>
  <div id="root"></div>
</body>
</html>

Note: The crossorigin="anonymous" attribute is required if your remote scripts are served from a different domain or CDN. Omitting it can cause the browser to download the script twice.

Method 2: Dynamic Preloading in JavaScript

When remote URLs depend on runtime variables, environment configuration, or feature flags, inject the preload link programmatically at the earliest entry point (e.g., inside bootstrap.js or before dynamic imports).

function preloadRemote(url) {
  const link = document.createElement('link');
  link.rel = 'preload';
  link.as = 'script';
  link.href = url;
  link.crossOrigin = 'anonymous';
  document.head.appendChild(link);
}

// Invoke early in the lifecycle
preloadRemote(process.env.REMOTE_APP_URL + '/remoteEntry.js');

// Dynamically load the federated module later
import('remoteApp/Widget');

Method 3: Using HtmlWebpackPlugin

If you use HtmlWebpackPlugin in your Webpack build, you can inject preload tags automatically using template parameters or custom plugins.

Webpack Configuration

// webpack.config.js
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  // ... other configurations
  plugins: [
    new HtmlWebpackPlugin({
      template: 'public/index.html',
      templateParameters: {
        remoteEntryUrl: process.env.REMOTE_URL || 'https://cdn.example.com/remoteEntry.js',
      },
    }),
  ],
};

HTML Template

<!-- public/index.html -->
<!DOCTYPE html>
<html>
  <head>
    <link 
      rel="preload" 
      href="<%= remoteEntryUrl %>" 
      as="script" 
      crossorigin="anonymous" 
    />
  </head>
  <body>
    <div id="app"></div>
  </body>
</html>

Critical Considerations

  • Cache Headers: Ensure your server or CDN sets short cache expiration headers or uses versioned query parameters for remoteEntry.js (e.g., remoteEntry.js?v=1.0.1), as manifest files should update frequently while remaining fast to fetch.
  • Preload Priority: Browsers assign high priority to scripts loaded with as="script". Only preload remoteEntry.js files that are strictly required for the above-the-fold content to avoid bandwidth contention with primary host assets.
  • Match Webpack Remotes Config: Ensure the href path in the <link> tag matches the exact URL specified in the ModuleFederationPlugin configuration to prevent duplicate network requests.
