How Webpack Treats .mjs vs .js Files

Webpack treats .mjs files as strict ECMAScript Modules (ESM) by default, adhering closely to the official Node.js and ECMAScript specifications, whereas standard .js files are treated with greater flexibility to maintain backward compatibility. While .js files can seamlessly mix CommonJS and ESM semantics depending on your configuration, .mjs files trigger strict parsing rules, strict runtime constraints, and altered module resolution behavior within the Webpack bundling pipeline.

Automatic Module Type Assignment

In modern Webpack (v4 and v5), .mjs files are assigned the module type javascript/esm. This forces Webpack to parse the file strictly as an ECMAScript module regardless of your project's package.json "type" field.

In contrast, standard .js files are typically categorized as javascript/auto. This allows Webpack to inspect the source code and automatically handle both CommonJS (require(), module.exports) and ESM (import, export) syntax within the same project or even the same file.

Fully Specified Import Paths

Webpack enforces standard ESM path resolution for .mjs files. Under the native ECMAScript specification, relative imports must explicitly include the file extension.

When importing a module inside an .mjs file:

  • An import like import { helper } from './utils.mjs'; will succeed.
  • An import like import { helper } from './utils'; will trigger a compile error unless explicitly overridden.

Standard .js files allow extension-less imports by default, relying on Webpack's resolve.extensions array to discover .js, .json, and other configured formats. To bypass this requirement for .mjs, you must explicitly configure resolve.fullySpecified = false in your Webpack configuration.

CommonJS Interoperability and Named Imports

When importing a CommonJS package from a .js file, Webpack creates synthetic named exports, allowing you to write:

// Valid in standard .js under Webpack
import { someFunction } from 'commonjs-package';

In .mjs files, Webpack adheres to the official Node.js ESM specification. Native ESM does not support static analysis of CommonJS named exports. Therefore, you can only import the default export from a CommonJS module:

// Required in .mjs
import cjsPackage from 'commonjs-package';
const { someFunction } = cjsPackage;

Attempting to use direct named imports from a CommonJS module within an .mjs file will result in a runtime or build-time error stating that the requested export was not found.

Execution Context and Module Globals

Files with the .mjs extension are automatically executed in JavaScript strict mode ("use strict"), even if the directive is not declared at the top of the file.

Additionally, standard CommonJS globals and variables are unavailable in .mjs files. Webpack will not provide or polyfill:

  • require()
  • module and module.exports
  • exports
  • __dirname and __filename

Instead, code in .mjs files must use modern standard alternatives, such as import.meta.url for location references and dynamic import() for conditional loading. Standard .js files retain access to these CommonJS identifiers because Webpack wraps them in standard function wrappers during bundling.
