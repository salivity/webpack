Webpack sideEffects: false and Import Restructuring

Marking a package or module with sideEffects: false informs Webpack that the code contains no top-level actions that alter the runtime environment outside its own scope. During import restructuring and tree shaking, this flag enables Webpack to optimize the dependency graph aggressively by pruning unreferenced re-exports entirely. Instead of evaluating unused files to preserve potential side effects, Webpack rewrites import chains to target only the consumed exports, excluding untouched modules from the production bundle.

The Role of sideEffects: false

In JavaScript, simply importing a module can execute code—such as modifying global prototypes, configuring window listeners, or injecting styles. Because the bundler cannot always determine through static analysis whether a module's execution has external consequences, it defaults to including imported modules even if none of their exports are consumed.

Setting "sideEffects": false in a project’s package.json guarantees to Webpack that none of the files in that package produce side effects upon import. If a file only declares and exports functions, classes, or constants, it is pure. This flag grants Webpack permission to skip module evaluation when exports are not explicitly used.

How Webpack Restructures Imports

Import restructuring occurs when consumer code imports through an entry point or barrel file that aggregates multiple modules.

Consider a typical barrel file pattern:

// components/index.js
export { Button } from './Button';
export { Modal } from './Modal';

And consumer usage:

// app.js
import { Button } from './components';

Without sideEffects: false, Webpack must include and evaluate both Button.js and Modal.js. Even though Modal is unused, Webpack cannot guarantee that loading Modal.js does not trigger side-effecting code.

With sideEffects: false, Webpack restructures this dependency:

  1. Graph Traversal: Webpack recognizes the import of Button through components/index.js.
  2. Re-Export Resolution: Webpack traces Button directly to ./Button.js.
  3. Bypassing Unused Modules: Because Modal.js is marked as having no side effects and its exports are not consumed, Webpack bypasses the file completely.
  4. Statement Rewriting: Webpack internally redirects the statement so that app.js imports directly from ./Button.js, effectively dropping ./Modal.js from the compilation graph.

Module-Level Pruning vs. Statement-Level Tree Shaking

It is important to distinguish between statement-level dead code elimination and module-level skipping:

  • Statement-level tree shaking: Webpack and minifiers (like Terser) load the module, parse its Abstract Syntax Tree (AST), and strip unused individual functions or variables inside that file.
  • Module-level pruning (sideEffects: false): Webpack drops the entire file before minification occurs. The unused module is never evaluated, wrapped into a bundle chunk, or processed by downstream minifiers.

This distinction drastically reduces bundle size and compilation overhead, especially in large UI component libraries or utility collections like lodash-es.

Handling Scoped Side Effects

If certain files in a package do produce side effects (such as CSS files or polyfills), the property accepts an array of file patterns instead of a boolean:

{
  "name": "my-library",
  "sideEffects": [
    "*.css",
    "*.scss",
    "./src/polyfills/**"
  ]
}

When configured this way, Webpack restructures and prunes all unreferenced JavaScript modules while guaranteeing that matching stylesheets and polyfills remain in the dependency graph when imported.
