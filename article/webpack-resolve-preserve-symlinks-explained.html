Webpack resolve preserveSymlinks Explained

The resolve.preserveSymlinks option in Webpack controls whether module resolution follows symbolic links to their real disk paths or treats the symlinked path as the actual module location. By default, Webpack resolves symlinks to their canonical filesystem targets, which can lead to duplicate package instances or unexpected dependency resolution in monorepos and locally linked packages. Setting preserveSymlinks: true tells Webpack to maintain the symlink path during resolution, ensuring dependencies are imported relative to the link's directory rather than the physical folder.

Default Behavior vs. Preserving Symlinks

By default, Node.js and Webpack have preserveSymlinks set to false. When Webpack encounters a symbolic link (such as a package linked via npm link or yarn link), it resolves the link to its canonical physical path on the filesystem.

For example, if your application resides in /projects/app and links a local library from /projects/library into /projects/app/node_modules/library, Webpack naturally traces imports inside that library to /projects/library. Consequently, any dependencies required by the library will be looked up inside /projects/library/node_modules rather than /projects/app/node_modules.

When resolve.preserveSymlinks is set to true, Webpack keeps the path as /projects/app/node_modules/library. Dependencies imported by the library are resolved starting from the application’s directory hierarchy, matching how regular installed packages behave.

How to Configure preserveSymlinks

You can configure this option within the resolve block of your webpack.config.js file:

module.exports = {
  // ...
  resolve: {
    preserveSymlinks: true,
  },
};

This mirrors Node.js's runtime flag --preserve-symlinks.

Common Use Cases

  • Local Package Development (npm link / yarn link): When testing shared components or utilities locally, libraries often rely on singleton instances of packages like react or vue. Default symlink resolution can cause duplicate instances of these dependencies to be loaded from both projects, triggering runtime errors. Enabling preserveSymlinks allows the linked package to consume the host project's versions.
  • Monorepos: Package managers that heavily rely on symlinks—such as pnpm, Lerna, or Yarn Workspaces—sometimes encounter issues where nested dependencies fail to resolve correctly if the canonical path isolates them from the consumer's environment.

Considerations and Trade-offs

While resolve.preserveSymlinks: true resolves issues with duplicate dependencies in linked packages, it can also lead to cases where a package cannot find its own internal dependencies if they are not explicitly installed in the parent project's node_modules. Additionally, if multiple symlinks point to the same physical file from different locations, Webpack may bundle that file multiple times under each unique symlink path.
