Memory Leaks in Custom Webpack Plugins and Loaders

Custom Webpack plugins and loaders can easily introduce memory leaks, especially during persistent development workflows using watch mode or Webpack Dev Server. Because Webpack runs as a long-lived Node.js process during continuous builds, retaining unnecessary references across incremental compilations prevents the V8 garbage collector from reclaiming memory. This article highlights the most common memory leak vectors in custom plugins and loaders—including unbounded caching, improper state retention across compilations, dangling event listeners, and child compiler misuse—and provides direct strategies to prevent them.

1. Module-Level and Global Caching Without Eviction

Loaders and plugins are often written to process thousands of files, leading developers to implement custom in-memory caches to speed up expensive tasks like AST generation or transpilation.

// Problematic pattern in a custom loader
const cache = new Map(); // Persists across all compilations in the Node process

module.exports = function(source) {
  if (!cache.has(this.resourcePath)) {
    cache.set(this.resourcePath, heavyComputation(source));
  }
  return cache.get(this.resourcePath);
};

When a module-level Map or plain object stores data keyed by file paths, deleted or modified files leave stale records behind. Over multiple rebuilds, these caches grow indefinitely.

Solution:

  • Rely on Webpack's native caching infrastructure (compiler.cache or this.cacheable()).
  • If a custom cache is mandatory, use an LRU (Least Recently Used) cache with strict item or byte limits, or use a WeakMap when mapping memory to object references.

2. Retaining compilation References in Plugin Instances

A Webpack Compiler runs for the lifetime of the process, while a Compilation represents a single build iteration. A common bug involves storing the compilation object directly on the plugin instance.

class LeakPlugin {
  apply(compiler) {
    compiler.hooks.compilation.tap('LeakPlugin', (compilation) => {
      // Memory leak: Storing compilation on the persistent compiler/plugin scope
      this.compilation = compilation; 
    });
  }
}

The compilation object contains the entire dependency graph, ASTs, source maps, and module instances. Holding a reference to it on the plugin instance keeps the entire previous build's graph alive in memory indefinitely.

Solution:

  • Pass the compilation instance directly into local function arguments.
  • Scope compilation-specific state to the hook's execution boundary instead of storing it on class properties.

3. Dangling Event Listeners and Hook Accumulation

When custom plugins tap into global event emitters—such as Node's process, external file watchers, or persistent Webpack hooks—without cleaning them up, listeners accumulate on every rebuild.

class ListenerLeakPlugin {
  apply(compiler) {
    compiler.hooks.thisCompilation.tap('ListenerLeakPlugin', () => {
      // This listener is added again on every single incremental build
      process.on('SIGINT', this.handleInterrupt);
    });
  }
}

Every repeated compilation registers a duplicate listener holding references to its surrounding closure, preventing garbage collection.

Solution:

  • Attach persistent or process-level listeners inside compiler.hooks.initialize or the apply method directly, ensuring they run only once.
  • Unsubscribe any per-compilation listeners using lifecycle hooks like compiler.hooks.failed and compiler.hooks.done.

4. Neglected Loader Callbacks and Closure Traps

In asynchronous loaders, memory leaks occur when asynchronous operations fail to resolve or when variables are trapped in unresolved closures.

module.exports = function(source) {
  const callback = this.async();
  
  heavyProcessing(source, (err, result) => {
    if (err) {
      // If the callback is not invoked here, Webpack retains the execution context
      console.error(err);
      return; 
    }
    callback(null, result);
  });
};

If an asynchronous pathway encounters an unhandled error branch or timeout and fails to call callback(), Webpack maintains internal references to the loader context and the source buffers awaiting completion.

Solution:

  • Always guarantee that this.async() callbacks are invoked exactly once across all execution branches, including error cases.
  • Avoid binding large buffers to closures that outlive the transformation phase.

5. Mismanaged Child Compilers

Plugins that extract assets or preprocess HTML often create child compilers via compilation.createChildCompiler(). Child compilers instantiate new module graphs and independent plugin pipelines.

If a child compiler is initialized on every run of make or thisCompilation without explicit cleanup or caching, it duplicates parts of the compilation ecosystem in memory.

Solution:

  • Restrict child compilation creation to instances where module dependencies have actually changed.
  • Ensure all child compiler assets are copied to the parent compilation and unneeded references to the child instance are cleared at the end of the hook.
