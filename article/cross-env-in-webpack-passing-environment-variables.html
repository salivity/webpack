cross-env in Webpack: Passing Environment Variables

Managing environment variables in npm execution scripts often causes cross-platform compatibility issues between Windows, macOS, and Linux. The cross-env package solves this problem by providing a unified syntax to set environment variables across different operating systems before executing Webpack commands. This article explains the role of cross-env, why it is essential for multi-platform development teams, and how it integrates with Webpack execution scripts.

The Problem: Operating System Inconsistencies

Operating systems handle command-line environment variables differently:

  • POSIX systems (macOS, Linux): Define variables using simple assignments inline with the command:
    NODE_ENV=production webpack
  • Windows (Command Prompt): Requires the SET keyword:
    SET NODE_ENV=production&& webpack
  • Windows (PowerShell): Requires environment variable syntax:
    $env:NODE_ENV="production"; webpack

If a package.json script uses POSIX syntax, it will fail on Windows with an error stating that the variable name is not recognized as an internal or external command.

The Role of cross-env

cross-env acts as a cross-platform compatibility layer. When installed and placed at the beginning of an npm script, it intercepts the variable assignment, determines the host operating system, and sets the environment variables using the correct system-specific API before delegating execution to the target command (such as Webpack).

Usage in Webpack Execution Scripts

To use cross-env, it is typically installed as a development dependency:

npm install --save-dev cross-env

You then prefix your Webpack execution commands in package.json:

{
  "scripts": {
    "build:dev": "cross-env NODE_ENV=development webpack --mode development",
    "build:prod": "cross-env NODE_ENV=production webpack --mode production"
  }
}

When running npm run build:prod:

  1. cross-env sets process.env.NODE_ENV = 'production' in a way that works seamlessly on Windows, macOS, and Linux.
  2. Webpack executes immediately within that configured Node.js process.

Accessing the Variable Inside Webpack

Once set by cross-env, the variable is immediately available in your webpack.config.js:

const path = require('path');

const isProduction = process.env.NODE_ENV === 'production';

module.exports = {
  mode: isProduction ? 'production' : 'development',
  devtool: isProduction ? 'source-map' : 'eval-cheap-module-source-map',
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: isProduction ? '[name].[contenthash].js' : '[name].js',
  },
};

cross-env vs. Webpack's --env Flag

Webpack includes a built-in --env CLI flag (e.g., webpack --env production), but its scope is different from cross-env:

  • --env: Passes an object directly to a exported configuration function (module.exports = (env) => { ... }). It does not automatically populate process.env.
  • cross-env: Sets global Node.js environment variables (process.env). This ensures that dependent tools, such as Babel (.babelrc.js), PostCSS (postcss.config.js), and other Webpack plugins that inspect process.env.NODE_ENV directly, receive the correct environment context during the build step.
