Handling Broken remoteEntry.js Errors in Webpack

In Webpack Module Federation architectures, a failure to fetch a remoteEntry.js file can cause critical host application failures if unhandled. This article outlines key network error handling strategies to build resilience against unreachable or broken remoteEntry.js files, covering dynamic remote initialization, automated retry mechanisms, React-level error boundaries, and modern Module Federation runtime plugins.

1. Dynamic Remotes with Promise-Based Loading

By default, statically declared remotes inject <script> tags automatically during initialization. If a remote service is offline, the script tag fails and throws an uncaught error.

Configuring remotes using dynamic Promises allows the host application to catch network failures before Webpack attempts to initialize the container:

// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        microApp: `promise new Promise((resolve, reject) => {
          const script = document.createElement('script');
          script.src = 'https://example.com/remoteEntry.js';
          script.onload = () => {
            const proxy = {
              get: (request) => window.microApp.get(request),
              init: (arg) => {
                try {
                  return window.microApp.init(arg);
                } catch(e) {
                  console.error('Remote initialization failed', e);
                }
              }
            };
            resolve(proxy);
          };
          script.onerror = (error) => {
            console.error('Network error loading remoteEntry.js', error);
            // Resolve with a fallback module or reject gracefully
            resolve({
              get: () => () => () => 'Remote Service Unavailable',
              init: () => {}
            });
          };
          document.head.appendChild(script);
        })`,
      },
    }),
  ],
};

2. Dynamic Component Injection with Retry Logic

Instead of declaring remotes in the Webpack configuration, load the remote dynamically in application code using helper utilities. This approach provides fine-grained control to implement retry strategies with exponential backoff before failing:

async function loadRemoteWithRetry(url, scope, module, retries = 3, delay = 1000) {
  for (let i = 0; i < retries; i++) {
    try {
      await loadScript(url);
      await __webpack_init_sharing__('default');
      const container = window[scope];
      await container.init(__webpack_share_scopes__.default);
      const factory = await container.get(module);
      return factory();
    } catch (error) {
      if (i === retries - 1) throw error;
      await new Promise((res) => setTimeout(res, delay * Math.pow(2, i)));
    }
  }
}

function loadScript(url) {
  return new Promise((resolve, reject) => {
    const existing = document.querySelector(`script[src="${url}"]`);
    if (existing) return resolve();

    const script = document.createElement('script');
    script.src = url;
    script.type = 'text/javascript';
    script.async = true;
    script.onload = resolve;
    script.onerror = () => {
      script.remove();
      reject(new Error(`Failed to load ${url}`));
    };
    document.head.appendChild(script);
  });
}

3. Component-Level Error Boundaries

When using dynamic imports (import('microApp/Component')), network errors manifest as runtime chunk-load errors. UI frameworks use Error Boundaries to isolate micro-frontend failures to specific regions of the page, preventing the entire application from crashing.

In React, wrap dynamic federated imports inside an Error Boundary and React Suspense:

import React, { Suspense, lazy } from 'react';
import ErrorBoundary from './ErrorBoundary';

const RemoteWidget = lazy(() => import('microApp/Widget'));

function App() {
  return (
    <ErrorBoundary fallback={<div>Remote component is currently offline.</div>}>
      <Suspense fallback={<div>Loading remote component...</div>}>
        <RemoteWidget />
      </Suspense>
    </ErrorBoundary>
  );
}

4. Modern Module Federation Runtime Plugins

Modern Module Federation (via @module-federation/runtime or Module Federation 2.0) introduces dedicated lifecycle hooks for error handling. Using runtime plugins decouples error management from Webpack configuration files:

import { init, loadRemote } from '@module-federation/runtime';

init({
  name: 'host',
  remotes: [
    {
      name: 'microApp',
      entry: 'https://example.com/remoteEntry.js',
    },
  ],
  plugins: [
    {
      name: 'offline-fallback-plugin',
      errorLoadRemote({ error, lifecycle }) {
        console.warn(`Failed during ${lifecycle}:`, error);
        return {
          default: () => 'Fallback content for unavailable remote.',
        };
      },
    },
  ],
});

5. Service Worker Fallback Strategy

For high-availability requirements, configure a Service Worker to intercept requests for remoteEntry.js. If the network request fails due to an offline state or remote server outage, the Service Worker can serve a cached version or an inline fallback script that exports empty interfaces, allowing the host application to continue running without unhandled script exceptions.
