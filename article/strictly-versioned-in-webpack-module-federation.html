strictlyVersioned in Webpack Module Federation

Webpack Module Federation allows independent applications to share common dependencies at runtime to avoid duplicate bundle downloads. In this architecture, version management is critical to ensure compatibility across micro-frontends. The strictlyVersioned concept—implemented in Webpack configuration via the strictVersion property within the shared object—controls whether Webpack strictly enforces shared package version requirements or allows fallback versions when semantic mismatches occur.

The Problem with Default Dependency Sharing

By default, Webpack Module Federation uses a flexible approach when resolving shared dependencies between host and remote containers. If a host requires lodash@^4.17.0 and a remote provides lodash@^4.16.0, Webpack logs a console warning about the version mismatch, but it still executes using the available instance to prevent the application from crashing.

While this default behavior prioritizes runtime availability, it introduces risks when libraries contain breaking changes, internal state incompatibilities, or breaking API modifications across minor or patch releases.

How strictVersion Works

Setting strictVersion: true changes how Webpack resolves mismatched versions. Instead of issuing a warning and continuing execution with an incompatible version, Webpack immediately rejects the mismatched shared package and throws a runtime error.

When strictVersion: true is enabled:

  • Compatible Versions: If the remote or host provides a version matching the defined requiredVersion range, it is shared normally.
  • Incompatible Versions: If no compatible version is found in the shared scope, Webpack throws a runtime error (e.g., Unsatisfied version ... from ... of shared singleton module ...). It will not fall back to an out-of-range shared instance.
  • Local Fallback: If the consuming application has bundled its own fallback copy of the dependency (and singleton is not set to true), it will load its local bundle instead of using the incompatible shared module.

Configuration Example

The setting is applied within the ModuleFederationPlugin configuration under the shared property:

const { ModuleFederationPlugin } = require('webpack').container;
const deps = require('./package.json').dependencies;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host_app',
      remotes: {
        remote_app: 'remote_app@http://localhost:3001/remoteEntry.js',
      },
      shared: {
        react: {
          singleton: true,
          strictVersion: true,
          requiredVersion: deps.react,
        },
        'react-dom': {
          singleton: true,
          strictVersion: true,
          requiredVersion: deps['react-dom'],
        },
      },
    }),
  ],
};

When to Use Strict Versioning

Enforcing strict versioning is particularly useful in specific architectural scenarios:

  • Stateful Libraries and Contexts: Libraries like React, React Router, or state management stores can break entirely if multiple versions or incompatible minor versions attempt to interact within the same runtime tree.
  • Strict Public APIs: When an internal library or design system frequently introduces breaking changes without proper semver safeguards, enabling strict checking prevents silent failures and corrupted UI states.
  • Preventing Undetected Drift: In large teams where independent applications deploy at different intervals, strict versioning surfaces compatibility issues immediately in testing environments rather than silently producing edge-case bugs in production.
