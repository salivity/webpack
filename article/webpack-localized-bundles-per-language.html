Webpack: Localized Bundles per Language

Generating separate localized bundles per language from a single codebase allows web applications to deliver optimized, locale-specific code without the runtime overhead of shipping massive translation dictionaries to the client. This article explains how to configure Webpack's multi-compiler mode and use compile-time replacements to output distinct static builds for every supported language.

Why Compile-Time Localization?

Traditional client-side internationalization (i18n) typically loads a single JavaScript bundle alongside external JSON translation files or embeds all translations directly into the application. While flexible, this approach increases memory usage, slows down initial rendering, and forces clients to download unused language strings.

Compile-time localization replaces translation identifiers with static strings during the build process. Webpack generates separate artifacts for each language (e.g., bundle.en.js, bundle.es.js), resulting in smaller bundle sizes, faster execution, and zero client-side localization lookup overhead.

Implementation: The Multi-Compiler Approach

Webpack natively supports exporting an array of configuration objects instead of a single configuration object. When Webpack detects an array, it runs in multi-compiler mode, executing each build in parallel or sequence and generating unique assets for each target language.

1. Directory Structure

Assume a project structure where translation strings are stored in locale-specific JSON files:

src/
  ├── index.js
  └── locales/
      ├── en.json
      ├── es.json
      └── de.json
webpack.config.js

2. Writing the Webpack Configuration

In your webpack.config.js, define the list of supported locales, map over them, and return a distinct configuration object for each language. Use webpack.DefinePlugin or webpack.NormalModuleReplacementPlugin to inject the proper language data.

const path = require('path');
const webpack = require('webpack');

const supportedLocales = ['en', 'es', 'de'];

module.exports = supportedLocales.map((locale) => {
  const translations = require(`./src/locales/${locale}.json`);

  return {
    name: `build-${locale}`,
    mode: 'production',
    entry: './src/index.js',
    output: {
      path: path.resolve(__dirname, 'dist', locale),
      filename: 'bundle.js',
      clean: true,
    },
    plugins: [
      new webpack.DefinePlugin({
        __LOCALE__: JSON.stringify(locale),
        __I18N__: JSON.stringify(translations),
      }),
    ],
  };
});

In this setup, each build outputs its artifacts to a language-specific directory (dist/en/, dist/es/, etc.), using the same entry point.

Accessing Translations in Code

With webpack.DefinePlugin, the placeholder variables are replaced at build time with literal values.

// src/index.js
function getGreeting(name) {
  // __I18N__ is inlined directly at compile time
  const template = __I18N__.greeting || 'Hello, {name}!';
  return template.replace('{name}', name);
}

console.log(`Current Locale: ${__LOCALE__}`);
console.log(getGreeting('Alice'));

When Webpack compiles the bundle for es, __I18N__.greeting is directly substituted with the Spanish string, removing the need for a runtime translation registry.

Alternative: Compile-Time AST Transformations

For large-scale applications where defining global variables creates maintainability challenges, use Babel plugins such as babel-plugin-react-intl or custom Abstract Syntax Tree (AST) transforms.

  1. Write standard i18n function calls in your code:

    import { t } from './i18n';
const label = t('submit_button');

  2. Configure Babel to run during the Webpack build, passing the target locale via loader options:

    // Inside the Webpack config map function
module: {
  rules: [
    {
      test: /\.js$/,
      use: {
        loader: 'babel-loader',
        options: {
          plugins: [
            ['babel-plugin-i18n-replace', { locale, file: `./src/locales/${locale}.json` }]
          ]
        }
      }
    }
  ]
}

    This pattern replaces the function calls directly with the raw translated string literals, removing unused translation functions from the production bundle entirely.

Serving Localized Bundles

Once the bundles are generated, serve them via a reverse proxy (e.g., NGINX, Cloudflare Workers, or Apache) based on:

  1. URL Subpaths: Route /en/* requests to /dist/en/ and /es/* requests to /dist/es/.
  2. Accept-Language Header: Inspect incoming HTTP headers at the edge to serve the corresponding localized directory automatically.
  3. User Preferences: Read a locale cookie or session state to determine the appropriate asset directory to serve.
