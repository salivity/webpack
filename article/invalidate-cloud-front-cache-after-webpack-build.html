Invalidate CloudFront Cache After Webpack Build

Deploying modern web applications requires an efficient cache management strategy so users immediately receive the latest code without stale resource interference. This guide outlines how to automatically trigger an Amazon CloudFront cache invalidation directly following a Webpack production build and deployment. By combining Webpack's content hashing capabilities with automated invalidation scripts or CI/CD automation, you can ensure instant updates for HTML entry points while keeping CloudFront costs and build times minimal.

1. Optimize Webpack Output First (Cache Busting)

Before invalidating caches, configure Webpack to append content hashes to generated filenames. Since immutable assets (JS, CSS, images) receive unique names with each change, you only need to invalidate entry files like index.html.

In your webpack.config.js:

module.exports = {
  output: {
    filename: '[name].[contenthash].js',
    chunkFilename: '[name].[contenthash].chunk.js',
    clean: true,
  },
};

Because hashed files are unique, they can be cached indefinitely on CloudFront and the browser. Only the non-hashed entry file (/index.html) requires invalidation upon deployment.

2. Method A: Automated Invalidation via CI/CD (Recommended)

The most reliable approach executes the invalidation step immediately after assets are synchronized to your storage backend (such as Amazon S3) within your deployment pipeline.

Using the AWS CLI in your pipeline (such as GitHub Actions, GitLab CI, or Bitbucket Pipelines):

# 1. Build the Webpack application
npm run build

# 2. Sync hashed assets with aggressive caching
aws s3 sync dist/ s3://your-bucket-name/ \
  --exclude "index.html" \
  --cache-control "max-age=31536000,immutable"

# 3. Sync index.html with no-cache headers
aws s3 sync dist/ s3://your-bucket-name/ \
  --exclude "*" \
  --include "index.html" \
  --cache-control "no-cache, no-store, must-revalidate"

# 4. Invalidate only the entry path
aws cloudfront create-invalidation \
  --distribution-id YOUR_DISTRIBUTION_ID \
  --paths "/index.html"

3. Method B: Using a Post-Build Node.js Script

If your deployment is driven via npm scripts rather than a CI system, you can use the AWS SDK for JavaScript (@aws-sdk/client-cloudfront) to programmatically request invalidations.

Install the AWS SDK client:

npm install --save-dev @aws-sdk/client-cloudfront

Create an invalidation script named invalidate-cdn.mjs:

import { CloudFrontClient, CreateInvalidationCommand } from "@aws-sdk/client-cloudfront";

const client = new CloudFrontClient({ region: "us-east-1" });

async function invalidate() {
  const params = {
    DistributionId: process.env.CLOUDFRONT_DISTRIBUTION_ID,
    InvalidationBatch: {
      CallerReference: `build-${Date.now()}`,
      Paths: {
        Quantity: 1,
        Items: ["/index.html"],
      },
    },
  };

  try {
    const command = new CreateInvalidationCommand(params);
    const response = await client.send(command);
    console.log(`CloudFront Invalidation created: ${response.Invalidation.Id}`);
  } catch (error) {
    console.error("CloudFront Invalidation failed:", error);
    process.exit(1);
  }
}

invalidate();

Chain the script in your package.json:

"scripts": {
  "build": "webpack --mode production",
  "deploy": "npm run build && aws s3 sync dist/ s3://your-bucket-name && node invalidate-cdn.mjs"
}

4. Method C: Webpack Custom Plugin Integration

You can execute the invalidation directly within the Webpack compilation cycle by leveraging compiler hooks.

In your webpack.config.js:

const { CloudFrontClient, CreateInvalidationCommand } = require("@aws-sdk/client-cloudfront");

class CloudFrontInvalidationPlugin {
  constructor(options) {
    this.options = options;
  }

  apply(compiler) {
    // Run after assets have been emitted to the output directory
    compiler.hooks.afterEmit.tapPromise('CloudFrontInvalidationPlugin', async () => {
      if (process.env.NODE_ENV !== 'production') return;

      const client = new CloudFrontClient({ region: "us-east-1" });
      const command = new CreateInvalidationCommand({
        DistributionId: this.options.distributionId,
        InvalidationBatch: {
          CallerReference: `webpack-${Date.now()}`,
          Paths: {
            Quantity: this.options.paths.length,
            Items: this.options.paths,
          },
        },
      });

      await client.send(command);
      console.log('Successfully triggered CloudFront invalidation.');
    });
  }
}

module.exports = {
  // ... other Webpack settings
  plugins: [
    new CloudFrontInvalidationPlugin({
      distributionId: process.env.CLOUDFRONT_DISTRIBUTION_ID,
      paths: ['/index.html'],
    }),
  ],
};

Best Practices for CloudFront Invalidations

  • Invalidate Specific Files, Not Wildcards: Avoid using /* because it drops cached assets across all edge locations, degrading performance and increasing AWS origin load. Target only /index.html or /service-worker.js.
  • Manage CloudFront Costs: AWS provides the first 1,000 invalidation paths per month for free, with fees applied per path afterward. Restricting invalidation solely to entry files keeps you within free allowances.
  • IAM Permissions: Ensure the execution identity (CI/CD role or local IAM user) is strictly assigned the cloudfront:CreateInvalidation permission for your target distribution ARN.
