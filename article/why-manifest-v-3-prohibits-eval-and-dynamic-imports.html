Why Manifest V3 Prohibits Eval and Dynamic Imports

Google Chrome's Manifest V3 enforces strict security policies designed to prevent extensions from executing arbitrary or remotely hosted code. This architectural shift strictly forbids the use of eval() and severely restricts dynamic imports, creating immediate build and runtime failures for standard Webpack configurations. This article breaks down why these mechanisms are banned, how they conflict with Manifest V3's Content Security Policy and Service Worker environment, and the technical reasons Webpack builds must be adapted to comply.

The Strict Content Security Policy (CSP)

The core reason eval() is prohibited in Manifest V3 is the enforced default Content Security Policy (CSP). Under Manifest V2, developers could loosen CSP restrictions to allow unsafe-eval, enabling arbitrary string-to-code execution. Manifest V3 completely disallows modifying the CSP to include 'unsafe-eval'.

The policy requires that all logic executed by the extension be fully contained and statically verifiable within the extension’s packaged archive. Because eval(), new Function(), and string-based execution in setTimeout() or setInterval() allow arbitrary strings to be interpreted as executable logic at runtime, they present a major attack vector. Attackers could exploit these vectors to bypass Google Web Store review processes, inject malicious scripts, or alter an extension's behavior post-installation.

Why Webpack Defaults Trigger the eval() Prohibition

Webpack commonly uses eval() to optimize developer workflows. During development, Webpack’s default configuration assigns source mapping options such as devtool: 'eval' or devtool: 'eval-cheap-source-map'.

These settings wrap every compiled module inside an eval() function string to improve incremental build speeds. When an unpacked Manifest V3 extension attempts to load these bundles, Chrome's runtime immediately blocks execution and throws a CSP violation error. To comply, Webpack builds targeting Manifest V3 must explicitly disable eval-based source maps and use compliant alternatives, such as source-map or cheap-module-source-map.

Transition to Service Workers and the Dynamic Import Problem

Manifest V3 replaces persistent background pages with ephemeral Service Workers. This transition fundamentally changes how code executes and dynamically loads.

  1. Service Worker Lifetime and Asynchronous Loading: Extension Service Workers are terminated when idle and restarted when events fire. Traditional dynamic imports (import()) often rely on creating DOM <script> tags to fetch and execute secondary chunks on demand. Because Service Workers lack access to the DOM, standard DOM-based dynamic loading mechanisms fail entirely.
  2. Deterministic Code Evaluation: Service Workers require all synchronous event listeners to be registered on their initial turn of the event loop. Dynamic code splitting via asynchronous import() can delay listener registration, causing the browser to miss incoming extension events (such as alarms, web requests, or message passing).
  3. Prevention of Remotely Hosted Execution: Dynamic import() statements capable of taking variable parameters create the risk of fetching remote modules or altering dependency graphs at runtime. Manifest V3 explicitly mandates that all executable code must be packaged locally within the CRX file, making arbitrary remote dynamic imports non-compliant by design.

Webpack Code Splitting Limitations

In standard web applications, Webpack automatically manages dynamic import() statements via chunking, loading additional files asynchronously as needed. In Manifest V3 extensions, especially within the background Service Worker context, standard chunk loading strategies break.

Webpack's runtime relies on loading chunks either through JSONP (which injects DOM scripts) or fetch-and-eval techniques, both of which are blocked by Manifest V3's environment. For background scripts, Webpack builds must be configured to output single, self-contained bundles or use static ES module imports that the browser can parse and validate ahead of execution.
