Webpack Web Workers with NPM Package Imports

This article explains how Webpack processes and bundles Web Workers that rely on external npm dependencies. Modern versions of Webpack provide native, loader-free support for Web Workers by analyzing native URL syntax, treating the worker as a distinct entry point, resolving third-party modules from node_modules, and producing an isolated, fully functional bundle for background execution.

Native Worker Syntax in Webpack 5

Webpack 5 introduced out-of-the-box support for Web Workers, removing the historical requirement for plugins like worker-loader. To instantiate a worker that can import npm modules, use the standard ECMAScript module syntax:

const worker = new Worker(new URL('./worker.js', import.meta.url));

When Webpack encounters this static analysis pattern during compilation, it automatically identifies ./worker.js as an entry point for a worker chunk.

How Webpack Compiles Worker Dependencies

When a Web Worker imports an npm package—for example, import { debounce } from 'lodash-es'; or import axios from 'axios';—Webpack executes the following pipeline:

  1. Child Compilation: Webpack spawns a separate compilation process for the worker script. This ensures the worker receives its own runtime environment, as workers execute in a different global scope (DedicatedWorkerGlobalScope) rather than the standard window object.
  2. Module Resolution: Webpack applies its standard resolver rules via enhanced-resolve. It traverses the node_modules directory to locate the requested npm packages, resolving package entry fields such as module or main.
  3. Loader Processing: Any configured loaders (such as babel-loader or ts-loader) that match the imported files within the worker or within node_modules run just as they would for the main application bundle.
  4. Packaging and Chunk Generation: Webpack bundles the worker code alongside its imported npm packages into a standalone asset file in the configured output directory.

Code Splitting and Shared Dependencies

If both the main thread application and the Web Worker import the same npm package, Webpack must determine how to serve those files.

By default, Webpack isolates worker chunks to avoid cross-context execution issues, which may duplicate the shared npm package in both the main bundle and the worker bundle. To optimize this behavior, you can configure Webpack's splitChunks optimization to share chunks across different chunk types:

// webpack.config.js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
    },
  },
};

When configured properly, Webpack creates a shared chunk containing the common npm dependency, loading it asynchronously in both the main thread and the worker scope.

Critical Considerations for NPM Packages in Workers

Not all npm packages can run inside a Web Worker. When importing packages, consider the following technical limits:

  • DOM Restrictions: Web Workers do not have access to the window, document, or DOM APIs. Any npm package that attempts to read or mutate the DOM upon initialization will throw a runtime error inside a worker.
  • Global Scope Access: Packages relying on global variables must use self or globalThis instead of window.
  • Output Targets: If the imported npm packages output modern ES modules, you must instruct the worker to load as a module by passing the type option:
const worker = new Worker(new URL('./worker.js', import.meta.url), {
  type: 'module',
});

Using modern Webpack worker construction enables seamless integration of external npm packages while maintaining proper code isolation and standard bundling workflows.
