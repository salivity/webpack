Webpack Eval vs Source Map: Performance Guide

Choosing between eval source maps and standard source-map in Webpack involves balancing build speed, rebuild efficiency, bundle size, and runtime performance. While eval-based configurations significantly accelerate compilation and Hot Module Replacement (HMR) during development, they introduce notable memory and execution overhead at runtime. Conversely, traditional source-map options yield production-ready, clean JavaScript bundles and precise debugging at the expense of substantially slower initial builds and incremental rebuild times.

How They Work Under the Hood

Eval Source Maps

Options like eval or eval-source-map wrap each compiled module in an eval() string alongside a //# sourceURL or an inlined base64-encoded SourceMap.

Because each module is isolated inside its own eval() call, Webpack can update individual modules without recalculating mappings for the entire chunk or regenerating external files.

Standard Source Maps

The source-map option generates a separate .map file alongside each output JavaScript bundle.

Webpack parses the complete Abstract Syntax Tree (AST), generates mappings for all modules, and creates an independent source map file containing line-and-column-level references to the original source code.

Build and Rebuild Performance

Initial Build Time

  • eval / eval-source-map: Moderately fast to very fast. Webpack avoids generating external files and managing cross-file mapping tables, which reduces processing time during compilation.
  • source-map: The slowest option. Webpack must calculate precise mappings across entire concatenated chunks and write external .map files to disk.

Rebuild Speed (Watch Mode & HMR)

  • eval / eval-source-map: Extremely fast. During incremental changes, Webpack only re-evaluates the modified module. The rest of the bundle cache remains untouched, making Hot Module Replacement almost instantaneous.
  • source-map: Slow. Modifying a single line often requires regenerating the complete source map for the entire chunk, leading to noticeable delays during iterative development.

Runtime and Memory Implications

Bundle Size and Memory Footprint

  • eval: Drastically inflates bundle size because every module includes stringified code and embedded mapping metadata. Browser memory usage increases significantly, as the JavaScript engine must maintain multiple execution contexts for each eval() call.
  • source-map: Leaves the primary JavaScript bundle completely clean, containing only a small comment URL at the end pointing to the external map file. Browser memory consumption remains minimal until developer tools are opened and the .map file is explicitly fetched.

Execution Speed and JIT Optimization

  • eval: Impairs runtime execution speed. Modern JavaScript engines struggle to apply Just-In-Time (JIT) optimizations to code executed inside eval().
  • source-map: Does not affect runtime execution. The browser executes standard, optimized code paths without intermediate string parsing.

Security and Production Suitability

  • Content Security Policy (CSP): eval strategies require the unsafe-eval directive in your CSP, creating significant security vulnerabilities. They are strictly intended for local development.
  • Production Deployment: Standard source-map (or hidden-source-map) is the standard choice for production. It allows error tracking tools like Sentry or Datadog to resolve stack traces without exposing source code directly to end users or compromising security policies.
