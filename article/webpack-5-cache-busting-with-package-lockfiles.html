Webpack 5 Cache Busting with Package Lockfiles

Webpack 5 introduced persistent filesystem caching to drastically reduce build times, but using cached assets when dependencies change can lead to runtime errors. To prevent this, Webpack automatically invalidates—or "busts"—its cache whenever package lockfiles are modified. This article explains the underlying mechanism, detailing how Webpack 5 tracks lockfile changes using build dependencies, snapshotting, and hash comparisons to ensure stale cache artifacts are discarded safely.

The Role of Persistent Filesystem Caching

In Webpack 5, setting cache.type = 'filesystem' writes compilation artifacts to disk (typically inside the node_modules/.cache/webpack directory). Instead of recompiling every module, Webpack reuses these stored records between builds. However, persistent caching requires a reliable invalidation strategy; if a third-party library changes in node_modules, Webpack must know that the previously compiled modules may no longer be valid.

Build Dependencies and Lockfile Tracking

Webpack addresses this through its cache.buildDependencies configuration. Build dependencies are external files that alter the build outcome if changed. By default or via common configuration conventions, tools register the project's build configuration files and package lockfiles (such as package-lock.json, yarn.lock, or pnpm-lock.yaml) as primary build dependencies.

When configured as follows:

module.exports = {
  cache: {
    type: 'filesystem',
    buildDependencies: {
      config: [__filename],
      lockfile: ['package-lock.json']
    }
  }
};

Webpack registers these files into its dependency tracking system during the compilation initialization phase.

Snapshot Generation and Hash Storage

When Webpack writes to the filesystem cache, it creates a "snapshot" of the environment using the snapshot configuration rules (such as snapshot.buildDependencies). For every tracked lockfile, Webpack calculates a cryptographic hash and records file system metadata (such as timestamps and file sizes). This snapshot data is serialized and stored alongside the cached compilation graph.

Because lockfiles explicitly record the exact resolved versions, integrity hashes, and tree structure of all installed node_modules, any installation, upgrade, or removal of a package updates the lockfile's contents.

The Invalidation Lifecycle

During the startup phase of subsequent builds, Webpack executes the following check:

  1. Resolution: Webpack locates the snapshot metadata stored inside the cache directory.
  2. Comparison: Webpack inspects the files defined in buildDependencies, including the lockfile, and compares their current state against the stored snapshot. Depending on snapshot settings, it checks either the file modification timestamp (mtime) or the content hash.
  3. Mismatch Detection: If npm install, yarn add, or an update has modified the lockfile, the computed hash or timestamp will not match the snapshot.
  4. Cache Eviction: Upon detecting the mismatch, Webpack marks the entire filesystem cache as invalid. It discards the existing cached compilation packfiles and performs a clean build from scratch, writing a brand-new cache entry with an updated snapshot of the lockfile.
