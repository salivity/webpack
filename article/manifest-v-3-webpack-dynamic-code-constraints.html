Manifest V3 Webpack Dynamic Code Constraints

Chrome’s Manifest V3 (MV3) introduces strict security policies that fundamentally change how browser extensions handle JavaScript, prohibiting remotely hosted code and the dynamic evaluation of strings as code. When bundling with Webpack, these rules directly disrupt standard dynamic code generation techniques, such as on-demand chunk loading, dynamic imports via standard DOM injection, and eval-based source maps. Developing extensions under MV3 requires specific Webpack configuration changes to ensure that all assets are pre-packaged, statically verifiable, and compliant with MV3's Content Security Policy (CSP).

The Ban on Dynamic Evaluation and Remote Code

Manifest V3 enforces a CSP that forbids the execution of arbitrary strings as code. Functions such as eval(), new Function(), and setTimeout([string]) are blocked entirely.

For Webpack users, this constraint directly impacts development tooling:

  • Source Maps: Webpack’s default development configuration often uses eval-based source maps (e.g., eval-cheap-module-source-map) to increase build speeds. Under MV3, any bundle using an eval variant will immediately trigger a CSP violation and fail to execute. Developers must switch to MV3-compliant alternatives such as source-map or inline-cheap-source-map.
  • String-to-Code Compilers: In-browser templating engines or dynamic runtime code generation libraries bundled by Webpack will fail unless configured to pre-compile templates during the Webpack build step.

Limitations on Dynamic Chunk Loading and Code Splitting

Webpack typically handles dynamic imports (import()) by creating separate chunks that are loaded on demand at runtime. In standard web environments, Webpack achieves this by injecting <script> tags into the DOM or fetching scripts over a network.

MV3 restricts this behavior in multiple ways:

  • Background Service Workers: MV3 replaces persistent background pages with Service Workers, which do not have access to the DOM. Consequently, Webpack's default chunk-loading mechanism (JSONP via <script> element injection) fails in the background context.
  • Importing Local Chunks: While dynamic import() is partially supported in ES module-based Service Workers, Webpack must be explicitly instructed to handle chunk loading via service worker-compatible APIs, such as importScripts for traditional service worker scripts, using output.chunkLoading = 'importScripts'.
  • External CDNs: All code executed by an MV3 extension must be packaged locally within the extension .crx bundle. Webpack’s output.publicPath cannot point to an external CDN to fetch chunks dynamically; all dynamically split files must reside locally within the extension directory and be declared in the web_accessible_resources field if loaded outside the extension's privileged context.

Required Webpack Adjustments for Manifest V3

To navigate these constraints, Webpack configurations for MV3 extensions typically require:

  1. Disabling Dynamic Chunking for Specific Contexts: For background workers and content scripts, developers often disable code splitting entirely by configuring optimization.splitChunks = false or generating isolated entry points to ensure each target executes from a single, self-contained bundle.
  2. Targeting the Right Environments: Configuring separate Webpack compiler configurations for different extension contexts—such as configuring target: 'webworker' for the background service worker and target: 'web' for popups and options pages.
  3. Strict Source Map Selection: Explicitly setting devtool: 'cheap-module-source-map' or devtool: 'source-map' across both development and production builds to avoid generating code that triggers CSP evaluation blocks.
