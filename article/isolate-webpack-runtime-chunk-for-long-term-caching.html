Isolate Webpack Runtime Chunk for Long-Term Caching

Webpack injects a runtime manifest into compiled bundles to manage module loading, chunk resolution, and execution. By default, this runtime code is embedded directly into your entry point bundles, causing their content hashes to change whenever any project module changes—even if the entry point's source code remains untouched. This guide explains how the Webpack runtime works, why inlining it breaks client caching, and how to use the optimization.runtimeChunk setting to extract it into an isolated file for optimal long-term caching.

The Webpack Runtime Problem

Webpack's runtime contains the logic and manifest required to connect your application modules while they run in the browser. It tracks module IDs, chunk IDs, and the mappings between them.

When you modify a file or add a new module, its ID and hash update. Webpack updates its internal manifest to reflect these changes. If the runtime lives inside your primary bundle (such as main.js or vendor.js), that bundle's hash changes on every build. Browsers are then forced to re-download the entire bundle, defeating the purpose of HTTP long-term caching.

Isolating the Runtime with optimization.runtimeChunk

Webpack provides the optimization.runtimeChunk configuration option to extract the runtime boilerplate into a standalone file.

To isolate the runtime, open your webpack.config.js and add runtimeChunk: 'single' inside the optimization block:

module.exports = {
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash].js',
    path: path.resolve(__dirname, 'dist'),
    clean: true,
  },
  optimization: {
    runtimeChunk: 'single',
  },
};

Using 'single' creates a shared chunk typically named runtime.js (or runtime.[contenthash].js in production). This is the recommended setting for single-page applications (SPAs).

Alternative Configuration Values

The runtimeChunk property supports other configurations depending on your architecture:

  • true or 'multiple': Generates a distinct runtime chunk for each entry point. This is useful for multi-page applications where different entry points should not depend on a single shared runtime.

  • Object notation: Allows you to explicitly define the name of the runtime chunk:

    optimization: {
  runtimeChunk: {
    name: (entrypoint) => `runtime~${entrypoint.name}`,
  },
}

Ensuring Deterministic Hashes

Isolating the runtime chunk resolves manifest churn, but long-term caching also requires stable module and chunk IDs. By default, module IDs can change based on the order in which files are resolved.

To prevent cascading cache invalidation, configure Webpack to use deterministic module IDs:

module.exports = {
  optimization: {
    runtimeChunk: 'single',
    moduleIds: 'deterministic',
    chunkIds: 'deterministic',
  },
};

With deterministic, Webpack generates short, persistent hashes for modules and chunks based on their file paths. This ensures that adding a new import in one file does not alter the generated IDs or hashes of unrelated vendor bundles.

Complete Caching Configuration

A standard production setup combining runtime isolation, deterministic IDs, and third-party vendor separation looks like this:

const path = require('path');

module.exports = {
  mode: 'production',
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash].js',
    path: path.resolve(__dirname, 'dist'),
    clean: true,
  },
  optimization: {
    runtimeChunk: 'single',
    moduleIds: 'deterministic',
    splitChunks: {
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
      },
    },
  },
};

Under this configuration:

  • The tiny runtime.[contenthash].js chunk updates whenever module relationships change.
  • The large vendors.[contenthash].js chunk remains cached indefinitely until dependencies are updated.
  • Application code in main.[contenthash].js only invalidates when application source files change.
