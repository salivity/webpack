How Singleton Works in Webpack Module Federation

The singleton configuration option in Webpack Module Federation ensures that only one instance of a shared dependency is loaded and used across all federated applications at runtime. This article explains the mechanics of the singleton flag, why it is critical for stateful libraries like React, how Webpack resolves version mismatches when it is enabled, and the key companion options you need to configure it reliably.

The Purpose of the Singleton Option

By default, Webpack Module Federation allows different micro-frontends (hosts and remotes) to load their own copies of a shared dependency if their version requirements differ. While this works well for stateless utility libraries like Lodash, it breaks libraries that rely on a single global state or identity checks, such as React, React DOM, Vue, and Redux.

If multiple instances of React load simultaneously, features like React Context, hooks, and component reconciliation will fail, often resulting in errors like "Invalid hook call." Setting singleton: true in your shared configuration instructs Webpack to enforce a single, global runtime instance of that library across the host and all consumed remotes.

// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      shared: {
        react: {
          singleton: true,
          requiredVersion: '^18.2.0',
        },
        'react-dom': {
          singleton: true,
          requiredVersion: '^18.2.0',
        },
      },
    }),
  ],
};

How Webpack Selects the Singleton Version

When multiple federated applications declare a shared module as a singleton, Webpack evaluates all available versions declared by the host and remotes. It negotiates the version based on the following process:

  1. Version Gathering: Webpack inspects the versions provided by all participating federated modules.
  2. Highest Version Selection: Out of all available versions that satisfy the declared requirements, Webpack selects and instantiates the highest compatible semantic version.
  3. Global Registration: The chosen version is registered in the shared scope (by default, default), and all subsequent requests for that module point to this single, instantiated copy.

Managing Version Conflicts

Because singleton: true strictly prevents multiple copies from loading, potential version conflicts must be handled carefully using companion properties:

requiredVersion

This property defines the semver range that an application expects. In most setups, this is imported directly from package.json dependencies (e.g., deps.react). Webpack uses this range to determine whether the resolved singleton version meets the application's criteria.

strictVersion

This boolean determines how Webpack behaves when a version mismatch occurs:

  • strictVersion: false (Default): If a remote requires React 17 but the host loads React 18, Webpack still forces the single version (React 18) to load to uphold the singleton rule. However, it outputs a warning in the browser console informing you of the mismatch.
  • strictVersion: true: Webpack halts execution and throws an error at runtime if the available singleton version does not satisfy the specified requiredVersion. This setting prevents subtle bugs caused by unexpected API differences between major versions.

Initialization and the Asynchronous Boundary

Singletons require Webpack to initialize the shared scope before application code executes. If your application entry file executes synchronously, Webpack cannot negotiate shared singletons with remotes in time, leading to warnings that the shared module is not available.

To ensure the singleton negotiation succeeds:

  • Create an asynchronous boundary by moving your main logic into a bootstrap.js file and importing it dynamically from your main index.js file (import('./bootstrap')).
  • Avoid using eager: true alongside singleton: true unless strictly necessary, as marking a singleton as eager bundles it into the initial chunk and can bypass version negotiation across federated remotes.
