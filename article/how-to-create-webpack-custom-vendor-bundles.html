How to Create Webpack Custom Vendor Bundles

Configuring optimization.splitChunks.cacheGroups in Webpack allows developers to separate third-party dependencies into dedicated, long-term cacheable vendor bundles. By segmenting libraries based on frequency of changes or specific functional domains, you can significantly reduce initial load times, prevent unnecessary cache invalidation, and optimize asset delivery. This guide details how to target specific dependencies and configure custom cache groups effectively within your Webpack setup.

Understanding cacheGroups

Webpack's SplitChunksPlugin operates through cacheGroups. While Webpack provides default vendor splitting, defining custom cacheGroups enables granular control over which modules are grouped into specific chunk files. Each custom cache group inherits the global splitChunks rules unless explicitly overridden.

Basic Custom Vendor Configuration

To create a separate bundle containing all dependencies imported from the node_modules directory, configure the optimization block in your webpack.config.js:

module.exports = {
  // ... other webpack configuration
  optimization: {
    splitChunks: {
      cacheGroups: {
        defaultVendors: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendor',
          chunks: 'all',
          priority: -10,
          reuseExistingChunk: true,
        },
      },
    },
  },
};

Isolating Specific Libraries into Dedicated Bundles

Lumping all vendor code into a single file can still result in large bundle sizes. You can create multiple cache groups to isolate critical libraries (such as UI frameworks or utility packages) into their own files.

Here is an example that separates React ecosystem packages and larger utility libraries like Lodash into standalone chunks:

module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      maxInitialRequests: 20,
      minSize: 20000,
      cacheGroups: {
        default: false, // Disables default cache group
        
        // Isolate React and related packages
        reactVendor: {
          test: /[\\/]node_modules[\\/](react|react-dom|react-router-dom)[\\/]/,
          name: 'vendor-react',
          chunks: 'all',
          priority: 40,
        },

        // Isolate UI/Component libraries
        uiVendor: {
          test: /[\\/]node_modules[\\/](@mui|@emotion)[\\/]/,
          name: 'vendor-ui',
          chunks: 'all',
          priority: 30,
        },

        // Catch-all for remaining node_modules dependencies
        commonVendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendor-common',
          chunks: 'all',
          priority: 20,
          reuseExistingChunk: true,
        },
      },
    },
  },
};

Key Cache Group Configuration Options

To effectively control output, use the following properties within each cache group definition:

  • test: Determines which modules are selected. It can be a regular expression matching the absolute resource path, a string, or a custom filtering function (module) => boolean.
  • name: Defines the output name of the chunk. Providing a static string groups all matching modules into a single file with that name. Providing a function enables dynamic naming based on chunk context.
  • chunks: Specifies which chunks are selected for optimization. Using 'all' is typically recommended for vendor bundles to cover both synchronous and asynchronous imports. Other options include 'initial' and 'async'.
  • priority: Sets the execution order when a module satisfies the test conditions of multiple cache groups. Groups with higher numerical values take precedence over groups with lower values.
  • reuseExistingChunk: When set to true, Webpack reuses an existing chunk rather than creating a duplicate if the current module has already been split from the main bundle.
  • enforce: When set to true, Webpack ignores size limits such as minSize, maxSize, minChunks, and maxInitialRequests for that specific cache group.
