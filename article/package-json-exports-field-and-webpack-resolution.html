Package.json Exports Field and Webpack Resolution

The package.json exports field is a modern standard for defining explicit entry points, subpath mappings, and conditional module loading for JavaScript packages. This article explains the architectural role of the exports field, how it enforces package encapsulation, and the step-by-step mechanism Webpack uses to parse and resolve it during the build process.

The Role of the package.json Exports Field

Introduced natively in Node.js and adopted across the JavaScript ecosystem, the exports field replaces and expands upon the legacy main field. It serves three primary functions:

1. Module Encapsulation

Historically, consumers of an npm package could deeply import any internal file (for example, require('my-pkg/lib/internal-helper.js')). The exports field enforces strict boundaries. When exports is defined, only the paths explicitly declared in the field are accessible to consumers. Any attempt to import an unlisted path results in a module resolution error.

{
  "name": "my-package",
  "exports": {
    ".": "./dist/index.js",
    "./feature": "./dist/feature.js"
  }
}

In this scenario, importing my-package or my-package/feature succeeds, while importing my-package/dist/internal.js fails.

2. Subpath Mapping and Patterns

The field allows package authors to map clean public specifiers to internal directory structures or expose entire folders using pattern matching:

{
  "exports": {
    "./components/*": "./dist/components/*.js"
  }
}

3. Conditional Exports

The exports field enables environment-aware and format-aware resolution. A single package can cleanly serve ECMAScript Modules (ESM) to modern bundlers while serving CommonJS (CJS) to legacy environments, or switch implementations between browser and server environments:

{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "browser": "./dist/index.browser.js",
      "default": "./dist/index.js"
    }
  }
}

How Webpack Resolves the Exports Field

Starting with Webpack 5, support for the package.json exports field is enabled by default through the enhanced-resolve engine. Webpack processes this field using a distinct resolution pipeline.

Precedence Over Legacy Fields

When Webpack encounters a package, it checks for the presence of the exports field before consulting legacy entry fields such as module, main, or browser. If an exports field exists:

  • Webpack exclusively uses exports to resolve the module.
  • Legacy fields (main, module, etc.) are ignored, even if the requested subpath is missing in exports.

Condition Matching and resolve.conditionNames

Webpack evaluates nested conditional objects within the exports field against an active list of condition names. This behavior is governed by the target configuration and the resolve.conditionNames option:

  1. Target-Driven Conditions: If the Webpack target is set to web or webworker, Webpack automatically adds the browser condition. If the target is node, it adds the node condition.
  2. Syntax-Driven Conditions: Depending on the import statement used in the application code, Webpack enables import (for import declarations) or require (for require() calls).
  3. Default Condition: The default key is always evaluated as a universal fallback.

Webpack checks conditions in the order they are listed in the package's exports map, matching against the enabled conditions in Webpack's resolution pipeline.

Customizing Resolution in Webpack Configuration

Developers can override or extend Webpack's default behavior using the resolve configuration block:

module.exports = {
  resolve: {
    // Defines which fields in package.json are checked for export maps
    exportsFields: ['exports'],

    // Explicitly controls condition priority
    conditionNames: ['production', 'import', 'browser', 'default']
  }
};

If a package defines custom condition names (such as "production", "development", or library-specific flags like "solid" or "worker"), adding them to resolve.conditionNames instructs Webpack to prioritize those specific implementation files.

Error Handling

If an application attempts to import a specifier not explicitly listed in exports, Webpack halts the compilation and emits a Module not found: Package path ./xyz is not exported error. This guarantees that consumers adhere strictly to the package's public API contract.
