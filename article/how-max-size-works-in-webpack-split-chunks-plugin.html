How maxSize Works in Webpack SplitChunksPlugin

The maxSize option in Webpack's SplitChunksPlugin automatically splits oversized chunks into smaller, more manageable pieces when a chunk exceeds a specified byte threshold. By enforcing a maximum file size while respecting module boundaries and caching requirements, this setting helps developers optimize asset delivery, improve HTTP/2 parallel loading, and prevent massive bundles from delaying initial page rendering.

The Chunk Splitting Lifecycle

Webpack executes chunk optimization in sequential phases. First, SplitChunksPlugin creates initial chunks based on parameters like minSize, entry points, and chunk types (async or initial).

Once the initial chunks are formed, Webpack evaluates each chunk against the configured maxSize (or its variants, maxAsyncSize and maxInitialSize). If a chunk's total byte weight exceeds this threshold, Webpack invokes an internal splitting algorithm to break that single chunk into multiple sibling chunks.

The Splitting Mechanism and Module Boundaries

Webpack cannot break a single module (such as an individual JavaScript file or library) into pieces. Consequently, the breakdown algorithm functions under specific constraints:

  1. Module-Level Granularity: Webpack sorts the modules contained within the oversized chunk and partitions them into groups. Each group becomes a new chunk whose size stays as close to or below the maxSize limit as possible.
  2. Atomic Modules: If an individual module (for example, a large third-party library like lodash or three.js) is intrinsically larger than the specified maxSize, Webpack cannot split it further. In this scenario, the module is isolated into its own dedicated chunk that exceeds maxSize. Webpack prioritizes module execution integrity over the strict size limit.
  3. The minSize Priority: When splitting, Webpack attempts to avoid creating chunks that fall below the minSize threshold. If splitting an oversized chunk would yield tiny, inefficient files smaller than minSize, Webpack limits how aggressively it partitions the assets.

Naming Conventions and Determinism

When maxSize divides an existing chunk, Webpack generates deterministic names for the resulting parts to ensure effective browser caching:

  • The derived chunk names are constructed using the original chunk name combined with a hash of the modules included in that specific subdivision (e.g., vendors~main~1a2b3c4d.js).
  • If custom naming functions are disabled, Webpack relies on internal numerical or hashed chunk IDs.
  • Because the split is deterministic, updating a single module only invalidates the specific sub-chunk containing that module, leaving the other derived chunks intact in the user's browser cache.

Configuration Example

A standard implementation defines both minSize and maxSize to establish an acceptable file-size window:

module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      minSize: 20000, // 20 KB minimum threshold
      maxSize: 70000, // 70 KB target maximum
    },
  },
};

In this configuration, Webpack merges small modules until they reach at least 20 KB, but once a combined chunk approaches or exceeds 70 KB, it divides the modules into additional chunks to keep individual asset payloads lightweight.
