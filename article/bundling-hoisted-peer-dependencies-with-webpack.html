Bundling Hoisted Peer Dependencies with Webpack

This article explains how Webpack resolves and bundles hoisted peer dependencies in a monorepo architecture. In multi-package repositories managed by tools like npm, Yarn, or pnpm, peer dependencies are typically installed once at the root level rather than duplicated across individual packages. Webpack relies on its internal module resolution engine, specific path-traversal algorithms, and configuration flags like aliases and symlink handlers to locate these root-level dependencies and bundle them without runtime duplication.

The Resolution Mechanism

Webpack utilizes enhanced-resolve, a dedicated resolver engine that mimics the standard Node.js module resolution algorithm while adding extensive customization. When a sub-package inside a monorepo (e.g., packages/ui-components) requires a peer dependency like react, the resolution process follows a specific order:

  1. Local Lookup: Webpack checks for a node_modules directory inside packages/ui-components. Because the dependency is marked as a peer dependency, it is absent from this local directory.
  2. Directory Traversal: Webpack navigates up the directory hierarchy to the parent directories.
  3. Root Resolution: Once the resolver reaches the repository root, it identifies the hoisted dependency in the root node_modules directory and binds the import to that file path.

The Symlink Challenge

Monorepo workspace managers typically link internal packages together via symlinks. By default, Webpack enables resolve.symlinks: true. This setting causes Webpack to resolve the real, physical path of files rather than their symlinked paths inside the consumer's node_modules.

When Webpack resolves the real path of an internal package, it searches for peer dependencies starting from that package’s physical directory upwards. If the package structure or package manager configuration does not properly expose the hoisted packages along that physical path, Webpack may fail to resolve the module, or worse, resolve multiple distinct instances of the same library from different locations.

Preventing Duplication with Aliases

To guarantee that a single instance of a hoisted peer dependency is included in the final bundle, Webpack configurations frequently use explicit path aliases. This is especially critical for libraries that rely on singleton states, such as React or GraphQL.

Configuring resolve.alias directs Webpack to map any import of the peer dependency directly to the hoisted version at the root:

const path = require('path');

module.exports = {
  resolve: {
    alias: {
      react: path.resolve(__dirname, 'node_modules/react'),
      'react-dom': path.resolve(__dirname, 'node_modules/react-dom'),
    },
  },
};

When Webpack encounters import React from 'react' inside any internal package, it bypasses standard relative directory traversal and maps the module to the specified absolute path.

Guiding Traversal with resolve.modules

Another technique Webpack uses to handle hoisted packages is configuring resolve.modules. By defining absolute search locations, Webpack prioritizes specific directories when searching for un-namespaced modules:

module.exports = {
  resolve: {
    modules: [
      path.resolve(__dirname, 'node_modules'),
      'node_modules',
    ],
  },
};

This tells Webpack to check the root node_modules before executing fallback traversals, ensuring that hoisted dependencies are discovered predictably regardless of which package initiated the import.

Final Bundle Deduplication

During the compilation phase, Webpack tracks modules using unique identifiers based on their resolved absolute paths. Because the resolver maps every package’s request for a hoisted peer dependency to the same file path in the root node_modules, Webpack assigns that dependency a single module ID. At runtime, the bundled module is executed only once, and all dependent monorepo packages receive a reference to the same shared export.
