Unit Testing Custom Webpack Loaders with Jest

Testing custom Webpack loaders requires simulating Webpack’s build environment to verify code transformations without running a slow, full-scale build. This article covers two straightforward approaches to unit testing custom loaders using Jest: isolating the loader function by mocking its execution context, and using Webpack's official loader-runner utility for realistic, pipeline-level verification.

Understanding Webpack Loaders

A Webpack loader is fundamentally an exported JavaScript function that accepts source content as an argument and returns the transformed result. Within the loader, Webpack injects utilities and configuration via the function's execution context (this), such as this.async(), this.getOptions(), and this.emitFile().

Consider a basic loader, reverse-loader.js:

module.exports = function (source) {
  const options = this.getOptions() || {};
  const reversed = source.split('').reverse().join('');
  
  if (options.uppercase) {
    return reversed.toUpperCase();
  }
  
  return reversed;
};

Method 1: Direct Execution with a Mocked Context

The fastest way to test a synchronous or asynchronous loader is to invoke the function directly while binding a mock context to this.

Testing Synchronous Loaders

Use Function.prototype.call to provide the mocked this properties:

const reverseLoader = require('../src/reverse-loader');

describe('reverseLoader (Direct Unit Test)', () => {
  it('should reverse input text', () => {
    const mockContext = {
      getOptions: () => ({ uppercase: false }),
    };

    const input = 'hello world';
    const result = reverseLoader.call(mockContext, input);

    expect(result).toBe('dlrow olleh');
  });

  it('should reverse and uppercase text when option is true', () => {
    const mockContext = {
      getOptions: () => ({ uppercase: true }),
    };

    const input = 'hello world';
    const result = reverseLoader.call(mockContext, input);

    expect(result).toBe('DLROW OLLEH');
  });
});

Testing Asynchronous Loaders

If your loader handles async operations via this.async(), mock the callback function within Jest:

// async-loader.js
module.exports = function (source) {
  const callback = this.async();
  setTimeout(() => {
    callback(null, `/* Header */\n${source}`);
  }, 10);
};
// async-loader.test.js
const asyncLoader = require('../src/async-loader');

describe('asyncLoader', () => {
  it('should prepend a header asynchronously', (done) => {
    const mockCallback = jest.fn((err, result) => {
      expect(err).toBeNull();
      expect(result).toBe('/* Header */\nconst a = 1;');
      done();
    });

    const mockContext = {
      async: () => mockCallback,
    };

    asyncLoader.call(mockContext, 'const a = 1;');
  });
});

Method 2: Testing with loader-runner

Webpack maintains loader-runner, a standalone library that executes loaders exactly as Webpack does internally. This eliminates the need to manually mock context properties.

1. Install loader-runner

npm install --save-dev loader-runner

2. Implement a Helper Function

Wrap runLoader in a Promise to use cleanly with modern async/await syntax in Jest:

const path = require('path');
const { runLoader } = require('loader-runner');

function executeLoader(fixturePath, options = {}) {
  return new Promise((resolve, reject) => {
    runLoader(
      {
        resource: fixturePath,
        loaders: [
          {
            loader: path.resolve(__dirname, '../src/reverse-loader.js'),
            options,
          },
        ],
        context: {
          emitFile: () => {},
        },
        readResource: require('fs').readFile.bind(require('fs')),
      },
      (err, result) => {
        if (err) return reject(err);
        resolve(result);
      }
    );
  });
}

3. Write the Test Suite

Create a dummy fixture file (fixture.txt) containing test content, then assert against the result output:

const path = require('path');
const { executeLoader } = require('./helpers');

describe('reverse-loader with loader-runner', () => {
  const fixture = path.resolve(__dirname, 'fixtures/sample.txt');

  it('transforms input using loader-runner', async () => {
    const output = await executeLoader(fixture, { uppercase: true });
    
    // output.result contains an array of results; the first is the transformed code
    const transformedCode = output.result[0];

    expect(transformedCode).toBeDefined();
    expect(transformedCode).toMatchSnapshot();
  });
});

Key Considerations

  • Pure Functions: Keep loader logic decoupled from complex context APIs wherever possible. Extract transformation algorithms into plain utility functions that can be tested in isolation.
  • Error Handling: Verify error states by calling this.emitError() or throwing errors directly in your loader, then asserting that loader-runner returns the expected failure.
  • Source Maps: If your loader generates source maps, verify that the second element of the result array (output.result[1]) matches the expected source mapping output.
