Dangers of Incorrect sideEffects False in Webpack

Setting "sideEffects": false in a library's package.json informs bundlers like Webpack that any module in the package can be safely skipped if its exported values are not directly consumed. While this allows aggressive tree-shaking to minimize bundle size, incorrectly flagging a package with implicit side effects as side-effect-free leads Webpack to silently eliminate essential code. This article outlines the dangerous, hard-to-detect bugs that occur when this property is misused, ranging from completely missing styles to broken runtime behavior.

1. Missing Global CSS and Component Styles

The most common consequence of an incorrect sideEffects: false flag is the complete elimination of imported stylesheets. In many component libraries, CSS is imported directly into JavaScript files without exporting anything:

import './Button.css';

export const Button = () => { /* ... */ };

If a consuming application imports a different component from the same bundle entry point and does not directly reference Button, Webpack considers Button.css dead code and strips it entirely. Even worse, if the library relies on global base styles, CSS resets, or theme variables imported via bare import './global.css'; statements, those files are dropped, completely breaking the user interface in production.

2. Dropped Polyfills and Global Runtime Patches

Libraries often import polyfills or patch standard runtime environments to ensure cross-browser compatibility:

import 'core-js/actual/structured-clone';
import './patches/window-fetch';

Because these files do not export variables, Webpack sees bare import statements with no assigned identifiers. When sideEffects: false is active, Webpack assumes these modules have no impact on the rest of the application and eliminates them. As a result, older browsers or environments missing native implementations will throw unhandled exceptions such as ReferenceError or TypeError: [method] is not a function, leading to critical runtime crashes.

3. Broken Self-Registering Systems and Web Components

Many modern architectures rely on modules executing immediately upon import to register themselves with a central registry. Common examples include:

  • Custom Web Components: Calls to customElements.define('custom-button', CustomButton) inside a standalone module.
  • Pluggable Libraries: Modules registering drivers, adapters, or syntax highlighters (e.g., Prism.js, Chart.js, or database drivers).
  • Dependency Injection Containers: Modules self-binding interfaces to implementations on evaluation.

When a package is falsely marked without side effects, importing the file for its registration side effect alone (import 'my-library/register-plugin') will be dropped by the bundler. The application will compile without warnings, but the features will fail silently at runtime, leaving custom HTML tags unrendered or plugin hooks absent.

4. Loss of State Initializers and Observability

Modules that initialize critical background processes often execute at import time without explicit exports:

  • Initializing telemetry, analytics, or error-tracking SDKs.
  • Setting up global event listeners (window.addEventListener).
  • Populating shared module-level caches or singletons.

If an author declares sideEffects: false, any entry module that orchestrates these initializations via side-effect imports is discarded. Telemetry goes dark, error trackers stop capturing uncaught exceptions, and state management systems fail to initialize their default stores.

5. Production-Only Discrepancies ("Works on My Machine")

Tree-shaking optimizations driven by sideEffects are typically disabled during development (mode: 'development') to improve build speeds. Consequently:

  • The application functions correctly in local development environments.
  • Unit tests run through Node.js or test runners (like Jest or Vitest) pass because they execute files directly without tree-shaking.
  • The bugs manifest exclusively in production builds (mode: 'production') after minification and module pruning.

This discrepancy makes tracking down the root cause notoriously difficult, as debugging minified production bundles often masks which files were dropped during compilation.

Preventing Side-Effect Pruning Issues

Package authors should never default to a blanket "sideEffects": false unless the library is strictly composed of pure functions. If side effects exist, authors should either avoid module-level execution entirely or use an array to explicitly whitelist files that must never be tree-shaken:

{
  "name": "my-library",
  "sideEffects": [
    "*.css",
    "*.scss",
    "./src/polyfills/**",
    "./src/register.js"
  ]
}
