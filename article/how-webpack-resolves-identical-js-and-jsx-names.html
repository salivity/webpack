How Webpack Resolves Identical js and jsx Names

When both .js and .jsx files coexist with the same base name in the same directory, Webpack resolves extensionless imports by strictly evaluating the order specified in its resolve.extensions configuration array. Whichever file extension appears earlier in that array is prioritized and selected for the bundle. This article explains how Webpack's module resolution algorithm processes these identical base names, the role of default settings, and methods to avoid ambiguous module resolutions.

The Role of resolve.extensions

When a module is imported without an explicit extension—such as import Button from './Button'—Webpack's internal resolver (enhanced-resolve) determines which physical file to load using the resolve.extensions option in webpack.config.js.

Webpack processes the extensions sequentially from left to right (index 0 onward). The first extension that produces an existing file path on the filesystem wins the match, and Webpack immediately ceases searching.

// webpack.config.js
module.exports = {
  // ...
  resolve: {
    extensions: ['.js', '.jsx', '.json'],
  },
};

In this configuration:

  1. Webpack checks for ./Button.js.
  2. If ./Button.js exists, it is loaded, and ./Button.jsx is completely ignored.
  3. If ./Button.js does not exist, Webpack moves to the next entry and checks for ./Button.jsx.

If the array is inverted to ['.jsx', '.js', '.json'], ./Button.jsx takes precedence over ./Button.js.

Webpack Default Behavior

In Webpack 5, the default value for resolve.extensions is:

['.js', '.json', '.wasm']

Because .jsx is not included in the default list, an extensionless import of a component named Button alongside both Button.js and Button.jsx will resolve Button.js. If Button.js did not exist, the build would fail with a Module not found error unless .jsx was manually added to the configuration array.

Explicit Extension Imports

The resolve.extensions priority only applies to extensionless import statements. If a file specifies an explicit extension:

import Button from './Button.jsx';

Webpack bypasses the resolve.extensions list and directly looks for ./Button.jsx, regardless of the presence of ./Button.js or the array order in the configuration.

Best Practices to Prevent Collision Issues

Relying on extension precedence when files share the same base name can lead to subtle bugs, unexpected bundle sizes, or test runner mismatches (such as Jest or Vite evaluating extensions in a different order). To maintain consistency:

  1. Avoid Identical Base Names: Do not keep both Component.js and Component.jsx in the same directory. If one is an implementation and the other is a test or wrapper, adopt clear naming conventions such as Component.test.jsx or ComponentContainer.jsx.
  2. Standardize Project Extensions: Standardize on a single extension across your codebase (e.g., strictly .jsx or .tsx for React components, and .js or .ts for non-UI utilities).
  3. Explicit Imports for Exceptions: If duplicate names are unavoidable during migrations, enforce explicit extension usage in import paths to ensure deterministic module resolution across all build and test tools.
