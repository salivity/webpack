Next.js Webpack Config in next.config.js

Next.js provides a built-in webpack function hook within next.config.js that allows developers to inspect and modify the underlying Webpack configuration. This article explains the signature of the webpack hook, details each property provided in its context options, and demonstrates how to safely apply custom loaders and plugins across client and server environments.

The webpack Function Hook

Next.js exposes its Webpack lifecycle through a single function defined in next.config.js. It receives two parameters: the existing Webpack configuration object and an execution context object containing metadata about the current build target.

// next.config.js
module.exports = {
  webpack: (config, options) => {
    // Perform customizations here
    return config;
  },
};

You must return the modified config object at the end of the function.

The options Parameter

The second argument passed to the webpack function is an object containing critical build context properties:

  • isServer (boolean): Indicates whether the current compilation target is for the server (true) or the client browser (false).
  • dev (boolean): Indicates whether the compilation is running in development mode (next dev) or production mode (next build).
  • buildId (string): A unique build identifier generated for the current build session.
  • nextRuntime (string | undefined): Present when isServer is true. Its value is either 'nodejs' or 'edge', denoting the execution environment for server-side code.
  • defaultLoaders (object): Exposes Next.js's internal loader configurations, such as defaultLoaders.babel, enabling you to apply standard Next.js compilation passes to custom rules.
  • webpack (object): The active Webpack instance. This allows you to reference built-in Webpack plugins (e.g., options.webpack.DefinePlugin, options.webpack.IgnorePlugin) without manually installing or importing webpack as a project dependency.

Common Modification Patterns

1. Target-Specific Adjustments

Because Next.js runs multiple Webpack compilers (client, Node.js server, and Edge runtime), use options.isServer to prevent client-side packages from leaking into the server bundle, or vice versa.

module.exports = {
  webpack: (config, { isServer }) => {
    if (!isServer) {
      // Prevent server-only modules from being bundled on the client
      config.resolve.fallback = {
        ...config.resolve.fallback,
        fs: false,
        net: false,
      };
    }
    return config;
  },
};

2. Adding Custom Loaders

To process non-standard file types, push a new rule into config.module.rules:

module.exports = {
  webpack: (config) => {
    config.module.rules.push({
      test: /\.svg$/,
      use: ['@svgr/webpack'],
    });

    return config;
  },
};

3. Injecting Plugins Using the Provided Instance

Instantiate Webpack plugins directly via the webpack property in options to avoid version mismatches with the Next.js bundled Webpack version:

module.exports = {
  webpack: (config, { webpack }) => {
    config.plugins.push(
      new webpack.DefinePlugin({
        'process.env.BUILD_TIMESTAMP': JSON.stringify(Date.now()),
      })
    );

    return config;
  },
};

Key Considerations

  • Return Value: The function must always return the modified config object. Returning undefined will break the build process.
  • Avoid Overwriting Rules: Mutating existing rules directly instead of appending or prepending can disrupt built-in Next.js features such as CSS modules, PostCSS integration, and SWC/Babel transforms.
  • Turbopack Notice: Customizations made in the webpack hook only apply when Next.js uses Webpack. If running Next.js with Turbopack (--turbo), this function is bypassed.
