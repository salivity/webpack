Webpack 5 output.workerChunkLoading Explained

In Webpack 5, the output.workerChunkLoading configuration option defines the mechanism Webpack uses to load on-demand chunks inside Web Workers. As modern web applications increasingly rely on background threads for intensive tasks, code-splitting within workers requires a reliable runtime strategy to fetch additional scripts. This article explains the purpose of output.workerChunkLoading, the values it accepts, and how to choose the right strategy based on your worker architecture and runtime target.

What is output.workerChunkLoading?

When Webpack compiles Web Workers—typically instantiated using standard syntax like new Worker(new URL('./worker.js', import.meta.url))—it supports dynamic imports and code splitting inside the worker scope. Because a worker runs in a separate global execution context (DedicatedWorkerGlobalScope) distinct from the main window object, the standard DOM-based chunk loading methods (such as injecting <script> tags via output.chunkLoading: 'jsonp') cannot function.

output.workerChunkLoading solves this by explicitly specifying how the worker runtime should fetch and execute additional JavaScript chunks.

Available Configuration Values

Webpack 5 supports several values for output.workerChunkLoading:

  • 'importScripts': This is the default mechanism for classic Web Workers. Webpack generates runtime code that calls the worker's native importScripts() API to synchronously fetch and execute code-split chunks.
  • 'import': Designed for modern ECMAScript module (ESM) workers (created via { type: 'module' }). When set to 'import', Webpack uses native dynamic import() statements to load chunks asynchronously as modules.
  • false: Completely disables chunk loading inside workers. If any code inside a worker triggers code-splitting or dynamic imports, Webpack will emit a compilation error.

Why You Need to Configure It

By default, Webpack attempts to infer the correct mechanism based on your compilation targets, such as target: 'web' or output.module. However, explicit configuration is often necessary in specific scenarios:

  1. Migrating to Module Workers: If you configure Webpack to output native ES modules using experiments.outputModule: true and instantiate workers with new Worker(..., { type: 'module' }), setting workerChunkLoading: 'import' ensures Webpack relies on native module imports instead of importScripts, which is disallowed in standard module workers across modern browsers.
  2. Strict Content Security Policies (CSP): In environments where CSP restricts the use of importScripts or evaluates it under strict script-src directives, aligning chunk loading to use standard module fetching ('import') helps maintain compliance.
  3. Cross-Platform Runtimes: When bundling for environments such as Node.js worker threads or hybrid desktop frameworks (like Electron), explicitly defining this setting ensures chunks resolve through supported file system or module protocols rather than browser-specific APIs.

Configuration Example

You can define workerChunkLoading in your webpack.config.js under the output block:

module.exports = {
  target: 'web',
  output: {
    filename: '[name].bundle.js',
    // Specifies chunk loading strategy for Web Workers
    workerChunkLoading: 'import',
  },
  experiments: {
    outputModule: true,
  },
};

Using output.workerChunkLoading ensures your background workers handle code splitting accurately, preventing runtime reference errors and maintaining compatibility with your application's module architecture.
