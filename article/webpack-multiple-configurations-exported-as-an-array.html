Webpack Multiple Configurations Exported as an Array

When you export an array of configuration objects from a Webpack configuration file, Webpack activates its MultiCompiler feature to process each configuration independently within a single execution. This article explains how Webpack processes these configurations simultaneously, manages execution order and system resources, and handles outputs, along with the standard use cases and trade-offs of this approach.

The MultiCompiler Mechanism

When Webpack detects an array exported from webpack.config.js (for example, module.exports = [clientConfig, serverConfig]), it does not instantiate a standard single Compiler. Instead, it instantiates a MultiCompiler.

The MultiCompiler acts as a wrapper that manages a collection of discrete Compiler instances. Each configuration object in the array receives its own isolated lifecycle, compilation pipeline, dependency graph, entry points, loaders, and plugin instances.

// webpack.config.js
const path = require('path');

const clientConfig = {
  name: 'client',
  target: 'web',
  entry: './src/client.js',
  output: {
    path: path.resolve(__dirname, 'dist/client'),
    filename: 'bundle.js',
  },
};

const serverConfig = {
  name: 'server',
  target: 'node',
  entry: './src/server.js',
  output: {
    path: path.resolve(__dirname, 'dist/server'),
    filename: 'server.js',
  },
};

module.exports = [clientConfig, serverConfig];

Concurrency and Resource Allocation

By default, Webpack runs the compilers in parallel or concurrently depending on your environment. You can control the degree of parallelism using the --parallelism flag in the Webpack CLI:

npx webpack --parallelism 2

Because each configuration runs through its own compilation pipeline, memory usage scales proportionally with the number of configurations. When compiling large applications, running too many configurations simultaneously can lead to out-of-memory errors. Setting an explicit limit on parallelism ensures Webpack schedules builds sequentially or in smaller batches.

Configuration Independence

Each configuration in the array must be completely self-contained:

  • Plugins: Plugin instances are not shared between configurations. If you use a plugin like HtmlWebpackPlugin in both builds, each configuration must instantiate its own copy.
  • Output Paths: Each configuration should define a unique output.path or ensure that filenames do not collide; otherwise, one compiler may overwrite the artifacts of another.
  • Loaders and Resolve Rules: Module resolution and transformations are isolated. Settings defined in one configuration object do not bleed into adjacent objects.
  • Naming and Dependencies: You can assign a name property to each configuration. Webpack allows defining dependencies between configurations using the dependencies array (e.g., dependencies: ['client']), which instructs Webpack to wait for the specified configuration to finish before starting the dependent one.

Webpack Dev Server Behavior

When using webpack-dev-server with an array configuration, the server inspects the configurations to determine how to serve assets. By default, the server serves assets generated by all compilers, but dev server configurations (such as port, proxy, and history fallback) are typically sourced only from the first configuration object in the array, or from a specific configuration that defines a devServer block.

Common Use Cases

  • Server-Side Rendering (SSR): Generating a Node.js-targeted bundle for server execution alongside a browser-targeted bundle for client hydration.
  • Modern vs. Legacy Builds: Generating one bundle with modern JavaScript syntax for evergreen browsers and a separate, transpiled bundle with polyfills for legacy browsers.
  • Multi-Format Libraries: Compiling a shared library simultaneously into CommonJS, ESM, and UMD formats from a single command.
