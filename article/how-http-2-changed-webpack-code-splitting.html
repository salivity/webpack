How HTTP/2 Changed Webpack Code-Splitting

This article examines how the introduction of HTTP/2 revolutionized code-splitting strategies in Webpack applications. By shifting from the connection constraints of HTTP/1.1 to the multiplexing capabilities of HTTP/2, developers moved away from serving massive monolithic bundles toward smaller, granular chunks that maximize cache efficiency without incurring severe network latency penalties.

The HTTP/1.1 Bottleneck and Bundling

Under HTTP/1.1, browsers were restricted to opening a limited number of concurrent TCP connections per domain—typically six. Each connection could only handle one request-response cycle at a time, creating a bottleneck known as head-of-line blocking.

Because opening new connections and managing request overhead was expensive, frontend best practices favored aggressive bundling. Webpack was primarily configured to merge application code and third-party dependencies into a minimal number of large files, typically an app.js and a vendor.js. While this solved network latency issues under HTTP/1.1, it introduced a significant caching drawback: a single-line change to your application code or a minor package update forced users to re-download the entire multi-megabyte bundle.

The HTTP/2 Paradigm Shift

HTTP/2 resolved the primary constraints of HTTP/1.1 by introducing binary framing and multiplexing. Through multiplexing, a browser can send and receive multiple requests and responses simultaneously over a single persistent TCP connection.

This architectural change eliminated the high latency cost associated with requesting multiple individual files. As a result, the necessity of creating massive, consolidated bundles disappeared, opening the door for far more aggressive code-splitting.

Granular Code-Splitting in Webpack

With HTTP/2, Webpack applications adopted "granular chunking." Instead of bundling all dependencies into one monolithic vendor file, Webpack’s SplitChunksPlugin can be configured to split code into smaller, module-specific chunks.

This approach yields two major advantages:

  1. Superior Cache Invalidation: When third-party libraries are isolated into their own chunks (for example, splitting React, Lodash, and routing libraries into separate files), updating one package only invalidates the cache for that specific module. The rest of the dependencies remain cached in the user's browser.
  2. On-Demand Loading: Applications can load code strictly when needed. Webpack can dynamically import routes and heavy components, fetching only the exact byte payload required for the current view over the multiplexed connection.

The Limits of Unbundling

While HTTP/2 reduced the overhead of multiple requests, it did not make bundling obsolete. Completely unbundled applications (serving thousands of individual raw files) still suffer from performance issues due to:

  • Compression Inefficiency: Compression algorithms like Gzip and Brotli perform significantly better on larger files with repetitive dictionaries than across hundreds of tiny, isolated files.
  • Browser Execution Overhead: Browsers still incur parsing, execution, and stream-management overhead when handling an excessive number of micro-files.

Modern Best Practices

Modern Webpack configurations find a balance between the two extremes. Webpack now uses default splitChunks thresholds designed for HTTP/2 environments, targeting chunks between 20KB and 50KB. This granular approach leverages HTTP/2 multiplexing for efficient parallel transfers and targeted cache invalidation, while retaining sufficient bundle size to allow compression algorithms to work effectively.
