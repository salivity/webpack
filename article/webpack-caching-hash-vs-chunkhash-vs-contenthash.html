Webpack Caching: Hash vs Chunkhash vs Contenthash

Webpack provides three distinct hashing strategies—[hash] (referred to as [fullhash] in modern Webpack versions), [chunkhash], and [contenthash]—to control how file names are generated for browser cache invalidation. By appending a unique cryptographic digest to the generated asset filenames, developers can leverage aggressive, long-term browser caching (using HTTP headers like Cache-Control: immutable) while ensuring users immediately download updated assets whenever changes occur. Selecting the correct hashing algorithm is critical to avoid unnecessary cache busts across unchanged assets.

[hash] (or [fullhash])

The [hash] placeholder generates a hash based on the entire build process.

  • How it works: A single hash is calculated for the compilation as a whole. If any single file in any part of the project is modified, the hash for the entire build changes.
  • Impact on caching: Every single output file—regardless of whether its underlying source code changed—will receive a new filename.
  • Use case: This strategy is rarely recommended for production deployments because modifying a simple line of CSS or an isolated component invalidates the browser cache for every file in the bundle. It is occasionally used in development or simple setups where granular caching is not a priority.

[chunkhash]

The [chunkhash] placeholder generates a hash based on the specific Webpack chunk to which an asset belongs.

  • How it works: Webpack creates chunks based on entry points and dynamic imports. A change inside an entry point or its imported modules only changes the hash of that particular chunk. Other unrelated entry points and independent chunks keep their original hashes.
  • Impact on caching: This provides significantly better cache retention than [fullhash], as users only re-download chunks that contain modified code.
  • Caveat: If you extract CSS into a separate file using plugins like MiniCssExtractPlugin within the same chunk as your JavaScript, both the generated .js and .css files historically shared the same [chunkhash]. Modifying only the JavaScript would cause the stylesheet's hash to update as well, forcing an unnecessary download of unchanged CSS.

[contenthash]

The [contenthash] placeholder generates a hash based strictly on the exact content of the individual asset file itself.

  • How it works: The hash is computed after the file has been fully processed and rendered. If a file's final output bytes do not change, its hash will remain identical, regardless of build changes elsewhere in the project or even within the same entry chunk.
  • Impact on caching: This provides the most precise and efficient caching strategy available in Webpack. If you update JavaScript in an entry file, only that specific .js file's hash changes; an extracted .css file from the same chunk retains its previous hash if its style rules were untouched.
  • Use case: This is the industry-standard recommendation for production output configurations.

Recommended Configuration

For optimal production performance, use [contenthash] on all generated output files, including JavaScript bundles, extracted stylesheets, and assets:

module.exports = {
  output: {
    filename: '[name].[contenthash].js',
    chunkFilename: '[name].[contenthash].chunk.js',
    clean: true,
  },
  plugins: [
    new MiniCssExtractPlugin({
      filename: '[name].[contenthash].css',
      chunkFilename: '[id].[contenthash].css',
    }),
  ],
};

Using [contenthash] guarantees that clients only download the files that have genuinely changed, maximizing cache hits and minimizing load times for returning users.
