Understanding exportsType in Webpack Configuration

In Webpack, configuring how code is exported and consumed requires a clear understanding of module resolution and library output settings. This article explains the exact role of exportsType within Webpack, clarifies how it directs the compiler to interpret module export structures, and breaks down related library settings—specifically output.library.type and output.library.export—that control how a packaged library is distributed to consumers.

The Role of exportsType in Webpack

Technically, exportsType is configured at the module parser level via Rule.parser.javascript.exportsType. It informs Webpack how an imported dependency or library exposes its exports, dictating how import statements (import ... from '...') interact with non-ECMAScript modules (such as CommonJS or JSON).

When dealing with third-party libraries or internal packages, Webpack automatically analyzes code to identify module formats. However, automated detection can occasionally cause interoperability issues between ES Modules (ESM) and CommonJS. Setting exportsType explicitly overrides this detection to enforce predictable behavior.

Supported Values for exportsType

Webpack supports several distinct values for exportsType:

  • auto (Default): Webpack analyzes the module to determine whether it behaves like an ES Module or CommonJS, applying standard interoperability rules.
  • default: Treats the entire module output as a single default export. Importing named bindings from this module is disallowed or yields undefined.
  • named: Treats all properties on the module's export object (module.exports) as separate named exports.
  • namespace: Treats the module as a full namespace object where all exports, including default and named properties, are wrapped into a synthetic ESM namespace.
  • dynamic: Determines exports dynamically at runtime, commonly used when exports cannot be statically analyzed ahead of time.

exportsType vs. output.library.type

In library development, developers frequently confuse exportsType with output.library.type. While exportsType controls how Webpack interprets incoming code, output.library.type controls how Webpack packages outgoing code.

To bundle a project as a reusable library, configure output.library.type in webpack.config.js:

module.exports = {
  output: {
    library: {
      name: 'MyLibrary',
      type: 'umd',
    },
  },
};

Common values for output.library.type include:

  • var: Exposes the library as a global variable.
  • commonjs / commonjs2: Formats the output for Node.js environments using exports or module.exports.
  • module: Emits the bundle as a native ES Module (requires experiments.outputModule: true).
  • umd: Creates a Universal Module Definition compatible with AMD, CommonJS, and script tags.

Targeting Specific Exports with output.library.export

Another configuration often tied to library export behavior is output.library.export. This option specifies which internal export from your entry point should be assigned to the library interface.

module.exports = {
  output: {
    library: {
      name: 'MyLibrary',
      type: 'var',
      export: 'default',
    },
  },
};

If your entry point uses export default MyClass, setting export: 'default' exposes MyClass directly under window.MyLibrary instead of requiring consumers to access window.MyLibrary.default.

Summary

  • Use exportsType under module.rules to define how Webpack's parser resolves the export structure of dependencies.
  • Use output.library.type to determine the output packaging format (such as ESM, CommonJS, or UMD) when building your own library.
  • Use output.library.export to expose a specific property or default export directly as the entry surface of your library.
