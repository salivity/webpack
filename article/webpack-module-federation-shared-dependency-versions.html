Webpack Module Federation Shared Dependency Versions

Webpack Module Federation manages shared dependencies by negotiating and resolving library versions at runtime across distinct builds. This article explains how Webpack's shared scope coordinates dependencies, handles semantic versioning (SemVer) constraints, enforces singleton instances to prevent runtime conflicts, and manages fallback strategies to optimize bundle sizes across host and remote micro-frontend applications.

The Share Scope and Version Negotiation

When configuring Module Federation, developers declare dependencies in the shared array or object within the ModuleFederationPlugin. At runtime, Webpack establishes a global "share scope" (defaulting to the default scope).

When federated applications load, they register their available shared packages, along with their respective versions and loader functions, into this central registry. Before an application executes code requiring a shared module, Webpack consults the share scope:

  1. It collects all registered versions of the requested dependency across the host and all loaded remotes.
  2. It evaluates the version requirements defined by the requesting container.
  3. It resolves to the highest compatible version matching the semantic version range.
  4. It initializes that single version and provides it to all modules that accept that version range.

Managing Singletons and State-Sensitive Libraries

Certain libraries, such as React, React DOM, or state management tools, fail if multiple instances exist simultaneously in memory. Webpack provides the singleton configuration to handle this constraint:

new ModuleFederationPlugin({
  name: 'app',
  shared: {
    react: {
      singleton: true,
      requiredVersion: '^18.2.0',
    },
    'react-dom': {
      singleton: true,
      requiredVersion: '^18.2.0',
    },
  },
});

When singleton: true is set, Webpack ensures that only one instance of the package is loaded across all federated containers. If two remotes provide incompatible versions under a singleton constraint, Webpack still selects only the highest version, but logs a runtime console warning to alert developers of the mismatch.

Strict Version Enforcement

To prevent breaking changes caused by loose SemVer matching or singleton fallbacks, Webpack provides the strictVersion option.

When strictVersion: true is enabled alongside requiredVersion, Webpack will throw a runtime error rather than proceed if a compatible version cannot be found in the share scope. Conversely, if strictVersion is set to false (the default) and singleton is not enforced, Webpack falls back to loading a separate, container-specific version of the library, isolating the micro-frontend without crashing the system.

Asynchronous Loading and the eager Flag

By default, shared dependencies are loaded asynchronously through dynamic imports (import()). This asynchronous boundary gives Webpack the execution pause necessary to inspect the share scope, negotiate versions, and download the negotiated chunks before any application code executes.

Marking a dependency with eager: true bundles that library directly into the initial entry chunk of the application rather than creating an asynchronous chunk. While this removes the need for asynchronous bootstrap boundaries, it bypasses standard runtime negotiation for that dependency, often forcing other remotes to consume that specific bundled version or load their own duplicates. For optimal sharing, keeping dependencies non-eager and wrapping the application entry point in an asynchronous import('./bootstrap') is the recommended pattern.
