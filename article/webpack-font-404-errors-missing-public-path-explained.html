Webpack Font 404 Errors: Missing PublicPath Explained

When bundling web applications with Webpack, developers often encounter 404 Not Found errors when the browser attempts to fetch custom font files referenced in CSS. This issue typically occurs because omitting the publicPath configuration causes the browser to resolve font asset paths relative to the current page URL or the HTML document rather than the correct asset output directory. Without an explicit base path, dynamically routed pages and injected stylesheets misdirect requests, resulting in broken asset loading.

How Webpack Processes Font Assets in CSS

When css-loader encounters a font declaration such as url('./fonts/font.woff2'), it treats the URL as a module dependency. In modern Webpack (version 5), Asset Modules handle this file, emitting the font file into the output directory and rewriting the CSS URL to reference that emitted file.

However, Webpack does not automatically know where those emitted files will reside on your production or development web server. It relies on the output.publicPath configuration option to determine the prefix applied to every emitted asset URL in the generated bundles.

The Role of Relative Paths and Execution Context

If output.publicPath is left undefined or set to an empty string, Webpack outputs relative paths for assets. The browser must then resolve these paths at runtime based on its current execution context. This creates two distinct scenarios where 404 errors occur:

  1. Nested Routes and HTML History API:
    If your application uses client-side routing, a user might visit a nested URL like https://example.com/user/profile. If the generated CSS references a font as fonts/roboto.woff2, the browser resolves this relative to the current path, requesting https://example.com/user/fonts/roboto.woff2. Because the font actually resides at https://example.com/fonts/roboto.woff2, the web server returns a 404 error.

  2. CSS Injected via style-loader:
    During development, developers frequently pair css-loader with style-loader to enable Hot Module Replacement (HMR). style-loader inlines compiled CSS directly into the HTML document using <style> tags. Because the CSS is embedded in the document itself, any relative url() paths are evaluated relative to the document's base URL, not the location of the bundle. On any page other than the root directory, these asset lookups will fail.

Extracted Stylesheets with MiniCssExtractPlugin

When using mini-css-extract-plugin for production builds, CSS is extracted into standalone .css files. If these CSS files are stored in a subdirectory (such as dist/css/main.css) and fonts are saved in another (such as dist/fonts/font.woff2), relative paths must accurately navigate back up the tree (e.g., ../fonts/font.woff2).

Without configuring publicPath either globally in output.publicPath or locally within the MiniCssExtractPlugin.loader options, the rewritten paths frequently fail to account for the directory structure difference between the source files and the compiled output directories.

Resolving the Issue

To fix these 404 errors, configure output.publicPath in your webpack.config.js. Setting this property provides an absolute base URL or server-relative root to which all asset paths prepend:

module.exports = {
  output: {
    publicPath: '/',
    // or a CDN path like 'https://cdn.example.com/assets/'
  },
};

Using a server-relative path (such as /) ensures that regardless of how deeply nested the current browser URL is, or whether the CSS is embedded into a <style> tag, the browser always requests font assets from the absolute root of the server.
