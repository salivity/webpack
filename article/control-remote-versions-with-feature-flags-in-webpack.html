Control Remote Versions with Feature Flags in Webpack

Integrating feature flags with Webpack Module Federation enables engineering teams to dynamically switch, test, and safely roll out different versions of remote micro-frontends at runtime without redeploying the host container. This article covers how dynamic remote resolution works, how to evaluate feature flags to determine remote URLs, and how to execute this pattern reliably in modern web applications.

The Limitation of Static Remotes

By default, Webpack Module Federation configurations define remotes statically within the webpack.config.js file:

// Static declaration
remotes: {
  dashboard: 'dashboard@https://cdn.example.com/v1/remoteEntry.js',
}

Static assignment prevents runtime flexibility. Every client receives the exact same remote version unless the host application is rebuilt and redeployed. To control versions via feature flags, the application must transition from static declarations to dynamic remote loading.

Dynamic Remote Loading Mechanism

Webpack exposes low-level runtime APIs—__webpack_init_sharing__ and __webpack_share_scopes__—that allow micro-frontends to be registered and initialized on demand. By decoupling the remote URL from the build-time configuration, the host can query a feature flagging service (such as LaunchDarkly, Unleash, or a custom API) to decide which remoteEntry.js file to load.

A typical runtime loading utility follows this sequence:

  1. Create a <script> tag pointing to the resolved remote URL.
  2. Append the script to the DOM and wait for it to load.
  3. Initialize the shared scope using __webpack_init_sharing__('default').
  4. Initialize the remote container via container.init(__webpack_share_scopes__.default).
  5. Call container.get(module) to retrieve and render the federated component.

Step-by-Step Implementation

1. Evaluate the Feature Flag

Before mounting a remote component, evaluate the flag with user context (e.g., user ID, tenant, or rollout percentage).

// Fetch flag value from your provider
const remoteVersion = await featureFlagClient.variation(
  'dashboard-microfrontend-version', 
  { fallback: 'v1' }
);

// Map flag variations to deployment URLs
const REMOTE_URLS = {
  v1: 'https://cdn.example.com/dashboard/v1/remoteEntry.js',
  v2: 'https://cdn.example.com/dashboard/v2/remoteEntry.js',
  canary: 'https://cdn.example.com/dashboard/canary/remoteEntry.js',
};

const targetUrl = REMOTE_URLS[remoteVersion];

2. Load the Remote Container Dynamically

Use a helper function to inject the determined remote entry point into the browser runtime:

async function loadComponent(scope, module, url) {
  // Inject remoteEntry script if not already present
  if (!window[scope]) {
    await new Promise((resolve, reject) => {
      const script = document.createElement('script');
      script.src = url;
      script.onload = resolve;
      script.onerror = reject;
      document.head.appendChild(script);
    });
  }

  // Initialize sharing and the container
  await __webpack_init_sharing__('default');
  const container = window[scope];
  await container.init(__webpack_share_scopes__.default);

  // Return the exported module factory
  const factory = await container.get(module);
  return factory();
}

3. Render the Component with Fallbacks

In framework environments such as React, wrap the dynamic loader inside React.lazy and Suspense, backed by an Error Boundary to handle missing scripts or network failures.

import React, { Suspense, useMemo } from 'react';

function DynamicRemoteView({ user }) {
  const version = useFeatureFlag('dashboard-version', user);

  const Component = useMemo(() => {
    const url = `https://cdn.example.com/dashboard/${version}/remoteEntry.js`;
    return React.lazy(() => loadComponent('dashboard', './Widget', url));
  }, [version]);

  return (
    <ErrorBoundary fallback={<div>Failed to load module.</div>}>
      <Suspense fallback={<div>Loading remote...</div>}>
        <Component />
      </Suspense>
    </ErrorBoundary>
  );
}

Alternative: Using Dynamic Remotes in Webpack Configuration

Webpack also supports runtime expression resolution directly in configuration when using external global variables:

// webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        dashboard: `external new Promise((resolve) => {
          const url = window.__REMOTE_URLS__?.dashboard || 'https://cdn.example.com/v1/remoteEntry.js';
          const script = document.createElement('script');
          script.src = url;
          script.onload = () => {
            resolve({
              get: (request) => window.dashboard.get(request),
              init: (arg) => {
                try {
                  return window.dashboard.init(arg);
                } catch (e) {
                  console.error(e);
                }
              }
            });
          };
          document.head.appendChild(script);
        })`,
      },
    }),
  ],
};

In this pattern, the host resolves feature flags before executing the main Webpack bootstrap chunk, populating window.__REMOTE_URLS__ before any federated module imports occur.

Key Considerations

  • Shared Dependency Mismatches: When serving multiple remote versions, ensure shared dependencies (such as React or component libraries) define wide semantic version ranges in shared configurations to avoid version conflicts and duplicate library instances.
  • Cache Management: Remote versions should be deployed to immutable, versioned paths (such as /v1.0.4/remoteEntry.js or content-hashed subdirectories) rather than overwriting a static asset. This avoids browser cache poisoning during flag evaluation transitions.
  • Resilience: Feature flag systems can fail or experience latency. Always implement a stable default remote entry URL to fall back on if the flag evaluation times out or encounters network errors.
