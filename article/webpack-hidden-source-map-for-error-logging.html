Webpack hidden-source-map for Error Logging

This article explains how the hidden-source-map configuration works in Webpack to enable secure error monitoring in production. You will learn the difference between standard source maps and hidden source maps, why omitting the mapping comment protects your proprietary code, and the step-by-step workflow required to upload these files to private logging platforms like Sentry, Datadog, or Bugsnag to reconstruct readable stack traces.

What is hidden-source-map?

In Webpack, setting devtool: 'hidden-source-map' instructs the compiler to generate complete, production-grade source map files (.map) alongside your minified JavaScript bundles, but with one critical distinction: it strips out the //# sourceMappingURL=... comment from the bottom of the generated JavaScript files.

Under standard source mapping configurations (such as source-map), Webpack appends this comment:

// At the bottom of bundle.js
//# sourceMappingURL=bundle.js.map

When a browser encounters that directive, developer tools automatically download the .map file and reconstruct the original, unminified source code directly in the user's browser. With hidden-source-map, that reference comment is completely absent.

Why Use hidden-source-map?

Standard source maps present a security and intellectual property risk when exposed publicly. Anyone opening the browser console can inspect your original source code, internal APIs, and comments.

However, running production applications completely without source maps makes debugging runtime errors difficult, as error reports will only provide minified traces (such as TypeError at a.b (app.min.js:1:3421)).

hidden-source-map solves this problem by decoupling the generation of source maps from public browser access.

How the Error Logging Workflow Works

Integrating hidden-source-map into an automated pipeline follows a four-step process:

1. Configure Webpack

Set your production configuration to generate hidden maps:

// webpack.config.js
module.exports = {
  mode: 'production',
  devtool: 'hidden-source-map',
  output: {
    filename: '[name].[contenthash].js',
    sourceMapFilename: '[file].map',
  },
};

Webpack emits both app.[contenthash].js and app.[contenthash].js.map in your output directory.

2. Upload Maps to the Monitoring Service via CI/CD

During your deployment pipeline, your CI/CD runner captures the .map files and uploads them directly to your private error logging provider's API. Most services provide dedicated CLI tools or Webpack plugins to handle this, tagging the upload with a specific release version or commit hash.

3. Exclude Source Maps from Public Hosting

After the source maps are uploaded to your error monitoring service, your build script must delete or exclude the .map files before the static assets are deployed to your web server, S3 bucket, or CDN. Because the .js files contain no reference to the maps, and the .map files are not publicly accessible, users and search engines cannot access your original source code.

4. Stack Trace Symbolication at Runtime

When an exception occurs in an end-user's browser:

  1. The client-side monitoring SDK catches the unhandled error.
  2. The browser sends the minified stack trace (e.g., file name, line 1, column 4520) along with the release identifier to your error logging service.
  3. The logging service receives the payload, looks up the corresponding private .map file stored during step 2, and performs symbolication.
  4. The error platform displays the reconstructed error with the exact TypeScript or JavaScript source file, component name, and line number where the issue occurred.
