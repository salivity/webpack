Create Reusable Webpack Configurations

Managing duplicate build scripts across multiple repositories often leads to configuration drift and maintenance overhead. By packaging common Webpack settings into a standalone, version-controlled npm package, engineering teams can standardize loaders, plugins, and optimization strategies across all front-end applications. This guide explains how to architect, structure, and consume a reusable Webpack configuration package efficiently using composable presets and modular design patterns.

1. Select the Abstraction Pattern

The most flexible approach to sharing Webpack configurations is exposing a function or composable objects via webpack-merge. Rather than delivering a monolithic, unchangeable build script, provide modular parts (such as base, development, and production configurations) that consumers can extend or override.

Install webpack-merge in your shared configuration package:

npm install --save-dev webpack-merge

2. Design the Package Structure

Create a dedicated repository or monorepo workspace for your shared configuration. A clean structure separates foundational settings from environment-specific behaviors:

webpack-config-shared/
├── package.json
├── index.js
├── src/
│   ├── base.js
│   ├── dev.js
│   └── prod.js

Define your configurations inside the src directory:

src/base.js

module.exports = {
  module: {
    rules: [
      {
        test: /\.(js|jsx|ts|tsx)$/,
        exclude: /node_modules/,
        use: 'babel-loader',
      },
      {
        test: /\.(png|svg|jpg|jpeg|gif)$/i,
        type: 'asset/resource',
      },
    ],
  },
  resolve: {
    extensions: ['.js', '.jsx', '.ts', '.tsx'],
  },
};

src/dev.js

const { merge } = require('webpack-merge');
const base = require('./base');

module.exports = (options = {}) =>
  merge(base, {
    mode: 'development',
    devtool: 'cheap-module-source-map',
    devServer: {
      hot: true,
      port: 3000,
    },
    ...options,
  });

src/prod.js

const { merge } = require('webpack-merge');
const TerserPlugin = require('terser-webpack-plugin');
const base = require('./base');

module.exports = (options = {}) =>
  merge(base, {
    mode: 'production',
    devtool: 'source-map',
    optimization: {
      minimize: true,
      minimizer: [new TerserPlugin()],
    },
    ...options,
  });

index.js

module.exports = {
  createDevConfig: require('./src/dev'),
  createProdConfig: require('./src/prod'),
  baseConfig: require('./src/base'),
};

3. Manage Dependencies Correctly

Handling dependencies properly prevents version conflicts between the shared package and the consuming applications:

  • peerDependencies: Place webpack and webpack-cli here. This ensures the host project provides the core compiler runtime and avoids multiple instances of Webpack being resolved.
  • dependencies: Place shared loaders, plugins, and utilities (such as babel-loader, terser-webpack-plugin, or webpack-merge) here so the consuming application does not have to install every single build dependency manually.

Example package.json:

{
  "name": "@your-org/webpack-config",
  "version": "1.0.0",
  "main": "index.js",
  "peerDependencies": {
    "webpack": "^5.0.0",
    "webpack-cli": "^5.0.0"
  },
  "dependencies": {
    "babel-loader": "^9.0.0",
    "terser-webpack-plugin": "^5.0.0",
    "webpack-merge": "^5.9.0"
  }
}

4. Consume the Package in a Project

Publish the package to an internal or public package registry (e.g., npm or GitHub Packages). In your target application, install the shared package along with the peer dependencies:

npm install --save-dev @your-org/webpack-config webpack webpack-cli

Import and invoke the configuration inside the target application's webpack.config.js:

const { createDevConfig, createProdConfig } = require('@your-org/webpack-config');
const { merge } = require('webpack-merge');

module.exports = (env, argv) => {
  const isProduction = argv.mode === 'production';
  const basePreset = isProduction ? createProdConfig() : createDevConfig();

  // Apply project-specific customizations
  return merge(basePreset, {
    entry: './src/index.js',
    output: {
      filename: '[name].[contenthash].js',
    },
  });
};

This pattern encapsulates build logic, centralizes toolchain upgrades, and leaves consumer applications free to add customized overrides where necessary.
