How Webpack Optimizes export * from Syntax

Webpack optimizes dependencies using the export * from syntax through compile-time static analysis, dependency graph flattening, and advanced tree shaking. While wildcard re-exports historically presented challenges for dead code elimination by obscuring explicit module bindings, modern Webpack versions analyze the underlying exports, trace symbol usage across module boundaries, and eliminate unused code without bundling redundant intermediate logic.

Static Export Mapping

When Webpack encounters export * from './module', it does not treat the export as an unknown dynamic object at runtime. Instead, during the compilation phase, Webpack reads the target module's AST (Abstract Syntax Tree) to determine the exact list of identifiers being exported.

Webpack tracks these symbols using internal optimization flags:

  • providedExports: Webpack traverses the target file and compiles an exhaustive list of all available named exports.
  • usedExports: Webpack tracks which of those re-exported identifiers are actually imported and consumed by other modules downstream.

By pairing providedExports with usedExports, Webpack can determine whether an identifier re-exported via export * is actively referenced. If a symbol from the source module is never imported elsewhere, Webpack marks it as unused.

Deep Tree Shaking and Dead Code Elimination

Once Webpack determines which identifiers are consumed, its tree-shaking mechanism prunes unreferenced exports. If moduleA uses export * from './moduleB', and an application only imports foo from moduleA, Webpack traces foo directly back to moduleB. Any other exports from moduleB that are not consumed anywhere else in the application are stripped from the final bundle, provided they do not produce side effects.

The Role of sideEffects Optimization

The wildcard syntax often appears in "barrel files" (index files aggregating multiple submodules). For Webpack to fully optimize export * from statements across separate files, the package.json file should declare the "sideEffects": false flag (or provide a glob pattern matching side-effect-free files).

When sideEffects: false is present, Webpack can completely bypass the re-exporting module and modules containing unreferenced exports, omitting entire files from the dependency graph rather than merely stripping out individual functions.

Inner Graph Analysis (Webpack 5)

Webpack 5 introduced enhanced "Inner Graph" analysis. In complex dependency chains—such as when an export * re-exports members that conditionally depend on other internal functions—Webpack tracks variable usage across multiple scopes and module hops. This ensures that unused code behind nested export * chains is reliably identified and pruned, even when passed through multiple intermediate files.

Scope Hoisting via Module Concatenation

In production mode, Webpack applies the ModuleConcatenationPlugin (scope hoisting). When modules use ES module syntax with export * from, Webpack can inline the re-exported modules into a single closure. Instead of generating separate runtime wrapper functions and module registry lookups for both the original module and the re-exporting module, Webpack merges them into the same scope and renames colliding variables, significantly reducing bundle size and runtime execution overhead.
