How package.json type: module Affects Webpack

Setting "type": "module" in a package.json file signals to Webpack that all .js files within that package's directory scope must be treated as native ECMAScript Modules (ESM) rather than CommonJS. This article covers how this declaration changes Webpack’s internal resolution algorithms, forces strict compliance with file extensions, alters how dependency entry points are selected, and impacts syntax rules during bundling.

Treatment of .js Files as Native ESM

Without "type": "module", Webpack treats .js files with legacy flexibility, allowing mixed module formats or defaulting to CommonJS semantics unless ES import/export syntax is explicitly detected.

When "type": "module" is present, Webpack treats all .js files within that boundary exactly like .mjs files. This changes how Webpack parses and evaluates the code:

  • CommonJS globals such as require(), module.exports, exports, __dirname, and __filename are no longer available and will trigger runtime errors or compilation warnings.
  • Top-level await is enabled natively within those files.
  • All imports must adhere to strict ESM interoperability rules, meaning you cannot use named imports from CommonJS modules unless Webpack can statically determine them.

Mandatory File Extensions and fullySpecified Resolution

The most noticeable impact of "type": "module" on Webpack 5 is the enforcement of strict path resolution. In the official Node.js ESM specification, file extensions cannot be omitted in relative import statements, and directory index files (like index.js) are not automatically resolved.

Webpack implements this behavior via the resolve.fullySpecified flag, which is enabled automatically for modules evaluated under ESM rules:

  • Extensionless imports fail: An import written as import { helper } from './utils' will fail to compile. Webpack will require import { helper } from './utils.js'.
  • Directory imports fail: An import written as import components from './components' will no longer automatically resolve to ./components/index.js. You must specify the full path including index.js.

If necessary, this behavior can be overridden in webpack.config.js by setting resolve.fullySpecified: false within a module rule, but by default, Webpack enforces this strict behavior to match native Node.js behavior.

Resolution of Package Entry Points (exports vs. main)

When resolving dependencies that declare "type": "module", Webpack prioritizes modern package entry fields:

  1. The exports field: Webpack will prioritize the "import" condition over the "require" condition inside conditional export maps.
  2. The module field: If exports is not defined, Webpack will prefer "module" over "main".
  3. The main field: Used as a fallback, but the target file will still be parsed as an ES module if "type": "module" is present.

This ensures that Webpack loads the pre-bundled ESM variant of third-party libraries, enabling better tree-shaking and dead-code elimination.

Impact on Dynamic Imports

When Webpack encounters dynamic imports (import()) in a package marked with "type": "module", it handles the returned object strictly as an ESM namespace. In CommonJS files, dynamic imports may wrap default exports differently, but under "type": "module", Webpack guarantees standard module namespace behavior where the default export is accessible strictly through the .default property.
