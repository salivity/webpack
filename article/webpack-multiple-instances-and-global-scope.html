Webpack Multiple Instances and Global Scope

When multiple Webpack builds or micro-frontends execute on a single webpage, they risk conflicting over shared global runtime variables responsible for loading asynchronous chunks and managing module registries. Webpack prevents this global scope contamination primarily through runtime isolation mechanisms such as output.uniqueName, modular closures (IIFEs), and scoped chunk-loading functions. This guide explains the mechanisms Webpack uses to isolate execution, prevent runtime collisions, and maintain stability across multi-bundle environments.

The Conflict: Shared Chunk Loading Registries

By default, Webpack needs a mechanism to track, load, and execute split code chunks dynamically. In single-bundle applications, Webpack stores pending chunks on a shared global object attached to the browser's window.

If two completely different applications or micro-frontends load on the same page using default identifiers, they attempt to read from and write to the same global registry. This causes chunk collisions, where one application attempts to execute code chunks that belong to the other, resulting in uncaught TypeError exceptions, module-not-found errors, or broken component lifecycles.

Webpack 5: Automatic Isolation via output.uniqueName

Webpack 5 resolves this issue by introducing output.uniqueName. Instead of using a static global variable, Webpack dynamically namespaces chunk loading mechanisms using a unique identifier.

Under the hood, Webpack sets its chunk-loading array to:

window["webpackChunk" + output.uniqueName]

By default, Webpack automatically computes output.uniqueName from the name field in your project's nearest package.json. If your projects have distinct package names (such as @org/navbar and @org/dashboard), their global chunk arrays become window["webpackChunk_org_navbar"] and window["webpackChunk_org_dashboard"], completely eliminating global collisions without manual configuration.

If package names are not unique or are not defined, you can set the property explicitly in webpack.config.js:

module.exports = {
  output: {
    uniqueName: 'myCustomMicroApp',
  },
};

Legacy Isolation: output.jsonpFunction in Webpack 4

In Webpack 4 and earlier versions, chunk arrays were stored under window["webpackJsonp"] by default. Multiple instances on the same page would overwrite this shared array.

To prevent contamination in Webpack 4, developers had to manually rename the property via output.jsonpFunction:

module.exports = {
  output: {
    jsonpFunction: 'webpackJsonp_myCustomApp',
  },
};

Webpack 5 deprecated output.jsonpFunction in favor of output.chunkLoadingGlobal, which works alongside output.uniqueName to ensure backward and forward compatibility.

Module Scoping via IIFEs and Closures

Beyond chunk loading, Webpack ensures that internal modules do not leak into the global window object. During compilation, each module is wrapped inside an Immediately Invoked Function Expression (IIFE) or compiled into native ES Module formats, depending on your target configuration.

The internal module registry (__webpack_modules__) and the require cache (__webpack_module_cache__) are declared as local variables inside this closure. Even if dozens of Webpack bundles run side by side, their internal functions, variables, and imported libraries stay completely sandboxed within their respective closure scopes.

Controlled Sharing via Module Federation

In micro-frontend architectures where instances intentionally need to communicate or share dependencies (such as React or Lodash), Webpack 5 uses Module Federation.

Rather than polluting the global scope, Module Federation provides a controlled initialization phase. A host container queries remote containers via a scoped container object (defined via the library configuration), negotiating versions and sharing module instances through an isolated shared scope object passed explicitly at runtime, rather than assigning variables directly to window.
