Webpack CSS Modules and Local Scoping Explained

Webpack handles CSS Modules and local scoping by transforming standard CSS class selectors into unique identifiers during the build process, preventing naming collisions across an application. By pairing Webpack's build pipeline with specific loaders, developers can write modular CSS where styles are scoped strictly to the component that imports them. This article explains how Webpack processes, transforms, and exports CSS Modules, transforming generic class names into uniquely hashed selectors.

The Role of Loaders

Webpack inherently understands only JavaScript and JSON. To process CSS and implement CSS Modules, it relies on a pipeline of loaders—primarily css-loader combined with either style-loader or MiniCssExtractPlugin.loader.

  1. css-loader: This loader handles the heavy lifting of CSS Modules. When configured with the modules option enabled, it parses the CSS, resolves @import and url() statements, and executes the scoping transformation.
  2. style-loader or MiniCssExtractPlugin: After css-loader parses the file, style-loader injects the resulting CSS into the DOM via <style> tags during runtime, or MiniCssExtractPlugin extracts the CSS into dedicated physical files during production builds.

The Scoping Mechanism and Selector Hashing

By default, standard CSS selectors exist in a single global namespace. When css-loader encounters a file designated as a CSS Module (commonly matching *.module.css), it treats all class names and animation names as local by default (equivalent to wrapping them in a :local(...) pseudo-selector).

During compilation, Webpack runs each local selector through an identifier generator. This generator replaces standard class names with unique hashes based on rules defined in the Webpack configuration via the localIdentName option.

A typical pattern format is: [name]__[local]--[hash:base64:5]

  • [name]: The file name of the CSS file.
  • [local]: The original class name written in the source code.
  • [hash:base64:5]: A unique hash generated from the file path and content.

For instance, a selector written as .button inside Header.module.css might be transformed into: .Header__button--3a8F1

Because the hash depends on the file's path and contents, identical class names in different files (such as .button in Header.module.css versus .button in Card.module.css) produce distinct strings, eliminating selector collision.

The JavaScript Mapping Export

Webpack bridges the gap between transformed CSS and JavaScript by generating a key-value dictionary.

When a component imports a module:

import styles from './Header.module.css';

Webpack’s css-loader compiles this import into a JavaScript object where:

  • The keys are the original class names written by the developer (e.g., button).
  • The values are the newly generated, hashed class names (e.g., Header__button--3a8F1).

When rendering elements, applying styles.button references the compiled value. The final HTML contains the hashed class name, matching the selector generated in the bundled CSS file.

Global vs. Local Escaping

Webpack also processes explicit scope flags within CSS Modules:

  • :local: The default state. Enforces class hashing and inclusion in the JavaScript mapping dictionary.
  • :global: An escape hatch. Selectors wrapped in :global(.className) are preserved as plain, unhashed strings (e.g., .className). Webpack leaves these selectors intact in the final stylesheet and does not add them to the exported JavaScript mapping object, allowing integration with third-party libraries or global design systems.
