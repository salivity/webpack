typed-css-modules with Webpack css-loader

This article explains how Webpack's css-loader and the typed-css-modules utility interact to provide complete type safety for CSS Modules in a TypeScript project. It covers the division of responsibilities between compile-time static analysis and runtime asset bundling, detailing how type definitions are generated, consumed, and synchronized with your build pipeline.

The Role of css-loader

Webpack’s css-loader interprets @import and url() statements within CSS and resolves them. When configured with the modules option enabled, it treats CSS files as CSS Modules.

In this mode, css-loader scopes class names locally by replacing standard class selectors with uniquely hashed strings (for example, converting .header to _header_1x8q9_1). When you import a CSS file into a JavaScript or TypeScript file, css-loader returns a JavaScript object where the original class names serve as keys and the hashed class names serve as the corresponding string values.

The Problem in TypeScript

TypeScript is unaware of CSS files by default. If you write:

import styles from './Button.module.css';

The TypeScript compiler (tsc) will throw an error stating that the module cannot be found. While a common workaround is declaring a wildcard ambient module (declare module '*.module.css'), this solution assigns the any or { [key: string]: string } type to the imported object. This eliminates type safety, preventing autocompletion and allowing invalid class names to pass compilation undetected.

The Role of typed-css-modules

typed-css-modules (often run via the CLI as tcm) solves the static typing issue. It parses CSS files, extracts all declared class selectors, and automatically generates matching TypeScript definition files (.d.ts) alongside the original stylesheets.

For example, given a file named Button.module.css:

.primaryButton {
  background-color: blue;
}
.label {
  color: white;
}

typed-css-modules generates Button.module.css.d.ts:

declare const styles: {
  readonly primaryButton: string;
  readonly label: string;
};
export default styles;

How typed-css-modules and css-loader Interact

typed-css-modules and css-loader do not interact directly; instead, they operate in parallel to handle compile-time verification and runtime execution independently.

  1. Compile-Time Static Analysis (TypeScript + typed-css-modules):
    Before or during the TypeScript compilation step, typed-css-modules analyzes the source CSS and outputs .d.ts files. When TypeScript compiles your .tsx or .ts files, it reads these generated .d.ts files. TypeScript validates that any accessed properties (e.g., styles.primaryButton) actually exist, providing intellisense and catching typos during development.

  2. Bundle-Time Processing (Webpack + css-loader):
    When Webpack bundles the application, it invokes css-loader. The loader ignores the generated .d.ts files and directly processes the source .css files, scoping the classes and creating the actual JavaScript module exports that supply class name strings at runtime.

Ensuring Naming Consistency

Because typed-css-modules creates types based on the raw CSS while css-loader transforms classes during bundling, configuration options must match between the two tools:

  • CamelCase Transformations: If you use kebab-case classes in your CSS (e.g., .primary-button) and configure css-loader with localsConvention: 'camelCase' or exportLocalsConvention: 'camelCase', css-loader exports the key as primaryButton. You must also supply the --camelCase flag to typed-css-modules so that the generated .d.ts file reflects the camelCase property name instead of the kebab-case string.
  • Synchronization in Pipelines: In a typical development environment, typed-css-modules runs in a watch process (tcm -w src) alongside the Webpack development server, ensuring definitions are regenerated whenever a CSS file is modified.
