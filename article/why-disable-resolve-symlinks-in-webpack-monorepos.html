Why Disable resolve.symlinks in Webpack Monorepos

Webpack resolves symlinks to their real path by default, which can introduce critical module resolution errors, duplicated dependencies, and broken singletons in monorepo architectures. Tools like Yarn Workspaces, npm workspaces, and pnpm rely heavily on symlinks to link shared local packages into consuming applications. Disabling resolve.symlinks by setting it to false alters how Webpack traverses the directory tree, forcing it to resolve nested dependencies relative to the symlink's location rather than its canonical path on disk.

How Webpack Handles Symlinks by Default

By default, Webpack sets resolve.symlinks: true. When Webpack encounters an imported package that is a symlink, it uses the Node.js fs.realpath equivalent to determine the file's canonical location.

For example, if packages/app depends on a local monorepo package packages/ui, a symlink exists at: packages/app/node_modules/@monorepo/ui -> packages/ui

With resolve.symlinks: true, Webpack resolves the path to packages/ui/src/index.js.

The Dependency Lookup Problem

Node's module resolution algorithm searches for dependencies by walking up the directory tree from the importing file until it finds a node_modules directory. When Webpack uses the canonical path (packages/ui), the search path becomes:

  1. packages/ui/node_modules
  2. packages/node_modules
  3. /node_modules (the monorepo root)

Webpack completely bypasses packages/app/node_modules. This creates several major issues:

1. Duplicate Dependency Instances (Broken Singletons)

Libraries like React, GraphQL, and styled-components rely on single instances at runtime. If packages/app and packages/ui both import React, resolving the symlink to packages/ui can cause Webpack to bundle two distinct copies of React—one from the root or local node_modules and one from the application. This typically results in fatal runtime errors, such as React's "Invalid hook call" error.

2. Broken Peer Dependencies

Shared internal packages often declare peer dependencies (like @angular/core or react) that are meant to be provided by the consumer application (packages/app). When Webpack jumps to the real path of packages/ui, it expects the peer dependencies to exist in the ancestry of packages/ui. If they are only installed in packages/app/node_modules, Webpack fails to resolve them entirely.

3. Inconsistent Build Contexts

When loaders (such as babel-loader or ts-loader) process files based on include or exclude regex rules, canonical paths can break these filters. A rule intended to exclude /node_modules/ might fail to match, or a rule targeting only files inside packages/app/src will unexpectedly process files from packages/ui because their real paths sit outside the expected root.

Why Disabling resolve.symlinks Solves the Issue

Setting resolve.symlinks: false in your webpack.config.js instructs Webpack to treat the symlink itself as the actual directory path:

module.exports = {
  resolve: {
    symlinks: false,
  },
};

With this configuration, when packages/app imports @monorepo/ui, Webpack views the file path as: packages/app/node_modules/@monorepo/ui/src/index.js

Module resolution now walks up the consumer tree:

  1. packages/app/node_modules/@monorepo/ui/node_modules
  2. packages/app/node_modules
  3. packages/node_modules
  4. /node_modules (the root)

This lookup hierarchy ensures that any dependencies imported by the shared module are resolved using the consuming application's node_modules directory first, preventing multiple instances of shared libraries and allowing peer dependencies to resolve as intended.
