Incompatible Shared UI Libraries in Webpack Micro-Frontends

When two micro-frontends load incompatible versions of a shared UI component library, Webpack’s runtime behavior depends on how the shared configuration in Module Federation is set up. This article explores what occurs when version mismatches arise, detailing runtime crashes, CSS and context collisions, performance degradations, and the specific mechanisms Webpack uses to handle conflicting dependencies.

The Role of Webpack Module Federation

Webpack Module Federation allows independent builds to share code dynamically using the shared configuration. When declaring a shared UI library (like Material UI, Ant Design, or an internal design system), developers typically configure parameters such as singleton, requiredVersion, and strictVersion. How Webpack reacts to incompatible versions depends entirely on whether the library is forced to act as a singleton or allowed to fall back to multiple instances.

Scenario 1: The UI Library is Configured as a Singleton

If the shared configuration sets singleton: true, Webpack enforces that only one instance of the UI library is loaded in the browser, regardless of how many micro-frontends request it.

  • Version Negotiation: Webpack attempts to resolve the highest version satisfying all remotes. If Host A requires version ^1.0.0 and Remote B requires version ^2.0.0, Webpack chooses version 2.x because it is the highest available.
  • Breaking API Changes and Runtime Crashes: If version 2.x introduces breaking changes—such as removed props, altered component exports, or modified hooks—Host A will crash at runtime with errors like TypeError: Cannot read properties of undefined or React.createElement: type is invalid.
  • Strict Version Enforcement: If strictVersion: true is also configured alongside singleton: true, Webpack will not negotiate. It will halt execution and throw a runtime error in the console warning that the required version range is not satisfied, preventing partial or corrupt rendering. If strictVersion: false, Webpack prints a console warning and proceeds with the highest version anyway, risking unhandled exceptions.

Scenario 2: The UI Library is Not a Singleton (Multiple Instances Allowed)

If singleton: false (or left unset), Webpack isolates the incompatible versions. It provides version 1.x to Host A and loads a second copy of version 2.x for Remote B. While this prevents direct JavaScript API mismatches, it creates other critical issues:

  • React Context Fragmentation: Most modern UI component libraries rely on React Context for themes, toast notifications, localization, and modal state. React Context relies on reference equality. If a component from version 1.x is wrapped inside a ThemeProvider from version 2.x, the child component cannot read the parent's context. This causes unstyled components, broken design tokens, or crashes due to missing context consumers.
  • Global CSS and Class Name Collisions: Many UI libraries use CSS class naming conventions (e.g., .btn, .modal) or CSS-in-JS solutions with deterministic class generation (e.g., .css-1a2b3c). Loading two versions simultaneously often results in style leaking, where CSS rules from the newer library overwrite the rules of the older library, causing severe visual defects across the application.
  • Increased Bundle Size and Memory Usage: Loading multiple instances of a heavy component library undermines the main performance benefit of micro-frontends. Network transfer sizes double for that dependency, and duplicate DOM nodes and scripts increase overall browser memory consumption.

How to Mitigate Incompatibility Issues

To prevent these failures, adopt the following practices:

  1. Strict Semantic Versioning: Treat your shared UI library as an external contract. Do not introduce breaking changes without planning coordinated deployments across all consuming micro-frontends.

  2. Explicit Shared Configurations: Define exact rules in webpack.config.js:

    shared: {
  '@my-org/ui-library': {
    singleton: true,
    strictVersion: true,
    requiredVersion: '^2.0.0',
  },
}

  3. Prefix CSS and Class Names: Configure CSS-in-JS generators or CSS Modules with unique prefixes per micro-frontend or major version to prevent runtime style overrides.

  4. Decouple UI Primitives from Business Logic: Keep the shared library lightweight, limiting it to stateless design tokens and primitives, while keeping complex state and logic contained within each individual micro-frontend.
