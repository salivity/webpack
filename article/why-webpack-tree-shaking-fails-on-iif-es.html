Why Webpack Tree Shaking Fails on IIFEs

Immediately Invoked Function Expressions (IIFEs) present a significant challenge for Webpack's tree shaking mechanism because they execute automatically at runtime, making it difficult for static analysis to determine if they are safe to remove. While Webpack can easily track and eliminate unused ECMAScript module (ESM) exports, it adopts a conservative approach toward IIFEs to avoid breaking code that relies on side effects. Consequently, unused IIFE blocks often remain in the final production bundle unless explicitly marked as side-effect-free.

The Role of Static Analysis in Tree Shaking

Tree shaking relies on the static structure of ES modules (import and export statements). Because ES module dependencies are deterministic and known at compile time before any code runs, Webpack can build an abstract syntax tree (AST) and mark exports that are never imported elsewhere in the application. The actual dead-code elimination is then deferred to a minifier, typically Terser, which strips out declarations marked as unused.

The Problem with Immediate Execution

Unlike plain function declarations that only execute when called, an IIFE runs the moment the script is evaluated. From a bundler's perspective, whether the returned value of an IIFE is assigned to an unused variable is irrelevant; the execution itself has already occurred.

Because JavaScript is a dynamic, highly mutable language, an IIFE can easily perform operations outside its immediate scope. Common side effects include:

  • Modifying global objects such as window or document.
  • Reading or writing to localStorage or sessionStorage.
  • Mutating external variables or prototypes.
  • Setting timers via setTimeout or setInterval.
  • Triggering network requests or logging to the console.

The Halting Problem and Conservative Bundling

To safely delete an unreferenced IIFE, Webpack and Terser must guarantee that running it produces zero observable side effects. Determining whether arbitrary, non-trivial JavaScript code has side effects is fundamentally equivalent to solving the halting problem.

Analyzing complex operations, deep object references, or calls to external libraries within an IIFE is computationally impractical and prone to false negatives. If a bundler incorrectly prunes an IIFE that configured a necessary global polyfill or registered a DOM listener, it would silently break the application. Therefore, bundlers follow a strict rule: if an expression cannot be proven pure with absolute certainty, it must be preserved.

Resolving the Issue: Annotations and ESM

To allow Webpack to eliminate dead IIFEs, developers must provide explicit hints to the compiler:

  1. /*#__PURE__*/ Annotations: Placing a /*#__PURE__*/ comment immediately before an IIFE tells Terser and Webpack that the function call has no side effects. If its result is unused, the entire expression can be pruned safely. Transpilers like Babel and TypeScript can generate these annotations automatically in many cases.
  2. sideEffects in package.json: Setting "sideEffects": false tells Webpack that the entire module or package contains no side effects, permitting more aggressive elimination of unreferenced files even if they contain top-level IIFEs.
  3. Migrating to Pure ES Modules: Refactoring code away from legacy patterns—such as Universal Module Definition (UMD) wrappers that bundle code inside outer IIFEs—into native import and export statements allows Webpack to analyze and prune code paths natively without relying on heuristic side-effect detection.
