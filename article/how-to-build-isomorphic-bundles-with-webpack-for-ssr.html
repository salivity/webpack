How to Build Isomorphic Bundles with Webpack for SSR

Creating an isomorphic (universal) JavaScript bundle with Webpack allows the same codebase to run in both Node.js for server-side rendering (SSR) and client browsers for hydration. Because the execution environments differ significantly, achieving this requires a dual-target build system rather than a single unified bundle. This guide explains how to configure Webpack to output optimized, server-ready and client-ready bundles using multi-compiler configurations, runtime targets, dependency externalization, and environment branching.

The Dual-Configuration Approach

True isomorphic applications require two separate Webpack configurations executed in tandem: one targeting the browser and one targeting Node.js. Running both configurations allows shared application logic while catering to the distinct runtime capabilities of each platform.

To implement this, export an array containing both configuration objects from your webpack.config.js:

const clientConfig = {
  name: 'client',
  target: 'web',
  entry: './src/client.js',
  output: {
    path: path.resolve(__dirname, 'dist/client'),
    filename: '[name].[contenthash].js',
    publicPath: '/static/',
  },
  // Loaders and plugins...
};

const serverConfig = {
  name: 'server',
  target: 'node',
  entry: './src/server.js',
  output: {
    path: path.resolve(__dirname, 'dist/server'),
    filename: 'server.js',
    library: {
      type: 'commonjs2',
    },
  },
  // Loaders and plugins...
};

module.exports = [clientConfig, serverConfig];

Configuring the Server Bundle

The server configuration requires specific settings to run natively in Node.js without bundling unnecessary runtime polyfills.

Set the Target

Set target: 'node' in the server configuration. This instructs Webpack to retain Node.js built-in modules (like fs, path, and http) as native require statements instead of attempting to polyfill them with browser-safe equivalents.

Externalize Dependencies

Bundling node_modules into a server bundle bloats build times and can break modules that rely on native C++ bindings or dynamic runtime paths. Use webpack-node-externals to prevent third-party packages from being packaged into the server output:

const nodeExternals = require('webpack-node-externals');

const serverConfig = {
  target: 'node',
  externals: [nodeExternals()],
  // ...
};

This ensures that third-party packages are loaded via Node's native module resolution at runtime.

Define the Output Format

Configure the output library format so the server runtime can require or import the compiled application:

output: {
  path: path.resolve(__dirname, 'dist/server'),
  filename: 'server.js',
  library: {
    type: 'commonjs2', // Exports module.exports
  },
}

If targeting Node with ES Modules enabled, use output.module: true and configure experiments.outputModule: true.

Managing Assets and Non-JavaScript Imports

Isomorphic code often imports CSS, images, and fonts directly into component files. While the client requires these assets, the server only needs the raw markup.

Stylesheets

On the client, stylesheets are processed using css-loader combined with MiniCssExtractPlugin.loader or style-loader. On the server, DOM manipulation is unavailable, and generating CSS files is redundant. Use css-loader with an export-only configuration or ignore styling altogether:

// Server config rule
{
  test: /\.css$/,
  loader: 'css-loader',
  options: {
    modules: {
      exportOnlyLocals: true, // Retains CSS module class names without outputting raw CSS
    },
  },
}

Static Assets

For static assets like images, ensure asset file paths resolve consistently across both builds. Use Webpack 5 Asset Modules:

{
  test: /\.(png|jpe?g|gif|svg)$/i,
  type: 'asset/resource',
  generator: {
    emit: false, // Prevents server build from writing duplicate asset files
    publicPath: '/static/',
  },
}

Handling Environment-Specific Logic

To execute code conditionally depending on whether it runs during SSR or client hydration, use the DefinePlugin to inject compile-time flags:

// In clientConfig plugins
new webpack.DefinePlugin({
  'process.env.IS_SERVER': JSON.stringify(false),
});

// In serverConfig plugins
new webpack.DefinePlugin({
  'process.env.IS_SERVER': JSON.stringify(true),
});

Within your shared codebase, guard browser-only APIs (window, document, localStorage) with these compile-time flags to prevent runtime crashes during server execution:

if (!process.env.IS_SERVER) {
  window.addEventListener('resize', handleResize);
}

During compilation, Webpack eliminates dead branches via tree-shaking, keeping both bundles lean, functional, and fully isomorphic.
