Webpack Target: Building for Node vs Web

The target property in Webpack directs the compiler to generate code optimized for a specific execution runtime, fundamentally altering how dependencies are resolved, how modules are loaded, and which global variables are expected. This article explains the technical role of Webpack's target setting, highlighting the core differences between compiling an application for Node.js versus standard web browser environments.

The Core Function of the target Property

Webpack does not generate a generic, environment-agnostic bundle by default. Because runtimes handle code loading and environment APIs differently, Webpack must know where the final bundle will execute. Setting the target property tells Webpack which built-in features to leverage, which modules to treat as native, and how to structure module chunking.

In a Webpack configuration file, this is defined at the root level:

module.exports = {
  // Options include 'web', 'node', 'electron-main', etc.
  target: 'web', 
};

Building for the Web (target: 'web')

The 'web' target is the default setting in Webpack and is designed for browser environments. When compiling with this target:

  • Global Scope: Webpack assumes the execution context contains browser globals such as window, document, and navigator. It structures the wrapper code around these references.
  • Module Loading: When code splitting or dynamic imports (import()) are used, Webpack generates chunk-loading mechanisms that rely on DOM manipulation, such as appending <script> tags or fetching JSONP callbacks.
  • Node.js Built-Ins: Webpack treats Node.js core modules (such as fs, path, and crypto) as foreign. In Webpack 5, it will not polyfill them automatically, resulting in build-time errors if your source code attempts to import them without explicit polyfills or fallback configurations.

Building for Node.js (target: 'node')

When developing server-side applications, microservices, or server-rendered backends, compiling with target: 'node' alters Webpack's output to match the V8 Node.js runtime:

  • Native Module Resolution: Core Node.js modules like fs, path, http, and child_process are recognized as native dependencies. Webpack does not attempt to bundle them or search for browser shims; instead, it compiles imports into native require() or ESM import statements.
  • Chunk Loading: Dynamic chunks are loaded using Node's filesystem or native require() functions rather than DOM-based injection.
  • Server Globals: The compiled bundle relies on Node-specific variables like process, __dirname, __filename, and global. Webpack provides options via the node configuration block to either mock, preserve, or pass through values like __dirname.
  • Externalizing Dependencies: In Node builds, it is common to combine target: 'node' with webpack-node-externals so that dependencies inside node_modules are excluded from the bundle and resolved at runtime from the server's local file system.

Key Differences at a Glance

Feature target: 'web' target: 'node'
Primary Runtime Modern web browsers Node.js runtime environment
Chunk Loading Strategy Script injection / Fetch / JSONP Node.js require() or ESM imports
Core Modules (fs, path) Generates errors unless polyfilled Treated as native external modules
Default Globals window, self, document global, process, __dirname
Packaging Strategy Bundles all code for network delivery Often leaves node_modules external

Choosing the correct target ensures that Webpack generates runtime code capable of executing without runtime syntax errors, missing references, or inappropriate chunk-loading behavior.
