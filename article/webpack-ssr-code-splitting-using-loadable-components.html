Webpack SSR Code Splitting Using Loadable Components

Server-side rendering (SSR) in React often clashes with code-splitting, as the client needs to load the split bundles before rendering to prevent hydration mismatches and screen flashes. Webpack handles this problem in conjunction with Loadable Components (@loadable/component) by mapping dynamic imports to compiled bundles via an asset manifest. This article explains how Webpack, Babel, and Loadable Components coordinate to extract, preload, and hydrate split chunks seamlessly across both the server and client environments.

The Fundamental Problem of SSR Code-Splitting

Standard dynamic imports using React.lazy and import() are asynchronous. In a purely client-side application, React suspends rendering and displays a fallback while the chunk downloads. However, during server rendering, the server cannot wait for asynchronous client chunks to load on the fly without complex synchronization.

Furthermore, if the server renders the final HTML and sends it to the browser, the client-side JavaScript must download those same split chunks before executing ReactDOM.hydrateRoot(). If hydration begins before the code-split components are available in the browser, React falls back to a loading state, causing UI flickers and hydration mismatch errors.

The Loadable Components Architecture

Loadable Components resolves this issue through a coordinated three-part system:

  1. @loadable/babel-plugin: Transforms dynamic import statements into objects containing metadata about chunk names and bundle paths.
  2. @loadable/webpack-plugin: Gathers compilation data from Webpack and writes a manifest file, typically named loadable-stats.json.
  3. @loadable/server: Reads the manifest during the Node.js server render pass, traces which components were executed, and injects the corresponding <script> and <link> tags into the initial HTML response.

How Webpack and Loadable Components Work Together

1. Code Transformation via Babel

When a developer writes a code-split component using loadable(() => import('./Component')), the Loadable Babel plugin modifies the call during the build step. It injects critical Webpack-specific identifiers, such as the chunk name, module ID, and a resolver function. This transformation allows Loadable Components to synchronously check whether a chunk has already been loaded on the client.

2. Asset Manifest Generation via Webpack

During the build process, the @loadable/webpack-plugin hooks into Webpack’s compilation lifecycle. As Webpack analyzes the dependency graph and splits the code into chunks, the plugin records the output assets (JavaScript files, CSS files, and source maps) associated with each split point.

The plugin outputs loadable-stats.json. This file acts as the bridge between Webpack's build-time output and the runtime server environment, detailing exactly which files belong to which dynamic module.

3. Server-Side Asset Tracking with ChunkExtractor

During an incoming request, the Node.js server uses the ChunkExtractor class from @loadable/server.

import { ChunkExtractor } from '@loadable/server';

const statsFile = path.resolve(__dirname, '../dist/loadable-stats.json');
const extractor = new ChunkExtractor({ statsFile, entrypoints: ['main'] });

// Wrap the App to track rendered dynamic components
const jsx = extractor.collectChunks(<App />);
const html = renderToString(jsx);

// Retrieve required script and link tags for the rendered components
const scriptTags = extractor.getScriptTags();
const linkTags = extractor.getLinkTags();
const styleTags = extractor.getStyleTags();

When renderToString executes, collectChunks intercepts every Loadable component rendered during that specific pass. The ChunkExtractor cross-references these components with loadable-stats.json and produces the exact <script> and <link rel="preload"> tags required for that specific page view.

4. HTML Assembly and Response

The server constructs the final HTML payload, placing preloaded link tags in the <head> and the extracted <script> tags immediately after the root application markup. Because the tags are present directly in the server response, the browser begins downloading the necessary split chunks in parallel before executing the main application code.

5. Client-Side Hydration with loadableReady

On the client side, the application uses the loadableReady helper before mounting:

import { loadableReady } from '@loadable/component';
import { hydrateRoot } from 'react-dom/client';

loadableReady(() => {
  const root = document.getElementById('root');
  hydrateRoot(root, <App />);
});

loadableReady waits for all scripts injected by the server to finish loading and executing in the browser. Once the split bundles are ready, React hydrates the DOM against the fully prepared markup, completely eliminating hydration mismatches and layout shifts.
