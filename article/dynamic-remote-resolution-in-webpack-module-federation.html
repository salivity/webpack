Dynamic Remote Resolution in Webpack Module Federation

This article explores dynamic remote resolution in Webpack Module Federation, focusing on the promise-based syntax used to load micro-frontends dynamically at runtime. You will learn the mechanics behind promise-based remote resolution, why it is preferable to static build-time definitions, and how to implement it to fetch remote entry files from dynamic URLs, environment variables, or external configuration services.

Understanding Dynamic Remote Resolution

In standard Webpack Module Federation setups, remote applications are declared statically in the webpack.config.js file using a fixed string format, such as app2: 'app2@https://example.com/remoteEntry.js'. While this works for simple deployments, it requires rebuilding the host application whenever a remote URL changes, such as when promoting code through development, staging, and production environments.

Dynamic remote resolution overcomes this limitation by determining the location of remote modules at runtime. Instead of hardcoding the URL, the host application resolves the remote module dynamically before executing the imported micro-frontend code.

The Promise-Based Syntax

Webpack Module Federation natively supports dynamic resolution through a promise-based syntax within the remotes configuration object. Instead of passing a static string, you provide a JavaScript expression wrapped in a promise. Webpack evaluates this promise at runtime when the remote module is first requested.

The syntax follows this core structure:

// webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host_app',
      remotes: {
        dynamicRemote: `promise new Promise((resolve, reject) => {
          const remoteUrl = window.remoteUrl || 'https://default.cdn.com/remoteEntry.js';
          const script = document.createElement('script');
          script.src = remoteUrl;
          script.onload = () => {
            // The container is attached to the window object
            const proxy = {
              get: (request) => window.dynamicRemote.get(request),
              init: (arg) => {
                try {
                  return window.dynamicRemote.init(arg);
                } catch(e) {
                  console.error('Remote container already initialized', e);
                }
              }
            };
            resolve(proxy);
          };
          script.onerror = (error) => {
            reject(error);
          };
          document.head.appendChild(script);
        })`
      },
      shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
    }),
  ],
};

How It Works Under the Hood

  1. Lazy Evaluation: Webpack intercepts the import statement (e.g., import('dynamicRemote/Component')) and initiates the promise defined in the configuration.
  2. Script Injection: The promise dynamically injects the <script> tag referencing the determined remoteEntry.js file into the DOM.
  3. Initialization and Resolution: Once the script loads, Webpack retrieves the global container created by the remote bundle (e.g., window.dynamicRemote). The promise resolves with a proxy interface containing the init and get methods, allowing Webpack's module sharing and container communication logic to proceed seamlessly.

Key Benefits

  • Environment Independence: Build the host application once and deploy it across multiple environments by fetching remote manifests or URLs from runtime APIs or environment-injected variables.
  • Independent Versioning: Dynamically swap micro-frontend versions for canary releases, A/B testing, or rollbacks without updating the host bundle.
  • Failover and Fallbacks: Implement custom fallback mechanisms directly inside the promise's reject or onerror handlers, enabling the host to load backup CDN endpoints or alternate components when a remote service fails.
