Webpack Multi-Compiler Mode for Concurrent Builds

Webpack's multi-compiler mode allows developers to define and run multiple build targets—such as client, server, modern, and legacy bundles—within a single project. This article explains how Webpack's multi-compiler functionality operates, how to configure multiple build configurations in a single file, and how to execute them concurrently to reduce overall build times.

Defining Multiple Configurations

Webpack natively supports multi-compiler mode by allowing webpack.config.js to export an array of configuration objects instead of a single configuration object.

// webpack.config.js
const path = require('path');

const clientConfig = {
  name: 'client',
  target: 'web',
  entry: './src/client.js',
  output: {
    path: path.resolve(__dirname, 'dist/client'),
    filename: 'bundle.js',
  },
};

const serverConfig = {
  name: 'server',
  target: 'node',
  entry: './src/server.js',
  output: {
    path: path.resolve(__dirname, 'dist/server'),
    filename: 'bundle.js',
  },
};

module.exports = [clientConfig, serverConfig];

Assigning a name property to each configuration improves logging clarity and allows specific configurations to be targeted via the command line using --config-name.

Concurrency in Standard Webpack

When passing an array of configurations to the Webpack CLI (npx webpack), Webpack instantiates a MultiCompiler. In Webpack 5, the MultiCompiler processes individual configurations in parallel when executed via the Node.js API or standard CLI.

However, because Node.js operates on a single main thread, CPU-intensive tasks—such as Babel transpilation, TypeScript type checking, or minification—can still block execution, preventing true hardware-level parallelism.

Achieving True Parallel Execution

To maximize hardware utilization and achieve process-level concurrency across multiple configurations, choose one of the following approaches:

1. Using parallel-webpack

The parallel-webpack package distributes each configuration across separate worker processes, allowing multi-core CPUs to compile all configurations concurrently without main-thread blocking.

Install the package:

npm install parallel-webpack --save-dev

Run the build:

npx parallel-webpack

You can control the concurrency level using the --max-spawns argument:

npx parallel-webpack --max-spawns 4

2. Using the Webpack Node.js API with Worker Threads

If you control your build via a custom Node.js script, you can leverage Node’s worker_threads or child_process modules to spawn a distinct Webpack instance per configuration:

// build.js
const { Worker } = require('worker_threads');
const configs = ['client', 'server'];

configs.forEach((target) => {
  const worker = new Worker('./run-compiler.js', {
    workerData: { target },
  });

  worker.on('message', (msg) => console.log(`[${target}]: ${msg}`));
  worker.on('error', (err) => console.error(`[${target}] Error:`, err));
});

Inside run-compiler.js, run webpack() on the targeted configuration independently.

Best Practices for Multi-Compiler Builds

  • Distinct Output Paths: Ensure each configuration outputs to a separate directory or uses unique file names to avoid write collisions.
  • Persistent Caching: Configure cache: { type: 'filesystem' } on each configuration. Webpack ensures caches do not conflict if the configurations have distinct name properties.
  • Avoid Inter-Config Dependencies: Multi-compiler tasks execute independently; do not design one configuration to rely on the output of another within the same build step.
