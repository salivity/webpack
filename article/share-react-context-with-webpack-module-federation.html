Share React Context with Webpack Module Federation

This article explores how Webpack Module Federation shares state across distributed micro-frontend applications using React Context. You will learn the mechanics behind context sharing across host and remote boundaries, how to configure the ModuleFederationPlugin to avoid runtime duplicate instances, and the standard architectural patterns required to maintain a single source of truth across independently deployed builds.

The Core Challenge: Reference Equality

React Context relies on JavaScript reference equality. For a component inside a remote container to consume state provided by a host application, both the host and the remote must reference the exact same memory instance of the React library and the specific Context object.

If Module Federation loads two different copies of React, or two distinct instances of the Context definition, useContext(MyContext) returns the default context value rather than the data passed into <MyContext.Provider value={...}>.

Configuring Module Federation for Shared Context

To allow React Context to traverse remotes, Webpack must be configured to treat React, its DOM renderer, and the shared Context definition as singletons.

In your webpack.config.js for both the host and all remotes, configure the shared property within ModuleFederationPlugin:

// webpack.config.js (Host and Remotes)
const { ModuleFederationPlugin } = require('webpack').container;
const deps = require('./package.json').dependencies;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host_app',
      remotes: {
        remote_app: 'remote_app@http://localhost:3001/remoteEntry.js',
      },
      shared: {
        react: {
          singleton: true,
          requiredVersion: deps.react,
        },
        'react-dom': {
          singleton: true,
          requiredVersion: deps['react-dom'],
        },
      },
    }),
  ],
};
  • singleton: true: Instructs Webpack to load only a single instance of the package across the entire application runtime.
  • requiredVersion: Ensures that all remotes match the host’s version range. If versions conflict, Webpack prints a console warning or fails depending on whether strictVersion is enabled.

Distributing the Context Object

Sharing React alone is insufficient; the Context instance itself must also be shared as a single instance. Two primary architecture patterns achieve this:

1. The Shared NPM or Monorepo Package (Recommended)

Define the Context and its Provider within a separate shared package or monorepo workspace.

// packages/shared-context/src/AuthContext.js
import React, { createContext, useContext, useState } from 'react';

const AuthContext = createContext(null);

export const AuthProvider = ({ children }) => {
  const [user, setUser] = useState(null);
  return (
    <AuthContext.Provider value={{ user, setUser }}>
      {children}
    </AuthContext.Provider>
  );
};

export const useAuth = () => useContext(AuthContext);

Add this package to the shared configuration in both host and remote webpack.config.js files:

shared: {
  react: { singleton: true, requiredVersion: deps.react },
  'react-dom': { singleton: true, requiredVersion: deps['react-dom'] },
  '@my-org/shared-context': {
    singleton: true,
    requiredVersion: deps['@my-org/shared-context'],
  },
}

2. Exposing Context Directly from the Host

If an external package is not viable, the host can expose the Context module over Module Federation:

// Host webpack.config.js
new ModuleFederationPlugin({
  name: 'host',
  filename: 'remoteEntry.js',
  exposes: {
    './AuthContext': './src/AuthContext',
  },
  shared: {
    react: { singleton: true },
    'react-dom': { singleton: true },
  },
});

The remote application then imports the Context dynamically or declares the host as a remote to consume it:

// Remote Component
import React from 'react';
import { useAuth } from 'host/AuthContext';

export default function RemoteProfile() {
  const { user } = useAuth();
  return <div>Logged in as: {user?.name}</div>;
}

Critical Pitfalls to Avoid

  • Missing Async Boundaries: If your entry point immediately executes React imports without dynamic import('./bootstrap'), Webpack cannot negotiate shared packages asynchronously, leading to fallback copies of React being instantiated.
  • Mismatched Major Versions: If the host runs React 18 and a remote runs React 17, setting singleton: true will force one version onto the other, often causing runtime crashes. Keep dependencies synchronized.
  • Overusing Context for High-Frequency State: Context is optimal for low-frequency updates (e.g., authentication, localization, themes). High-frequency state shared across micro-frontends can trigger unnecessary re-renders across remote boundaries, making event-driven buses or external stores like Zustand or Redux better alternatives for performance-critical data.
