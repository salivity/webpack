How Webpack Resolves Symlinks in Monorepos

In a monorepo setup, package managers like Yarn, npm, or pnpm link internal packages together via symlinks inside the local node_modules folders. Webpack handles these symlinked dependencies through its internal module resolution algorithm, primarily governed by the resolve.symlinks configuration option. Understanding how Webpack traverses symlinks—whether resolving to the canonical disk path or maintaining the symlinked location—is essential for avoiding duplicate dependency bugs, build failures, and loader misconfigurations.

The Default Behavior: Real Path Resolution

By default, Webpack sets resolve.symlinks to true. This instructs Webpack to follow any symbolic link to its canonical physical location on disk before running module resolution.

When an application imports a local package (for example, import { Button } from '@monorepo/ui'), the following sequence occurs:

  1. Webpack finds the symlink in apps/web/node_modules/@monorepo/ui.
  2. Because resolve.symlinks: true is active, Webpack resolves the symlink to its real target path: packages/ui.
  3. Any subsequent imports made by @monorepo/ui (such as react or utility libraries) are resolved starting from the real directory: packages/ui/node_modules, cascading upward to packages/node_modules, and finally to the root node_modules.

Common Issues Caused by resolve.symlinks: true

While following symlinks mirrors standard Node.js behavior, it frequently causes issues in monorepos:

  • Duplicate Singletons: If the shared package and the host application both depend on libraries that rely on a single runtime instance (such as React, styled-components, or GraphQL), Webpack may bundle two distinct copies of the library—one from apps/web/node_modules and one from packages/ui/node_modules or the repository root. This often leads to runtime errors, such as the "Invalid Hook Call" error in React.
  • Loader Exclusions: Many Webpack configurations exclude /node_modules/ from loaders like babel-loader or ts-loader. Because the symlinked package resolves to packages/ui (which is outside the consuming app's node_modules), Webpack treats it as local source code and may attempt to transpile it unexpectedly—or fail if the loader configuration does not include files outside the project root.

Disabling Symlink Resolution (resolve.symlinks: false)

Setting resolve.symlinks: false in webpack.config.js changes this behavior completely:

module.exports = {
  // ...
  resolve: {
    symlinks: false,
  },
};

When disabled, Webpack treats the symlink as if it were a physical directory located directly inside apps/web/node_modules/@monorepo/ui.

This alters the dependency search path:

  • Webpack searches for sub-dependencies starting within apps/web/node_modules/@monorepo/ui/node_modules, then moves up to apps/web/node_modules, and finally to the root node_modules.
  • The package consumes the host application's versions of shared libraries, significantly reducing duplicate dependency conflicts.
  • Path-based loader rules that rely on /node_modules/ will consistently treat the package as a third-party dependency unless explicitly included.

Configuring Webpack for Monorepos

Depending on your monorepo architecture, two primary strategies exist for managing Webpack symlink resolution:

Strategy A: Use resolve.symlinks: false with Explicit Loader Inclusions

If workspace packages are published as uncompiled source code (e.g., TypeScript), set resolve.symlinks: false and explicitly point your loaders to include the workspace packages:

const path = require('path');

module.exports = {
  resolve: {
    symlinks: false,
  },
  module: {
    rules: [
      {
        test: /\.(js|ts|tsx)$/,
        include: [
          path.resolve(__dirname, 'src'),
          path.resolve(__dirname, 'node_modules/@monorepo'),
        ],
        loader: 'babel-loader',
      },
    ],
  },
};

Strategy B: Keep resolve.symlinks: true with Aliasing

If maintaining real path resolution is necessary, prevent duplicate dependencies by aliasing shared libraries directly to the root node_modules or the application's local node_modules:

const path = require('path');

module.exports = {
  resolve: {
    symlinks: true,
    alias: {
      react: path.resolve(__dirname, 'node_modules/react'),
      'react-dom': path.resolve(__dirname, 'node_modules/react-dom'),
    },
    modules: [
      path.resolve(__dirname, 'node_modules'),
      path.resolve(__dirname, '../../node_modules'),
      'node_modules',
    ],
  },
};

Using this approach, Webpack resolves internal packages at their canonical disk paths while strictly enforcing that shared runtime dependencies point to a single, unified copy.
