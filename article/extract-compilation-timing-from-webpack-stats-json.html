Extract Compilation Timing from Webpack Stats JSON

Webpack's stats JSON output provides a comprehensive performance breakdown of your build pipeline. This guide explains how to configure Webpack to include timing data, identify the specific timestamp and duration properties in the generated JSON, and extract these metrics using a Node.js script to pinpoint bottlenecks in your modules and loaders.

1. Generate the Stats File with Profile Data

By default, Webpack omits granular performance measurements. To capture detailed timing metrics, you must enable the profile flag alongside the JSON output generation.

Run the build via the command line:

npx webpack --profile --json=stats.json

Alternatively, configure this within your webpack.config.js:

module.exports = {
  // ...
  profile: true,
  stats: {
    timings: true,
    modules: true,
    profile: true
  }
};

2. Key Timing Properties in the Stats JSON

Once stats.json is generated, it contains several fields that detail execution speed:

  • time (Root level): The total compilation duration in milliseconds.
  • builtAt (Root level): The UNIX timestamp (in ms) when the build finished.
  • modules[].profile: Contains phase-specific timings for each compiled module (available only when profile: true is set):
    • factory: Time spent resolving module paths and initializing loaders.
    • building: Time spent executing loaders and parsing source code into an AST.
    • dependencies: Time spent discovering and resolving child dependencies.

3. Extracting the Data via Node.js

You can parse stats.json to calculate the overall build duration and identify the top slowest modules using a custom Node.js script.

Create a file named parse-timings.js:

const fs = require('fs');

// Read and parse stats.json
const rawData = fs.readFileSync('stats.json', 'utf8');
const stats = JSON.parse(rawData);

// 1. Overall compilation duration
console.log(`Total Compilation Time: ${stats.time} ms`);

// 2. Extract and sort modules by compilation duration
if (stats.modules && stats.modules.length > 0) {
  const moduleTimings = stats.modules
    .filter(mod => mod.profile) // Filter modules with profile data
    .map(mod => ({
      name: mod.name,
      totalTime: mod.profile.factory + mod.profile.building + mod.profile.dependencies,
      buildingTime: mod.profile.building,
      factoryTime: mod.profile.factory,
      dependenciesTime: mod.profile.dependencies
    }))
    .sort((a, b) => b.totalTime - a.totalTime);

  console.log('\nTop 5 Slowest Modules:');
  moduleTimings.slice(0, 5).forEach((mod, index) => {
    console.log(`${index + 1}. ${mod.name}`);
    console.log(`   Total: ${mod.totalTime} ms (Building: ${mod.buildingTime} ms, Factory: ${mod.factoryTime} ms, Deps: ${mod.dependenciesTime} ms)`);
  });
}

Run the script:

node parse-timings.js

4. Extracting Multi-Compiler Timings

If you are running multi-compiler configurations (such as separate client and server builds), the root object contains a children array instead of top-level metrics. Each entry in children is an independent stats object:

if (stats.children && stats.children.length > 0) {
  stats.children.forEach(child => {
    console.log(`Target: ${child.name} - Compilation Time: ${child.time} ms`);
  });
}

Targeting the time field for the root or child compilers and parsing the profile object inside individual modules allows you to isolate whether compilation overhead stems from module resolution, heavy loaders (such as Babel or TypeScript), or dependency tree traversal.
