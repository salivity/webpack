Webpack 5 Asset Processing Stages Explained

Webpack 5 introduced the processAssets hook on the Compilation object to unify and standardize how plugins emit, transform, and optimize output files. Instead of relying on multiple disjointed hooks from earlier versions, asset lifecycle modifications are now organized into distinct execution stages defined by constants on the Compilation class. This article details every asset processing stage available in Webpack 5 in their exact order of execution, detailing their specific purposes in the asset compilation pipeline.

The processAssets Hook

Plugins tap into the compilation.hooks.processAssets hook by supplying an options object containing a name and a stage. Webpack sorts all registered callbacks by their stage value (from lowest to highest) and executes them sequentially.

compilation.hooks.processAssets.tap(
  {
    name: 'MyPlugin',
    stage: Compilation.PROCESS_ASSETS_STAGE_OPTIMIZE,
  },
  (assets) => {
    // Modify or inspect compilation assets here
  }
);

Webpack 5 Asset Processing Stages in Order of Execution

Below are the official Compilation.PROCESS_ASSETS_STAGE_* constants provided by Webpack 5:

1. PROCESS_ASSETS_STAGE_ADDITIONAL (Stage: -2000)

Used to add extra assets to the compilation before any core processing begins. This is ideal for plugins that generate initial, standalone assets that should undergo the full compilation and optimization pipeline.

2. PROCESS_ASSETS_STAGE_PRE_PROCESS (Stage: -1000)

Reserved for early transformations and basic preprocessing on existing assets before other plugins begin deriving or refining them.

3. PROCESS_ASSETS_STAGE_DERIVED (Stage: -500)

Used to derive new assets directly from existing ones. Examples include extracting source maps, generating compressed alternate versions, or creating secondary manifest data based on initial outputs.

4. PROCESS_ASSETS_STAGE_PAINT (Stage: -250)

Intended for non-destructive visual or superficial modifications to existing assets without altering their logical functionality or structural makeup.

5. PROCESS_ASSETS_STAGE_ADDITIONS (Stage: -100)

Used for adding secondary or supporting assets to the compilation after primary asset transformations have occurred, but before optimization begins.

6. PROCESS_ASSETS_STAGE_NONE (Stage: 0)

The default stage assigned when no specific stage is declared in the plugin configuration. It runs before active optimizations start.

7. PROCESS_ASSETS_STAGE_OPTIMIZE (Stage: 100)

The standard stage for general optimization of existing assets. This is commonly where code minification (such as Terser), tree-shaking adjustments, and dead-code removal on output strings take place.

8. PROCESS_ASSETS_STAGE_OPTIMIZE_COUNT (Stage: 200)

Designed specifically for reducing the total number of assets. Plugins that merge chunks, combine small assets, or bundle multiple styles/scripts together should hook into this stage.

9. PROCESS_ASSETS_STAGE_OPTIMIZE_COMPATIBILITY (Stage: 300)

Used for compatibility-related transformations, such as injecting polyfills, applying vendor prefixes, or adjusting syntax for older browser support.

10. PROCESS_ASSETS_STAGE_OPTIMIZE_SIZE (Stage: 400)

Intended for size-reduction passes that do not alter code logic, such as stripping comments, aggressive whitespace reduction, or running gzip and Brotli pre-compression routines.

11. PROCESS_ASSETS_STAGE_DEV_TOOLING (Stage: 500)

Used to attach developer tooling assets or augment existing ones, such as appending development source map comments or injecting debugging anchors.

12. PROCESS_ASSETS_STAGE_OPTIMIZE_INLINE (Stage: 700)

Used to inline smaller assets directly into larger assets (for example, base64 data URIs for images or inlining critical CSS directly into HTML output).

13. PROCESS_ASSETS_STAGE_SUMMARIZE (Stage: 1000)

Reserved for plugins that inspect the final list of assets to produce summaries, statistics, or inventory manifests (e.g., manifest.json or asset-manifest.json).

14. PROCESS_ASSETS_STAGE_OPTIMIZE_HASH (Stage: 2000)

Used to optimize or recalculate hashes attached to asset filenames to ensure proper cache-busting behavior.

15. PROCESS_ASSETS_STAGE_OPTIMIZE_TRANSFER (Stage: 3000)

Used for operations focused on asset delivery and HTTP transport, such as generating prefetch/preload link headers, Service Worker pre-cache manifests, or HTTP/2 push descriptors.

16. PROCESS_ASSETS_STAGE_ANALYSE (Stage: 4000)

Dedicated to inspecting, measuring, and analyzing the finalized set of assets. Bundle visualizers, size checkers, and performance budget validators hook in here.

17. PROCESS_ASSETS_STAGE_REPORT (Stage: 10000)

The final stage in the asset lifecycle. It is used exclusively to generate build reports, print completion summaries to the terminal, or send build metrics to remote monitoring services.
