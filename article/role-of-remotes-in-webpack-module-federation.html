Role of Remotes in Webpack Module Federation

Webpack Module Federation revolutionizes micro-frontend architectures by allowing distinct JavaScript builds to dynamically share code at runtime. Within the ModuleFederationPlugin configuration, the remotes option acts as the bridge connecting a host application to external builds. This article explores the precise role of the remotes configuration, detailing how it maps external entry points, resolves runtime dependencies, and enables seamless module consumption across separate applications.

Defining External Connections

The primary role of the remotes configuration is to inform the host application which foreign applications (remotes) it depends on and where to locate them. In micro-frontend architectures, separate builds need a mechanism to reference code that does not exist in their own bundle. The remotes object defines these external boundaries using a key-value structure.

new ModuleFederationPlugin({
  name: 'host_app',
  remotes: {
    marketing: 'marketing@https://cdn.example.com/marketing/remoteEntry.js',
    checkout: 'checkout@https://cdn.example.com/checkout/remoteEntry.js',
  },
})

In this syntax:

  • Key (marketing): The internal identifier or alias used within the host application's import statements.
  • Value (marketing@https://...): A string containing the global name assigned to the remote's container, an @ separator, and the URL to the remote's manifest file, typically named remoteEntry.js.

Establishing Runtime Resolution

Traditional bundling requires all dependencies to be resolved at build time. The remotes configuration defers this resolution to the client runtime. When the host application boots in the browser:

  1. Webpack reads the remotes configuration.
  2. It injects a script tag to load the specified remoteEntry.js file over the network.
  3. The remote entry file initializes a global container on the window object containing the remote application's module map.

By delegating resolution to runtime, the host can consume updates deployed to the remote application instantly without needing to rebuild or redeploy the host itself.

Aliasing and Transparent Module Imports

The remotes configuration creates an aliasing layer that makes importing federated code identical to importing standard npm packages or local files.

When you configure marketing: 'marketing@...', developers can write standard ECMAScript imports inside host files:

import PromotionalBanner from 'marketing/PromotionalBanner';

Webpack intercepts any import starting with the alias declared in remotes, prevents the local build from failing due to a missing local file, and translates the import into an asynchronous request to the remote container.

Facilitating Shared Dependency Management

The remotes configuration plays an essential role in dependency negotiation. When a host imports a federated module via a declared remote, the host and the remote cross-reference their shared scope.

If both the host and the remote specify a shared library (such as React), the runtime ensures only one version is downloaded and shared between both contexts, preventing duplicate downloads and runtime conflicts.

Dynamic Remote Configuration

Beyond static URL definitions, the remotes configuration can be defined dynamically for complex deployments where endpoints vary by environment (e.g., development, staging, production). Developers can configure remotes using promise-based syntax or load entry files manually at runtime via container factories, allowing dynamic routing of remote endpoints directly through configuration scripts.
