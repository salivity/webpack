pnpm Symlinks and Webpack Module Resolution

This article examines how pnpm's content-addressable storage and symlinked node_modules layout interact with Webpack's module resolution algorithm. It explores how Webpack's default symlink-following behavior affects dependency traversal, peer dependency resolution, and loader processing, while providing concrete configuration adjustments to ensure seamless builds in single packages and monorepos.

Understanding the pnpm Directory Structure

Unlike npm and Yarn Classic, which historically flatten the node_modules directory, pnpm uses a content-addressable store on the disk and links dependencies using hard links and symbolic links (symlinks).

In a pnpm project:

  1. Direct dependencies declared in package.json are placed in the root node_modules as symlinks.
  2. These symlinks point to a hidden, nested directory called node_modules/.pnpm.
  3. Inside .pnpm, each package version has its own dedicated directory containing its code and symlinks to its own direct dependencies.

This architecture prevents "phantom dependencies" (importing packages not declared in package.json) and avoids duplication on disk.

How Webpack Interacts with Symlinks

Webpack uses the enhanced-resolve package to find imported modules. By default, Webpack sets:

module.exports = {
  resolve: {
    symlinks: true
  }
};

When resolve.symlinks is true, Webpack resolves the symlink to its real canonical path on the filesystem before proceeding with module evaluation.

When applied to pnpm:

  1. Webpack encounters an import 'lodash' statement.
  2. It looks inside the root node_modules/lodash.
  3. It detects that node_modules/lodash is a symlink pointing to node_modules/.pnpm/lodash@4.17.21/node_modules/lodash.
  4. It resolves the file path to the real path inside .pnpm.
  5. Further dependency resolution for that package occurs relative to the .pnpm path, not the root node_modules.

Implications for Webpack Builds

1. Loader Filtering (include and exclude)

A common issue occurs when configuring loaders (such as babel-loader or swc-loader). Developers frequently use rules like:

{
  test: /\.jsx?$/,
  exclude: /node_modules/,
  use: 'babel-loader'
}

In a monorepo setup, if Workspace Package A imports Workspace Package B via a pnpm workspace protocol, Package B is symlinked into Package A's node_modules. Because Webpack resolves real paths, Package B resolves to its true source location (e.g., packages/package-b/src). Consequently, the /node_modules/ exclusion does not match Package B, and Webpack unexpectedly processes it with the loader.

Conversely, if an include pattern explicitly targets only the current project directory (e.g., include: path.resolve(__dirname, 'src')), local symlinked packages outside that path will be excluded from compilation. To fix this, explicitly include symlinked workspace directories in your loader's include array.

2. Peer Dependency Resolution

Because pnpm creates distinct folder hierarchies in .pnpm for packages with different sets of peer dependencies, Webpack correctly isolates package variants. When resolving from the real path inside .pnpm/package@version_peer@version/node_modules/package, the peer dependency is located alongside the package, preventing Webpack from resolving the wrong peer dependency version from the application root.

3. Toggling resolve.symlinks: false

Setting resolve.symlinks: false instructs Webpack not to resolve the real path and instead treat the symlink's location inside node_modules as the module's actual location.

While this mimics Node's legacy --preserve-symlinks behavior, it can break pnpm's architecture:

  • Transitive dependencies nested inside .pnpm may fail to resolve because Webpack will attempt to look for them in the root node_modules, where pnpm does not place them.
  • Packages that rely on singleton states (like React or GraphQL) might be duplicated in the bundle if they are accessible through multiple symlink paths.

For pnpm, it is strongly recommended to keep resolve.symlinks: true (the default) to allow Webpack to locate transitive dependencies inside their dedicated .pnpm virtual stores.

Recommended Webpack Configurations for pnpm

To ensure reliable builds with pnpm:

  1. Keep resolve.symlinks enabled: Retain the default resolve.symlinks: true so Webpack navigates the .pnpm tree as designed.
  2. Use absolute paths for loaders: When targeting workspace packages in a monorepo, define include rules using path.resolve or require.resolve targeting the real paths of workspace sources.
  3. Explicit module directories: If runtime dependencies cannot be found during deep nested imports, explicitly specify the fallback search paths:
module.exports = {
  resolve: {
    modules: ['node_modules', path.resolve(__dirname, 'node_modules')]
  }
};
