Webpack Multiple Rules Matching Same Asset

When a module matches multiple rules defined in Webpack's module.rules configuration, Webpack does not stop at the first match by default. Instead, it accumulates all matching rules and applies their respective loaders and configurations to that asset in a defined execution pipeline. This article explains how Webpack resolves multiple matching rules, the order in which loaders execute across these rules, how loader enforcement stages modify this behavior, and how to restrict execution using configuration properties like oneOf.

Cumulative Rule Execution

In Webpack, module.rules is an array of rule objects. When an asset path satisfies the test, include, or exclude conditions of more than one rule, Webpack combines the loaders from each matching rule rather than choosing between them. The asset is passed through a unified processing chain composed of all matched loaders.

Loader Execution Order

Loaders in Webpack run in reverse order (bottom-to-top and right-to-left). When multiple rule objects match the same file, this order is determined by their position within the module.rules array:

  1. Rule Array Positioning: Rules defined later (further down) in the module.rules array run earlier in the pipeline.
  2. Internal Loader Array: Within an individual rule's use array, loaders specified at the end run before those at the beginning.

For example, if Rule A is declared first and Rule B is declared second, and both match an asset, Rule B's loaders will process the asset first and pass the resulting output to Rule A's loaders.

Execution Phases via the enforce Property

Webpack provides an enforce property that overrides the standard array-order execution. Regardless of where a rule is positioned in the configuration array, Webpack categorizes loaders into four distinct execution phases:

  1. Pre-loaders (enforce: 'pre'): Executed first. Commonly used for linting or tasks that must inspect the raw, unmodified source code.
  2. Normal loaders (no enforce property): Executed second in bottom-to-top array order.
  3. Inline loaders: Applied directly in import statements within the code (if allowed).
  4. Post-loaders (enforce: 'post'): Executed last. Often used for operations like code coverage instrumentation or final transformations.

If an asset matches multiple rules across different phases, the loaders are strictly executed in the order of pre -> normal -> inline -> post.

Restricting Matches with oneOf

If applying multiple matching rules is not the desired behavior, Webpack provides the oneOf array. When rules are nested inside a oneOf block, Webpack evaluates them sequentially from top to bottom and applies only the first matching rule, ignoring any subsequent matches:

module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        oneOf: [
          {
            resourceQuery: /inline/, // Matches style.css?inline
            use: ['style-loader', 'css-loader'],
          },
          {
            use: ['file-loader'], // Default fallback for other .css imports
          },
        ],
      },
    ],
  },
};

Conflicting Configurations and Asset Modules

While loaders can be chained safely if their inputs and outputs are compatible, matching multiple rules that specify conflicting properties can cause build failures or unexpected output:

  • Asset Modules: In Webpack 5, rules defining conflicting type properties (such as asset/resource and asset/source) on the same file will conflict or override unpredictably.
  • Incompatible Transformed Output: If an earlier loader outputs binary data, a subsequent loader expecting a JavaScript AST or text string will throw a compilation error.
