Webpack resolve.extensions Precedence Order

This article explains how Webpack evaluates file extensions when resolving module requests using the resolve.extensions configuration. It details the left-to-right precedence rule, default extension behaviors, how to maintain or override default lists, and how resolution order impacts projects containing files with identical base names.

The Left-to-Right Precedence Rule

In Webpack, the resolve.extensions option specifies an array of strings that tell the bundler which file extensions to check when an import statement lacks a file extension (e.g., import Component from './Component').

Webpack processes the resolve.extensions array strictly from left to right. When looking for an extension-less file, Webpack tests each extension in the exact order it appears in the array. As soon as it encounters a file on disk that matches an extension, it halts the search and resolves that file. Any subsequent extensions in the array are ignored for that specific import.

Consider the following configuration:

module.exports = {
  // ...
  resolve: {
    extensions: ['.tsx', '.ts', '.jsx', '.js'],
  },
};

If a directory contains both Component.tsx and Component.js, and an import asks for ./Component:

  1. Webpack checks for ./Component.tsx.
  2. Because it exists, Webpack resolves ./Component.tsx and immediately stops.
  3. ./Component.js is ignored.

If the order were reversed (['.js', '.tsx']), Webpack would resolve Component.js instead.

Default Extensions in Webpack 5

By default, Webpack 5 provides a built-in list:

['.js', '.json', '.wasm']

When you define a custom resolve.extensions array without referencing the defaults, your custom array completely overwrites this default list. If your project still relies on extension-less imports for JSON or WebAssembly files, omitting them will cause module resolution errors.

Retaining Defaults with the Spread Operator

Webpack 5 introduced the spread string ('...') within the resolve.extensions array. This syntax allows you to import and position the default extensions relative to your custom extensions.

Prioritizing Custom Extensions Before Defaults

To prioritize extensions like TypeScript before the default .js or .json files:

module.exports = {
  resolve: {
    extensions: ['.ts', '.tsx', '...'],
  },
};

This resolves in the order: ['.ts', '.tsx', '.js', '.json', '.wasm'].

Prioritizing Defaults Before Custom Extensions

To check standard JavaScript files before custom extensions:

module.exports = {
  resolve: {
    extensions: ['...', '.vue'],
  },
};

This resolves in the order: ['.js', '.json', '.wasm', '.vue'].

Best Practices for Ordering Extensions

  1. Place most frequently used extensions first: If your codebase is primarily TypeScript, placing .ts and .tsx at the beginning reduces the number of file system checks Webpack must perform during the build process, which improves build performance.
  2. Be specific with type definitions: Do not include .d.ts in resolve.extensions, as definition files should not be compiled directly into bundles.
  3. Avoid name collisions: Relying on precedence to differentiate between two source files with the same name (such as Button.js and Button.jsx) can cause unexpected bugs during refactoring. Keep file base names unique within the same directory whenever possible.
