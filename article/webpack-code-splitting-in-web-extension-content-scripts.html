Webpack Code Splitting in Web Extension Content Scripts

Webpack code splitting breaks large JavaScript bundles into smaller chunks loaded on demand, optimizing load times and memory usage. However, implementing code splitting within Web Extension content scripts introduces distinct challenges because content scripts operate within isolated execution contexts on arbitrary host web pages. This article explains the technical mechanics of how Webpack manages split chunks in content scripts, why standard dynamic loading fails in this environment, and how to configure your build system to load chunks reliably.

The Problem with Default Dynamic Chunk Loading

By default, Webpack handles dynamic import() statements using an internal runtime that injects <script> tags into the DOM or fetches resources relative to the current URL. When a content script runs on a target webpage (such as https://example.com), Webpack's default behavior attempts to load split chunks relative to that host's origin (e.g., https://example.com/chunk.js). This results in failed requests (404 errors) or Cross-Origin Resource Sharing (CORS) blocks because the chunk exists only inside the extension package, not on the host server.

Configuring the Public Path at Runtime

To direct Webpack to fetch chunks from the extension package instead of the host page, Webpack must be instructed to resolve chunk URLs against the extension’s base URI.

Webpack provides the global dynamic variable __webpack_public_path__. In your content script entry point, you must define this variable before any dynamic imports are evaluated:

__webpack_public_path__ = chrome.runtime.getURL('/');

Alternatively, if you are targeting modern extension architectures using Webpack 5, you can configure the output configuration statically or rely on automatic path detection:

// webpack.config.js
module.exports = {
  output: {
    publicPath: '',
    chunkFilename: '[name].chunk.js',
  },
};

Even with an empty publicPath, setting __webpack_public_path__ dynamically at the very top of your entry file remains the most reliable method for content scripts.

Declaring Chunks in Manifest Permissions

When Webpack splits code into secondary files, these files become separate resources that the browser must permit the content script to access. In Manifest V3 (MV3), you must explicitly expose these split chunks in your manifest.json under web_accessible_resources.

{
  "manifest_version": 3,
  "web_accessible_resources": [
    {
      "resources": ["*.chunk.js"],
      "matches": ["https://*/*", "http://*/*"]
    }
  ]
}

Without this declaration, the browser’s security sandbox blocks the execution context from loading the split chunk, throwing a network or security exception during dynamic module evaluation.

Dynamic Import Mechanisms: Native vs. JSONP

Webpack determines how to fetch chunks based on the build target:

  1. Native Dynamic Imports (scriptType: 'module'): If your manifest declares the content script as an ES module ("type": "module"), native import() can be used. Native module imports in content scripts can fetch extension resources directly using the fully qualified chrome-extension://<id>/chunk.js path.
  2. JSONP Script Injection: For standard, non-module content scripts, Webpack's runtime creates a <script> tag referencing the chunk and appends it to the host document's <head>. While this loads the code, it executes within the host page's context (the "main world") rather than the content script's "isolated world" unless configured carefully, potentially exposing internal extension logic to page scripts.

Disabling Code Splitting as an Alternative

Because chunk loading in content scripts introduces security and manifest maintenance overhead, many developers disable code splitting strictly for content script entry points while keeping it enabled for popups, options pages, and background scripts.

In Webpack, this is achieved by targeting chunk generation per entry point:

// webpack.config.js
module.exports = {
  entry: {
    contentScript: './src/contentScript.js',
    popup: './src/popup.js',
  },
  optimization: {
    splitChunks: {
      chunks(chunk) {
        // Exclude content scripts from code splitting
        return chunk.name !== 'contentScript';
      },
    },
  },
};

This configuration packages the entire dependency tree of the content script into a single, self-contained file, entirely eliminating runtime dependency resolution failures on third-party web pages.
