Why Add Custom Config to Webpack buildDependencies

Webpack 5 persistent caching dramatically reduces build times by storing compilation artifacts to disk between runs. However, for this caching mechanism to be reliable, Webpack must accurately detect when your build environment changes. Listing custom configuration files under cache.buildDependencies guarantees that any modification to your build rules, environment settings, or custom plugins triggers an automatic cache invalidation, preventing corrupted outputs and stale builds.

How Webpack Persistent Caching Works

When you enable filesystem caching using cache.type = 'filesystem', Webpack writes compilation results to disk. On subsequent builds, Webpack verifies whether any source files or build dependencies have changed. If they remain untouched, Webpack reuses the cached build artifacts instead of recompiling assets from scratch.

To determine cache validity, Webpack relies on the cache.buildDependencies object. By default, Webpack only registers its own source code as a build dependency. It does not automatically trace and watch every external configuration file, auxiliary module, or shared utility that informs your Webpack setup.

The Dangers of Missing Custom Configuration Files

If you split your configuration into multiple files (for example, webpack.common.js, webpack.dev.js, and webpack.prod.js) or import custom loader options from external modules, Webpack does not track these imports out of the box.

Failing to list these custom configurations leads to critical issues:

  • Stale Builds: Modifying a rule, updating an alias, or tweaking a loader option in an unlisted configuration file will not bust the cache. Webpack will continue serving artifacts generated under the old configuration.
  • Inconsistent Environments: Builds executed on CI/CD pipelines may behave differently from local environments because of lingering local cache directories.
  • Wasted Debugging Time: Developers frequently encounter "phantom bugs" caused by out-of-sync cache entries, forcing them to manually delete the node_modules/.cache directory to resolve build anomalies.

Implementing cache.buildDependencies

To resolve this, you must explicitly declare your configuration entry points under the config array within cache.buildDependencies. Webpack will resolve these files and all of their direct dependencies, automatically generating a cache hash based on their contents.

const path = require('path');

module.exports = {
  // ...
  cache: {
    type: 'filesystem',
    buildDependencies: {
      // Treat this file and any of its dependencies as build dependencies
      config: [
        __filename,
        path.resolve(__dirname, 'webpack.parts.js'),
        path.resolve(__dirname, 'postcss.config.js')
      ],
    },
  },
};

What Files Should Be Included?

You should include any file that directly controls the build output. Recommended targets include:

  • Modular Webpack Configs: Base configurations, environment-specific overrides, and shared helper scripts.
  • External Tool Configurations: Files like babel.config.js, postcss.config.js, or tsconfig.json if Webpack loaders rely on them directly.
  • Environment Files: Files defining build-time environment variables or build flags that alter how loaders and plugins operate.

Explicitly declaring these custom files ensures Webpack achieves maximum build performance without sacrificing build integrity.
